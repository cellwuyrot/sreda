# Обновление TZ ID: редактор приложений и длительные сессии Business

## Что поставляется

- **sreda-tz-id-admin-update.zip** — обновлённый основной проект из присланного sreda-main.zip. Изменены только редактор приложений TZ ID, API управления, связанные компоненты/тесты и эта документация. Процесс PM2: **trioz**.
- **tzbiz-1.3.2-session-update.zip** — полный исходный код Business 1.3.2 с предыдущими исправлениями 1.3.0/1.3.1 и обновлением сессий. Процесс PM2: **tzbiz**.
- **tz-id**: код issuer не изменён, новых миграций его БД нет, перезапуск для этого обновления не требуется. Его adapter читает динамические настройки клиента из БД.

Не распаковывайте один проект поверх другого. Содержимое папки из каждого архива переносится в корень соответствующего существующего Git-репозитория. Сначала сделайте commit текущего исходного кода и резервные копии рабочих .env и БД. Не заменяйте серверные .env примерами из архивов. Не удаляйте uploads, секреты, ключи и базы. Исторические отчёты и UPDATE-MANIFEST.json в основном проекте относятся к предыдущим обновлениям; актуальные изменения перечислены в TZ-ID-SESSION-CHANGED-FILES.txt.

Поставка — исходники, не готовая .next-сборка и не дамп БД. Не копируйте node_modules между серверами. Не обновляйте Prisma до предлагаемой RC/major-версии.

## 1. Обновить основной проект — PM2 trioz

Примеры используют `/var/www/trioz` из присланного ecosystem.config.cjs. Сначала проверьте фактическую рабочую папку:

```bash
/usr/bin/pm2 show trioz
/usr/bin/pm2 show tz-id
```

Если cwd отличается, используйте фактический корень монорепозитория (в нём package.json и папка apps). После переноса обновлённых исходников в Git и push выполните по порядку. При любой ошибке остановитесь; не выполняйте последующие команды.

```bash
cd /var/www/trioz
git pull --ff-only
export PATH="/opt/tzbiz-node22/current/bin:$PATH"
hash -r
node -v
npm ci --ignore-scripts
npm exec -w apps/web -- prisma generate
npm run test -w apps/web -- --maxWorkers=2
npm run test -w apps/id
npm run build
```

Используется уже установленный для Business отдельный Node 22, системный `/usr/bin/node` не заменяется. Если указанного бинарника нет, остановитесь и найдите рабочий Node >=22.12 из настройки вашего tz-id. Не устанавливайте новый Node глобально наугад. `--ignore-scripts` не запускает lifecycle-скрипты остальных workspace (в том числе desktop); Prisma генерируется явно, build собирает shared и web.

**Только после успешной сборки:**

```bash
/usr/bin/pm2 restart trioz --update-env
/usr/bin/pm2 save
/usr/bin/pm2 logs trioz --lines 60 --nostream
```

Интерпретатор процесса не переопределяется. В этом обновлении нет новых миграций основной БД, поэтому `migrate` ради данного обновления не запускается. Если у вас ещё не установлены миграции предыдущего присланного проекта, это отдельное обновление по его исходной инструкции.

**tz-id сейчас не перезапускайте.** Команда для его отдельного перезапуска, только если он действительно понадобится по другой причине: `pm2 restart tz-id --update-env`. Она не входит в обязательные шаги этого релиза. Не выполняйте pm2 update/kill/restart all и не перезапускайте pm2-root.service.

## 2. Включить продление именно у существующего Business

В основной платформе откройте **Администрирование → TZ ID**.

1. Найдите существующее приложение Business и нажмите **Настроить**.
2. Убедитесь, что адрес возврата остался прежним: `https://business.trioz.ru/api/auth/tz-id/callback` (если были дополнительные действующие адреса, сохраните их).
3. Включите **Продлевать вход без повторной авторизации**.
4. Сохраните разрешение **Проверять права администратора своего проекта** и остальные ранее нужные разрешения.
5. Нажмите **Сохранить изменения**. Проверьте, что у приложения отображается «Продление входа разрешено».

Не создавайте новый клиент вместо существующего. Client ID, секрет, тип приложения и назначения администраторов сохраняются. Секрет при редактировании не возвращается браузеру. Новые разрешения начинают действовать после повторного входа и согласия пользователя.

Изменение адресов возврата или уменьшение прав отзывает старые авторизации приложения. Это преднамеренная мера защиты; назначения администраторов при этом не удаляются. Отключение входа также отзывает доступ, а включение не восстанавливает старые сеансы.

## 3. Обновить Business — PM2 tzbiz

Перенесите исходники Business из второго архива в его существующий Git-репозиторий, commit/push. На сервере:

```bash
cd /var/www/tzbiz
git pull --ff-only
export PATH="/opt/tzbiz-node22/current/bin:$PATH"
hash -r
node -v
```

В рабочем `.env` добавьте или замените **одну** строку (не создавайте дубликаты):

```dotenv
TZ_ID_OFFLINE_ACCESS="1"
```

Не меняйте SESSION_SECRET, TZ_ID_TOKEN_KEY, Client ID/secret и банковские реквизиты.

В этом проекте есть **одна новая добавочная миграция** `20261028200000_tz_session_refresh`: три nullable-поля таблицы Session. Старые пользователи, заказы, счета и платежи не меняются. Перед её применением сделайте резервную копию БД. Для известной по вашему выводу базы `tzbiz_business`, под root на Ubuntu:

```bash
umask 077
runuser -u postgres -- pg_dump -Fc tzbiz_business > "/root/tzbiz-before-session-$(date +%Y%m%d-%H%M%S).dump"
```

Если имя БД или PostgreSQL-пользователь иные, используйте свою штатную процедуру резервного копирования. При ошибке резервирования не продолжайте. Команда не выводит DATABASE_URL/пароль в чат.

Установите зависимости, проверьте код, затем примените миграцию и соберите приложение:

```bash
npm ci
npm run db:generate
npm run images:check
npm test
npm run db:deploy
npm run build
```

При любой ошибке остановитесь. Не запускайте db:setup, db:seed, migrate reset, git reset --hard или git clean. PostgreSQL-миграция checkout из версии 1.3.0 остаётся неизменной. Обработчик ImageMagick из 1.3.1 сохранён.

**Только после успешных тестов, миграции и сборки:**

```bash
TZ_ID_OFFLINE_ACCESS=1 /usr/bin/pm2 restart tzbiz --interpreter /opt/tzbiz-node22/current/bin/node --update-env
/usr/bin/pm2 save
/usr/bin/pm2 show tzbiz
/usr/bin/pm2 logs tzbiz --lines 60 --nostream
```

Префикс TZ_ID_OFFLINE_ACCESS=1 обновляет также сохранённое окружение PM2 именно для tzbiz. Не перезапускайте другие приложения.

## 4. Проверка на рабочем сайте

1. Выйдите из Business и войдите через TZ ID заново. Старые пятиминутные сессии автоматически не превращаются в длительные.
2. Подтвердите согласие на продление входа. Проверьте кабинет и, для назначенного администратора Business, админку.
3. Через 6–10 минут продолжите работу, откройте кабинет в нескольких вкладках и сохраните обычное изменение. Повторный вход из-за истечения access token не должен требоваться.
4. Проверьте обычный выход из Business: закрытый кабинет не должен открываться без входа.
5. На отдельном тестовом аккаунте проверьте отзыв доступа приложения в TZ ID — после него Business должен требовать новый вход. Не отключайте рабочий Business ради теста всех клиентов: это отзовёт доступ всем.
6. Проверку отзыва прав администратора проводите с отдельным тестовым пользователем, сохранив доступ владельца.

Реальные действия на вашем сервере этими архивами ещё не выполнялись. Локальные проверки не заменяют этот smoke-test после развёртывания. Не присылайте cookies, токены, .env и пароли в чат.

## Как теперь устроена сессия

- Access token TZ ID по-прежнему живёт 5 минут — это защита, не таймер выхода из кабинета.
- Business обновляет его до истечения и хранит refresh token только зашифрованным на сервере.
- Локальная cookie/сессия с refresh grant ограничена 7 днями, но действительный доступ ограничен также центральным сеансом TZ ID. В присланном issuer тот живёт **2 дня**, refresh token — до 30 дней и не обходит отзыв/завершение центрального сеанса. «30 дней гарантированного входа» не обещается.
- Без разрешения на продление или без выданного refresh token остаётся старый короткий режим. Включение проверяется и в основном клиенте, и в .env Business.
- Одновременные запросы координируются в процессе и атомарно через БД. Старый refresh token помечается использованным до сетевого обмена, чтобы после сбоя процесса/потери ответа не повторить его и не отозвать весь grant.
- При временном сбое discovery доступ к запросу закрывается, но токен не удаляется. При неоднозначном сбое уже начатой ротации прежний token не повторяется: после защитного ожидания может потребоваться новый вход. Это безопаснее бесконечных повторов одноразового token.
- Выход, отзыв доступа и проверка актуальной роли администратора не отключены.

## Откат

Сохраните предыдущие commits и сборки перед обновлением. Если новый Business не работает, не сбрасывайте БД: добавленные nullable-поля совместимы с предыдущим кодом. Откатите исходники на заранее сохранённую версию, верните TZ_ID_OFFLINE_ACCESS=0 в .env и в окружении PM2, выполните её проверки/сборку и перезапустите только tzbiz. Старый код снова будет требовать вход после короткого токена. Редактор TrioZ можно откатить отдельно без изменения БД. Не восстанавливайте всю БД из дампа поверх появившихся после обновления заказов без отдельного плана восстановления.
