# Ручные назначения и доверительный доступ — обновление

Это обновление заменяет прежнее ограничение «только просмотр» в основной админке. Платежей, банковских форм и подтверждения оплаты на trioz.ru по-прежнему нет. Обновляются основной проект sreda (PM2 trioz) и Business (PM2 tzbiz). Код приложения apps/id не менялся; PM2 tz-id перезапускать не требуется.

## Что изменилось

### Ручная выдача
Основной проект → администрирование → Подписки пользователей → карточка пользователя → «Ручная выдача и отзыв подписки». Выберите Надёжное соединение или Premium (включает соединение), 1/3/6/12 месяцев или бессрочно. Укажите основание не короче 5 символов. Продление добавляет срок к действующим ручным периодам; независимые банковские права не меняются. Отзыв снимает только выбранное ручное назначение. Действия записываются в аудит. Только глобальный ADMIN основного проекта может выдавать эти глобальные права; обычного администратора подключённого приложения недостаточно.

Ручное назначение не создаёт фиктивной оплаты и не превращает Business PENDING в ACTIVE: финансовая заявка и отдельное ручное право намеренно различаются. Ручные назначения отображаются в основной админке; письма покупки относятся к оформлению в Business, не к этой форме.

### Временный доступ
Business → администрирование → Оплаты и контроль подключения → Доверительный доступ. По умолчанию 24 часа, настройка 0–168 часов. 0 отключает новые выдачи, существующие сроки не изменяет.

Доступ выдаётся только для первой заявки VPN/PREMIUM после успешного Init с сохранённым PaymentId, при NEW/FORM_SHOWED/AUTHORIZED. Банк должен реально создать платёж: одного локального CREATING или сетевого таймаута недостаточно. Восстановление пропущенной выдачи возможно только в течение 15 минут после создания заявки. Старые зависшие заявки не получают новый бесплатный период. Для счёта, физических ручных услуг и повторного продления кредит не предоставляется.

Один временный период на пару аккаунт TZ ID + услуга. Создание новой заявки не обновляет лимит. Тип доступа TRUSTED, источник TRUST — явно не «оплачено»; paidUntil остаётся пустым, paidIndex равен -1. После CONFIRMED выдаётся полный согласованный оплаченный срок от подтверждения банка. При окончательном отказе/отмене либо истечении доверительного срока отзывается только это право. Другие оплаченные, ручные и ролевые права сохраняются. Просрочка не отменяет операцию в банке и не запускает возврат. Позднее подтверждение учитывается, если пользователь явно не остановил заявку.

Применение VPN на узле происходит в рамках штатной синхронизации разрешённых пиров, не обязательно в ту же секунду. Не следует считать физическое подключение выполненным до успешной синхронизации.

### Письма
Business ставит в очередь сообщения об оформлении заявки, доверительном подключении, подтверждении оплаты/подключения, напоминании и отмене/завершении. Получатель — регистрационный email пользователя; используется существующая SMTP-конфигурация. Чеки банка/кассы остаются отдельной фискальной процедурой. Напоминание по кредиту: в последние 6 часов, но не раньше половины срока; обычное неоплаченное оформление — через сутки; оплаченный период — за сутки. Это не почасовая рассылка. Устаревшие напоминания об оплате и доверительном доступе не отправляются, если подтверждение банка или более новая версия доступа уже получены (SKIPPED). Неопределённый результат SMTP UNKNOWN не повторяется автоматически во избежание дублей.

## Установка после переноса файлов в соответствующие Git-репозитории

1. Сделайте проверенные резервные копии обеих PostgreSQL БД, .env и пользовательских файлов. Проверьте git status; при локальных изменениях не используйте reset --hard. Не заменяйте .env содержимым .env.example, не загружайте секреты в Git.
2. На время обновления приостановите существующую фоновую задачу Business; обновляйте в короткое окно обслуживания. Не запускайте одновременно cron и systemd timer одной задачи.
3. Сначала основной проект, затем Business. Обе новые миграции называются 20261030000000_trust_access, каждая находится в своей БД. Это добавочные миграции, не сброс БД. Не используйте migrate reset или db push.

Основной проект:

```bash
cd /var/www/trioz &&
export PATH="/opt/tzbiz-node22/current/bin:$PATH" &&
git pull --ff-only &&
npm ci &&
npm run migrate &&
npm run test -w apps/web -- --maxWorkers=2 &&
npm run build &&
/usr/bin/pm2 restart trioz --update-env &&
/usr/bin/pm2 save
```

Business (сохраняет уже настроенные доверенные CA; проверку TLS не отключать):

```bash
cd /var/www/tzbiz &&
export PATH="/opt/tzbiz-node22/current/bin:$PATH" &&
export NODE_EXTRA_CA_CERTS=/etc/ssl/certs/ca-certificates.crt &&
git pull --ff-only &&
npm ci &&
npm run db:generate &&
npm run db:deploy &&
npm test -- --maxWorkers=2 &&
npm run build &&
/usr/bin/pm2 restart tzbiz --update-env &&
/usr/bin/pm2 save
```

Команды предполагают существующий Node 22 по указанному пути и текущие PM2 процессы. Не заменяют глобальный Node и не перезапускают остальные приложения. Если pull сообщает локальный конфликт — остановитесь и сохраните изменения, не удаляйте миграции. Предыдущий commit может быть несовместим с новыми статусами TRUSTED: при откате сначала остановите новые покупки и фоновые задачи; не откатывайте БД вслепую.

## Фоновая обработка обязательна

PM2 restart сам по себе не запускает расписание Business. В основном проекте сроки managed-доступов проверяются штатным сервером раз в минуту. Business должен ежеминутно сверять банк, обрабатывать очередь синхронизации и писем.

Перед включением просмотрите существующие `crontab -l` и systemd timers. Оставьте только один планировщик. Полная задача `jobs:run` МОЖЕТ ОТПРАВЛЯТЬ РЕАЛЬНЫЕ РЕКУРРЕНТНЫЕ СПИСАНИЯ, если они разрешены настройками и согласиями. Не запускайте её как безобидный тест. Не меняйте TerminalKey или глобальные переключатели рекуррентов ради установки.

Пример ОДНОЙ строки cron для полной штатной обработки после проверки накопленных задач и разрешений банка:

```cron
* * * * * cd /var/www/tzbiz && /usr/bin/flock -n /var/lock/tzbiz-services.lock /usr/bin/env PATH=/opt/tzbiz-node22/current/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin NODE_ENV=production NODE_EXTRA_CA_CERTS=/etc/ssl/certs/ca-certificates.crt /opt/tzbiz-node22/current/bin/node node_modules/tsx/dist/cli.mjs scripts/jobs.ts >> /var/log/tzbiz-jobs.log 2>&1
```

Для первоначальной проверки без запросов в банк и без списаний есть отдельная команда:

```bash
cd /var/www/tzbiz &&
export PATH="/opt/tzbiz-node22/current/bin:$PATH" &&
npm run services:check &&
/usr/bin/flock -n /var/lock/tzbiz-services.lock npm run services:deliver
```

`services:check` — диагностика без оплаты. `services:deliver` НЕ read-only: передаёт изменения доступа в TZ ID, снимает истёкший временный доступ, ставит/отправляет письма. Не вызывает Init, Charge, GetState и не создаёт новые бесплатные периоды. Это не замена полной сверки: при пропущенном callback без jobs:run нужно нажать «Проверить существующий платёж» в админке. Не запускайте delivery параллельно с полной задачей без общего flock.

Если используете имеющиеся systemd unit-файлы из deploy/, проверьте User/Group, путь Node22 и NODE_EXTRA_CA_CERTS: старый ExecStart через системный npm может использовать Node20. Не устанавливайте unit без адаптации к вашему серверу.

## Проверка на сервере

1. Под ADMIN выдайте тестовому аккаунту VPN на месяц, обновите страницу и войдите этим пользователем. Отзовите только созданное назначение; чужие права должны сохраниться. Затем проверьте Premium и бессрочное назначение.
2. Для проверки банка используйте отдельный тестовый терминал и тестовый аккаунт. Не меняйте ключ у живой заявки, не используйте реальную карту в тестовом терминале. Старые зависшие заявки не удаляйте и не отмечайте «оплачено» без подтверждения банка.
3. Создайте НОВУЮ заявку на услугу с автоматическим типом VPN. После успешного Init при настройке 24 ч ожидайте TRUSTED и срок до, а не оплаченную подписку. В основном проекте после синхронизации появится право с источником TRUST.
4. Успешная тестовая оплата должна дать банковский CONFIRMED, Business ACTIVE с paidUntil и источник PAID в основном проекте. Возврат по successUrl сам по себе ничего не доказывает.
5. При отклонении банк должен вернуть окончательный отказ: временное право снимается, paidUntil не появляется; другие права остаются. Для проверки срока можно настроить 1 час для НОВЫХ заявок. Не редактируйте время в production БД ради теста.
6. Проверьте письма в регистрационном ящике и журнале SMTP. UNKNOWN разбирайте отдельно; не запускайте массовую повторную рассылку.
7. Старой спорной заявке можно независимо выдать ручное право на согласованный срок. Это не решает банковскую сверку и не подтверждает оплату; сохраняйте PaymentId и проверяйте его в том же терминале.

Локальные тесты выполнены на заглушках банка/SMTP и временной SQLite БД Business. Реальный терминал, касса, доставка в пользовательский ящик и production PostgreSQL здесь не проверялись. Изменения на ваш сервер не устанавливались.
