# Мониторинг проектов — установка

Обновляются два репозитория: **sreda (PM2 trioz)** и **tzbiz (PM2 tzbiz)**.
`apps/id` и процесс `tz-id` менять/перезапускать не нужно. Существующий вход через TZ ID остаётся: аккаунты и пароли не копируются.
Новые показатели появятся только после установки агента, создания привязок и настройки проверок. Архив сам по себе не подключает ваши серверы.

## 1. Подготовка и резервные копии

Архивы содержат полный исходный код, не `node_modules`, `.next`, рабочие `.env`, БД и пользовательские загрузки.
Включите новые файлы в соответствующие Git-репозитории и отправьте изменения из своей рабочей копии. Не пушьте `.env`, токены агентов и сертификаты с закрытыми ключами.
На сервере сделайте резервные копии обеих БД и `.env` по вашей обычной процедуре; проверьте возможность восстановления. Не заменяйте секреты, банковские настройки, `TZ_ID_TOKEN_KEY`, `TZ_ID_STORAGE_KEY`, `ENCRYPTION_SECRET` и существующие TLS CA.

Перед `git pull` проверьте `git status --short`. Если Git сообщает о локальных/неотслеживаемых миграциях или изменениях, остановитесь: сначала сравните и сохраните их. **Не выполняйте `git reset --hard`, `git clean` или удаление миграций ради обновления.** Миграции этого выпуска добавочные; уже применённые не редактируются.

## 2. Настройка связи до запуска

В `/var/www/trioz/apps/web/.env` добавьте:

```dotenv
MONITOR_BUSINESS_CLIENT_ID=идентификатор_существующего_серверного_приложения_Business
```

Это **тот же ID**, что `TZ_ID_CLIENT_ID` в Business. Не TerminalKey банка. Используется уже существующий клиент TZ ID типа «сайт с сервером», его действующий секрет и пользовательский access token. Нового OIDC-клиента и нового секрета создавать не нужно. Не меняйте существующие области доступа для подписок.

В `/var/www/tzbiz/.env` добавьте:

```dotenv
PROJECT_MONITOR_ENABLED=1
```

Существующие `TZ_ID_CLIENT_ID`, `TZ_ID_CLIENT_SECRET`, ключ шифрования и issuer `https://id.trioz.ru` должны оставаться правильными. Business обращается только к фиксированному HTTPS-адресу `https://trioz.ru/api/integrations/project-monitor`; главному проекту нужны доступ к своей БД и правильное время. На сервере не отключайте TLS-проверку.
Если параметры также заданы в ecosystem/окружении PM2, приведите их к тем же значениям: старое значение в окружении процесса может перекрывать `.env`.

## 3. Сначала основной проект

```bash
cd /var/www/trioz &&
export PATH="/opt/tzbiz-node22/current/bin:$PATH" &&
git pull --ff-only &&
npm ci &&
npm run migrate -w apps/web &&
npm run test -w apps/web -- --maxWorkers=2 &&
npm run build &&
/usr/bin/pm2 restart trioz --update-env &&
/usr/bin/pm2 save
```

Новая миграция: `20261031000000_project_monitoring` — размещения проектов, снимки метрик, отдельный heartbeat мониторинга. Обновлён и `apps/web/server.ts`: история старше семи дней чистится раз в час. Запускайте обычный custom server проекта, не заменяйте его на `next start`: он также обслуживает realtime и фоновые задачи.

## 4. Затем Business

```bash
cd /var/www/tzbiz &&
export PATH="/opt/tzbiz-node22/current/bin:$PATH" &&
export NODE_EXTRA_CA_CERTS=/etc/ssl/certs/ca-certificates.crt &&
git pull --ff-only &&
npm ci &&
npm run db:generate &&
npm run db:deploy &&
npm test -- --maxWorkers=2 &&
npm run build &&
/usr/bin/pm2 restart tzbiz --update-env &&
/usr/bin/pm2 save
```

Новая миграция Business `20261031000000_consultant_cabinet` добавляет значение `CONSULTANT` в PostgreSQL Role; SQLite-вариант также включён. Скрипт проекта сам выбирает поставщика по `DATABASE_URL`.
Не обновляйте глобальный Node и не перезапускайте все процессы PM2. Существующие задания подписок/почты не заменяются и не создаются повторно этой инструкцией.

## 5. Аккаунт партнёра и проект

1. В TrioZ назначьте нужному аккаунту роль **CONSULTANT**. Используйте его точный ID, не ID другого пользователя с похожим email.
2. Откройте **Администрирование → Сервисы и система → Проекты и серверы** (`/admin/monitor`). Раздел доступен ADMIN.
3. Создайте проект и укажите ID владельца CONSULTANT. Существующему проекту можно изменить владельца/название здесь же. Проекты создаёт только ADMIN; прежняя кнопка создания для CONSULTANT убрана, API также закрыт.
4. В Business войдите **тем же аккаунтом TZ ID** → «Мои проекты» (`/dashboard`). Партнёр получает личный кабинет, не админку Business, без доступа к чужим серверам и проектам. Роль проверяется на сервере, не берётся из параметра URL.

Партнёрская роль CONSULTANT и проектные права администратора Business — разные полномочия. Если этому же аккаунту отдельно выдан ADMIN в Business, существующая админская навигация имеет приоритет. Для проверки партнёрского сценария используйте CONSULTANT без проектного ADMIN Business.

## 6. Зарегистрировать машину и установить агент

Для каждого хоста с PM2, включая текущий сервер, создайте в разделе **Серверы** отдельную запись:
- назначение **Приложение (APP)**;
- роль **Дочерний (CHILD)** — это логическая роль коллектора, даже на текущей физической машине;
- понятное имя, например `monitor-main` или `monitor-shop-1`;
- поле адреса для этого сборщика не используется: можно оставить пустым; входящий HTTP/SSH-порт агенту не нужен.

Сохраните выданный токен: он показывается один раз. Не используйте токен другого VPN/хранилища. Мониторинг имеет отдельное время последнего отчёта и не делает неработающий VPN-агент «онлайн».

На текущем сервере исходники агента уже лежат в обновлённом sreda. Пример, **если PM2 работает от root**, Node 22 находится по знакомому пути, а PM2 — `/usr/bin/pm2`:

```bash
sudo bash /var/www/trioz/deploy/monitor-node.sh \
  --repo=/var/www/trioz \
  --user=root \
  --node=/opt/tzbiz-node22/current/bin/node \
  --pm2=/usr/bin/pm2 \
  --pm2-home=/root/.pm2
```

Скрипт запросит токен скрытым вводом и создаст только службу `trioz-monitor`. Существующие PM2-приложения не перезапускаются. Node должен быть >=20; рекомендуется уже установленный Node 22. Если Node/PM2 отсутствуют, установщик остановится — он не ставит пакеты и не меняет Node других проектов.

На новом сервере можно получить только нужные исходники:

```bash
git clone --depth 1 --filter=blob:none --sparse https://github.com/cellwuyrot/sreda /opt/trioz
cd /opt/trioz && git sparse-checkout set deploy apps/monitor
```

Если `/opt/trioz` уже существует, **не клонируйте поверх и не сбрасывайте sparse-набор VPN**. После проверки локальных изменений:

```bash
cd /opt/trioz && git pull --ff-only && git sparse-checkout add apps/monitor deploy
```

Далее запустите `deploy/monitor-node.sh` с реальными путями Node/PM2 и владельцем PM2 этой машины. Для непривилегированного владельца укажите, например, `--user=deploy --pm2-home=/home/deploy/.pm2`. Не запускайте второй PM2-демон от root вместо существующего пользователя. Один агент обслуживает один PM2_HOME на хосте. Несколько разных PM2_HOME на одной машине требуют отдельных экземпляров службы/конфигурации (установщик этого выпуска создаёт один); обычные PM2 namespace поддерживаются.

## 7. Привязать PM2 и настроить здоровье/размер папки

В `/admin/monitor` добавьте размещение: проект, созданный APP-узел, **точное имя PM2**, namespace (обычно `default`). Можно несколько компонентов/серверов у одного проекта. Кластер PM2 с одинаковым именем/namespace считается одним размещением, метрики процессов суммируются. Одна и та же привязка узел+имя+namespace не выдаётся двум проектам. В этом выпуске — максимум 100 включённых размещений на агент и 20 файловых систем; не превышайте эти лимиты.

Скопируйте **ID размещения** из карточки. На соответствующем хосте откройте локальный файл:

```bash
sudo nano /etc/trioz-monitor/config.json
```

Сохраните уже имеющиеся `token`, `pm2Bin`, `pm2Home`, `mainUrl`. Добавьте реальные значения в секции (это фрагмент, не замена всего файла):

```json
{
  "healthChecks": {
    "ID_РАЗМЕЩЕНИЯ": "http://127.0.0.1:3000/ПУТЬ_ПРОВЕРКИ_ВАШЕГО_ПРИЛОЖЕНИЯ"
  },
  "projectPaths": {
    "ID_РАЗМЕЩЕНИЯ": "/var/www/папка-этого-проекта"
  },
  "disks": [
    { "path": "/", "label": "rootfs" }
  ]
}
```

Укажите **существующий** порт/endpoint приложения, возвращающий HTTP 2xx без перенаправления. Пример пути выше не является готовым `/health` вашего сайта: отдельный endpoint автоматически не добавлен. Агент разрешает только `127.0.0.1` или `[::1]`, HTTP/HTTPS без логина/пароля и без redirect. Проверка публичного домена не подменяет здоровье локального процесса. Для фонового worker можно снять «Требовать HTTP-проверку»: тогда проверяется только PM2 online, не успешность его задач. Эту настройку и обязательность компонента можно менять в карточке без удаления привязки.

Файл доступен только владельцу агента (`600`); никогда не публикуйте его и не присылайте целиком в чат.

```bash
sudo systemctl restart trioz-monitor
sudo systemctl status trioz-monitor --no-pager
sudo journalctl -u trioz-monitor -n 20 --no-pager
```

Через 30–90 секунд проверьте карточку проекта. Первый замер размера папки может быть «Нет данных»: `du` выполняется в фоне, чтобы не задерживать heartbeat.

## 8. Что измеряется и ограничения

- CPU машины — по разнице системных CPU-счётчиков; RAM — `/proc/meminfo`, Load — системная средняя. CPU приложения и RAM его процессов — из PM2, не доля всего сервера. Сумма CPU кластера может быть больше 100%.
- Сервер перегружен при CPU >=90% или доступной RAM <10%; только свежие измерения. Это диагностический порог, не SLA и не внешняя проверка доступности.
- Диски — доступное место файловых систем через `statfs`. В сводке «занято» включает зарезервированное место (`total - bavail`); повторно указанные пути одной файловой системы не суммируются.
- Размер папки проекта — логический `du --apparent-size`, без квоты и без обещания точного физического расхода. Нет доступа/таймаут/нет пути → «Нет данных», не 0. Обновление примерно раз в 5 минут, одна фоновая проверка за раз. Не назначайте партнёру корень сервера или общую папку других проектов.
- Хосты дедуплицируются по SHA-256 `/etc/machine-id`; у разных физических машин machine-id должен быть разным. Основной и дополнительные диски нужно перечислить отдельно. Контейнерные лимиты/cgroup не вычисляются: ставьте агент на хост, не в контейнер, если нужны показатели всей машины.
- Статусы: работает / частично работает / недоступен / нет свежих данных / отключён. Старше 2 минут — не «работает». «Проектов работает» считает только полностью работающие проекты; остальные состояния показаны отдельно. Список PM2 недоступен → неизвестно; доступен, но процесса нет → недоступен.
- История сохраняется примерно 7 дней, очистка раз в час custom server. Business получает последние до 48 отчётов за последние сутки и показывает до 12; это не график за сутки, не процент uptime и не система оповещений.
- Браузер обновляет мониторинг каждые 30 секунд и при возврате в окно. Агент делает цикл с паузой 30 секунд после сбора/отправки. Остановка вкладки сбор не останавливает.
- Управления PM2/SSH, рестартов, консоли и удаления файлов из интерфейса нет. Агент выполняет только `pm2 jlist`, чтение метрик, локальную health-проверку и `du`. Работает с правами владельца PM2: это доверенный локальный процесс, не изолированная песочница. Службе разрешена запись только в PM2_HOME для служебного обмена PM2.
- Роль/владелец проверяются на каждом запросе Business; вывод, уже показанный в открытой вкладке, исчезнет после следующего обновления. Сбой связи не превращается в успешный пустой список и не выдаёт чужие данные.

## 9. Приёмка на ваших серверах

1. Назначить CONSULTANT два тестовых проекта разным аккаунтам; каждый видит только свой.
2. Проверить один PM2-процесс текущей машины и один удалённый; сравнить с PM2/системными средствами под правильным владельцем. Не публиковать `pm2 jlist`: там могут быть секреты.
3. В безопасном тестовом проекте остановить процесс обычным способом → «Недоступен»; вернуть → «Работает». Не останавливать production ради теста.
4. Остановить **только агент** `sudo systemctl stop trioz-monitor`; через >2 минут → «Нет свежих данных». Вернуть `sudo systemctl start trioz-monitor`.
5. Проверить передачу владельца и отзыв CONSULTANT: новый запрос старого партнёра не должен возвращать проект.
6. Убедиться, что подписки/почта/вход/обмен сообщениями работают по прежнему сценарию. Этот выпуск не проводит банковские операции.

## Отключение / откат

Можно снять привязку/выключить мониторинг в карточке — PM2 и файлы не меняются. Для отключения службы: `sudo systemctl disable --now trioz-monitor`. Для отключения Business-функции: `PROJECT_MONITOR_ENABLED=0` и перезапуск только `tzbiz` с обновлением окружения. Не удаляйте таблицы и enum при обычном откате исходников: миграции добавочные. Очистка старой истории не удаляет пользовательские файлы.
