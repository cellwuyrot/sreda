# Ревью проекта `sreda-main`

Дата: 2026-09-30  
Метод: статический анализ исходного кода (Next.js 16, React 18, Prisma, Socket.IO/WebRTC). В архиве не было `node_modules`, поэтому сборка и тесты не запускались. Обнаружено 119 тестовых файлов, но нет целевых тестов календаря и восстановления screen share.

## Краткий итог

- **P0:** 1 критический сценарий восстановления приватной трансляции.
- **P1:** 5 существенных дефектов/рисков в трансляции, календаре и сообщениях.
- **P2:** 6 UX/целостностных проблем.
- Два исходных замечания подтверждены: плашка трансляции не перетаскивается; удаление календарного события реализовано частично и плохо доступно из основного месячного сценария.

## Заявленные дефекты

### 1. Плашка «Идёт трансляция» перекрывает чат и не перемещается — подтверждено (P1)

**Код:** `apps/web/src/components/voice/ScreenShareWindow.tsx:433–479`.

Плашка рендерится через portal с `position: fixed`; координаты жёстко рассчитываются от области контента (`left + 16`, `top + height - 64`). Обработчиков drag/pointer у неё нет. Перетаскивание реализовано только для режима мини-окна ниже по файлу.

**Последствие:** на небольших окнах, при изменённой компоновке или высоте composer плашка может закрывать чат/управление и пользователь не может убрать её в другое место. Кнопка «Скрыть» не является полноценной заменой перемещению.

**Исправление:** переиспользовать drag-механику mini-окна для плашки, ограничивать координаты viewport/контейнером чата, хранить позицию в `sessionStorage`/local state, добавить сброс позиции. Альтернатива — закреплять плашку в отдельном layout-slot над composer, а не поверх контента.

### 2. Удаление события календаря — частично реализовано, но UX неполный (P1)

**API уже есть:** `DELETE /api/calendar/[id]` в `apps/web/src/app/api/calendar/[id]/route.ts:64–74`; роли OWNER/ADMIN/MODERATOR и автор проходят проверку.

**UI:** удаление доступно только в списочном представлении: `CalendarPanel.tsx:89–93` и кнопка в карточке списка. В месячном представлении клик по событию всегда открывает `EventForm`, но в форме нет кнопки удаления (`CalendarPanel.tsx:220–303`). Поэтому основной сценарий «месяц → событие» не даёт администратору удалить запись.

Дополнительно обычный участник тоже может открыть редактируемую форму из месяца и увидеть кнопку «Сохранить», после чего получить 403 от сервера.

**Исправление:** передавать в форму `canManage = canEdit || authorId === currentUserId`; для управляющих добавить опасную кнопку «Удалить», для остальных показывать read-only карточку события. После удаления обновлять локальный список и закрывать форму.

## Возможные баги при общении пользователей

### P0 — восстановление приватной трансляции может потерять состояние доступа

**Код:** `apps/web/src/contexts/VoiceContext.tsx:2834–2839`.

После reconnect клиент повторно отправляет `screen-share-started`, но **без `allowUserIds`**. Сервер трактует отсутствие списка как публичную трансляцию (`apps/web/server.ts:1565+`). При этом событие отправляется сразу вслед за асинхронным `join-voice` и может быть проигнорировано сервером, если новая socket-сессия ещё не добавлена в voice room.

Получаются два гоняющихся исхода:
1. событие приходит слишком рано — трансляция после reconnect не восстанавливается у зрителей;
2. событие принимается — приватное состояние заменяется публичным.

Даже если видеотреки на клиенте дополнительно фильтруются, сам факт приватной трансляции и её состояние могут раскрыться, а дальнейшее поведение зависит от renegotiation.

**Исправление:** повторно объявлять трансляцию только после `voice-joined`; передавать `allowUserIds: screenAllowRef.current ? [...screenAllowRef.current] : null`; на сервере не позволять повторному announce без списка расширять уже приватное состояние. Добавить интеграционный тест reconnect для public/private share.

### P1 — нет rate limit для отправки личных сообщений

**Код:** `apps/web/src/app/api/dm/[id]/route.ts`, обработчик POST.

Для сообщений канала есть лимит 30/мин, для звонков — socket flood control, но POST личных сообщений не вызывает `rateLimit`. Авторизованный пользователь может быстро создать большое число DM, realtime-событий, уведомлений и push-сообщений.

**Риск:** спам/травля, нагрузка на БД и push-инфраструктуру.

**Исправление:** лимит по user + conversation/IP; отдельный более строгий лимит уведомлений; 429 с `Retry-After`; тест burst/concurrency.

### P1 — редактирование/удаление сообщений канала не перепроверяет актуальный доступ

**Код:**
- PATCH: `apps/web/src/app/api/messages/route.ts:472–520`;
- DELETE: `apps/web/src/app/api/messages/route.ts:558–614`.

PATCH проверяет авторство и бан, но не `getChannelPermissions`/членство/паузу/тайм-аут. DELETE для автора не проверяет ни актуальное членство, ни бан. Исключённый из сообщества автор с живой сессией может менять или удалять старые сообщения, а PATCH создаёт новые mention-уведомления и realtime-события внутри уже недоступного канала.

**Исправление:** перед каждой мутацией проверять как минимум `canView`; для edit — также действующие правила редактирования и запрет после исключения/бана. Явно определить продуктовую политику удаления собственного сообщения после выхода.

### P1 — пустые сообщения проходят при `attachments: []`

**Код:**
- каналы: `apps/web/src/app/api/messages/route.ts:160+`, повторная проверка около `258`;
- DM: `apps/web/src/app/api/dm/[id]/route.ts`, POST.

Пустой массив в JavaScript truthy. Проверка `(!content && !attachments)` считает `[]` вложением, затем сохраняется `attachments: "[]"`. В итоге можно создать пустой bubble и обойти ожидаемую валидацию.

**Исправление:** вычислять `hasAttachments = Array.isArray(attachments) && attachments.length > 0`; запрещать пустой массив при пустом тексте. Нормализовать пустой массив в `null`.

### P1 — мутации DM не повторяют проверку доступа к разговору

**Код:** `apps/web/src/app/api/dm/[id]/route.ts:332–413`.

GET/POST используют `openConversation`, а PATCH/DELETE — только авторство сообщения и совпадение `conversationId`. Они также не вызывают `checkBan`; PATCH не учитывает business lock/изменение роли сотрудника. Пользователь с сохранённой сессией может менять старые сообщения после изменения статуса доступа, а событие будет разослано текущей аудитории бизнес-чата.

**Исправление:** вызывать `openConversation` и `checkBan` для PATCH/DELETE; определить, разрешено ли клиенту редактировать сообщения после блокировки обращения и сотруднику после потери staff-роли.

### P2 — счётчик ответов ветки не уменьшается после удаления

POST ответа увеличивает `threadCount`, но DELETE сообщения выполняет hard delete без decrement родителя (`messages/route.ts:613–614`). UI может показывать несуществующие ответы/неверное число.

**Исправление:** транзакция удаления + decrement родителя с нижней границей 0; тест удаления thread reply.

### P2 — удаление DM очищает текст, но не вложения

`dm/[id]/route.ts:396–399` выставляет `deleted: true, content: ""`, однако `attachments` остаются. Если какой-либо клиент, экспорт или уведомление не скрывает вложения строго по `deleted`, удалённый файл продолжит отображаться/экспортироваться.

**Исправление:** очистить `attachments`, `replyToId` при soft delete либо гарантировать серверную фильтрацию во всех read/export endpoint.

### P2 — гонка автоответа может породить несколько автоответов

POST DM сначала читает `lastAutoReplyAt`, затем отдельно обновляет его и создаёт автоответ. Два параллельных сообщения могут оба увидеть старое значение и оба создать автоответ.

**Исправление:** условный `updateMany` по старому timestamp/транзакция/уникальный lease.

## Дополнительные проблемы календаря

### P2 — многодневные события пропадают на границе диапазона

`apps/web/src/app/api/calendar/route.ts:31–46` фильтрует только `start >= from AND start <= to`. Событие, начавшееся раньше отображаемого диапазона, но продолжающееся внутри него, не возвращается.

**Исправление:** пересечение интервалов: `start <= to AND (end >= from OR (end IS NULL AND start >= from))`, с отдельной продуктовой трактовкой событий без конца.

### P2 — GET календаря принимает невалидные даты

`new Date(from/to)` передаётся в Prisma без проверки `isNaN`, что может привести к 500 вместо 400.

### P2 — PATCH позволяет сохранить `end < start`

POST это запрещает, PATCH — нет (`calendar/[id]/route.ts:35–50`). После редактирования можно получить неконсистентное событие.

## Что сделано хорошо

- Проверка доступа к комнатам Socket.IO и WebRTC-сигналингу в основном выполнена аккуратно: события offer/answer/ICE разрешены только общим участникам voice room.
- Есть серверная проверка reply/thread принадлежности каналу.
- Санитизация обычного текста удаляет HTML и управляющие/Bidi-символы.
- Для private screen share сервер фильтрует объявления по userId и проверяет зрителя при `screen-view-start`.
- В проекте много защитных комментариев и регрессионных тестов для уже найденных проблем.

## Рекомендуемый порядок исправлений

1. **Private screen reconnect**: перенос announce после `voice-joined`, сохранение allow-list, серверный guard.
2. **DM anti-spam**: rate limit + ограничение уведомлений/push.
3. **Плашка трансляции**: drag или layout-slot, тест на перекрытие composer.
4. **Календарь**: удаление в форме месяца, read-only просмотр, тесты ролей.
5. **Авторизация мутаций сообщений/DM**: единый helper для актуального доступа.
6. **Пустые attachments, threadCount, soft-delete вложений**.
7. **Диапазоны и валидация календаря**.

## Минимальный набор регрессионных тестов

- Private/public screen share → disconnect/reconnect → late joiner.
- Плашка не перекрывает composer на desktop/mobile и переносится pointer/touch.
- OWNER/ADMIN/MODERATOR/author/member: create/edit/delete calendar event из month/list.
- Участник исключён из группы: PATCH/DELETE старого сообщения.
- DM burst: превышение лимита возвращает 429 и не создаёт push.
- `content=""`, `attachments=[]` возвращает 400 для channel и DM.
- Удаление thread reply корректно уменьшает count.
- Многодневное событие пересекает границу месяца.
