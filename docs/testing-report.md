## Найденные ошибки — все четыре исправлены

Первым заходом ошибки не чинились: правки в криптографии и модели безопасности
не должны быть побочным продуктом написания тестов. Отдельным заходом все четыре
исправлены, а выключенные тесты включены. **Пропущенных тестов в наборе больше
нет.**

### 1. `buildWireGuardConfig` не проверял ключи (`lib/wgKeys.ts`)

Функция принимала `privateKey` и `serverPublicKey` как произвольные строки и
подставляла в текст конфигурации без проверки — ни длины (у base64-ключа
WireGuard это ровно 44 символа), ни того, что это вообще base64. Мусор проходил
молча, а профиль отвергал уже сам клиент WireGuard при импорте: ошибка вылезала
далеко от места, где возникла, и без указания на испорченное поле.

Добавлена проверка по образцу `^[A-Za-z0-9+/]{43}=$` с сообщением, называющим
поле. В сообщение попадает длина, но **не само значение**: сюда приходит и
приватный ключ, а текст ошибки имеет привычку оказываться в журналах. Отдельный
тест следит именно за этим.

Единственный вызывающий код — `PremiumInfoModal` — уже обёрнут в `try/catch` со
`setError`, так что исключение превращается в сообщение, а не в падение окна.
Формулировка там общая («не удалось создать ключ на этом устройстве») и для
случая испорченного ключа узла неточна — стоит уточнить, когда до этого окна
дойдут руки.

### 2. `headerValue` терял заголовок при смешанном регистре (`lib/identity.ts`)

Было `rec[name] ?? rec[name.toLowerCase()]`: прямое попадание и нижний регистр,
но не наоборот. Словарь с ключом `"X-User-Id"` при запросе `"x-user-id"` давал
`null`.

В бою это не стреляло — у `Headers` работает ветка `.get()` выше по коду, а Node
сам приводит имена входящих заголовков к нижнему регистру, — но в модуле
блокировок такую ловушку держать не стоит. Добавлен перебор ключей с
нормализацией: имена заголовков регистр не различают (RFC 9110 §5.1), а простой
объект различает. Обычные случаи решаются прежними двумя обращениями, перебор
включается только когда их не хватило.

### 3. Значок «CRM» не выбирался для «CRM-система» (`components/connect/BlockIcons.tsx`)

Список `KEYWORDS` обходится сверху вниз до первого совпадения, а запись
`systems` с ключевым словом «систем» стояла раньше `crm`. Строка «CRM-система»
совпадала с «систем» и получала значок «Системы». Запись `crm` поднята выше;
значимость порядка объяснена комментарием прямо над списком, чтобы следующая
запись не легла снова не туда.

### 4. Ключевое слово «облач» не покрывало слово «облако» (там же)

Совпадение ищется подстрокой, а `"облако".includes("облач")` — ложь: корень в
этих формах разный. Раздел с названием «Облако» оставался без значка вовсе. Ключ
укорочен до общей части «облак».

Рисунки значков не менялись — правка только в сопоставлении названия с ключом.

## Чего в наборе нет

- **Интеграционных тестов с реальной базой.** Всё на глубоком моке Prisma.
  Логику прав это проверяет полностью, а вот опечатку в `include`/`select`
  или неверную связь в схеме — нет. Как поднять `trioz_test`, описано в
  `docs/testing-setup.md`; это следующий заметный шаг.
- **Тестов на `lib/vpn.ts`** (319 строк, 0 %) — зона примыкает к криптографии,
  её решили не смешивать с зоной A в одном заходе.
- **Тестов на `lib/encryption.ts` и `lib/auth.ts`** — по условию задачи их
  трогать было нельзя, только импортировать.
- **Компонентов целиком.** `MessageArea.tsx` (2600 строк), `VoiceContext.tsx`
  (3300) и подобные тестами не покрыты: без разделения на части их можно
  проверять только полным рендером с сокетом, а такой тест дороже пользы.

Особенность первого файла: тест прогоняет через `resolveAttachment()` КАЖДОЕ расширение из
`CHAT_ATTACHMENT_ACCEPT`. Именно расхождение клиентского списка с серверным давало самый
обидный из исходных симптомов: файл можно выбрать, но нельзя отправить. Теперь такое
расхождение падает тестом, а не обнаруживается жалобой.

## Почему прогон не снят

Зависимости в среде, где готовилась эта правка, установить не удалось: реестр npm
отвечает на `ping`, но загрузка пакетов падает на ENOTFOUND, и установка завершается
ошибкой `npm error Exit handler never called!`:

```
http fetch GET https://registry.npmjs.org/@vitest/utils/-/utils-3.2.7.tgz attempt 1 failed with ENOTFOUND
npm error Exit handler never called!
```

Поэтому `vitest`, `eslint` и `build:shared` не запускались ни до правок, ни после них.
Называть набор зелёным на основании чтения кода было бы нечестно — цифры в таблице выше
относятся к предыдущему прогону и новых файлов не включают.

На машине с сетью достаточно обычного:

```bash
npm install
npm --workspace apps/web exec prisma generate
npm test
npm run lint
npm run build:shared
```
