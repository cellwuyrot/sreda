# Единые услуги Business ↔ TZ ID — обновление 1.4.0

## Что изменилось и какие процессы затронуты

- **sreda-main**: единый каталог услуг и назначений администраторов, серверное API интеграции, реальные права Premium/VPN, контроль окончания срока. Обновляются **PM2 trioz и tz-id**: изменены также scopes провайдера и портал TZ ID.
- **tzbiz-main 1.4.0**: оформление услуг и оплата, подписки 1/3/6/12 месяцев, T-Банк Init/Charge/GetState, отдельное согласие на автопродление, отмена будущих списаний, очередь синхронизации и писем. Процесс **PM2 tzbiz**.
- Главный источник услуг/ролей — БД TrioZ/TZ ID; Business хранит финансовые договоры и замороженные условия. Пароли, глобальные роли и секреты между аккаунтами не копируются.
- Эта поставка включает предыдущие исправления изображений/сессий. Старые инструкции и отчёты оставлены как история; текущие — этот файл, TEST-REPORT-SERVICES.md и SERVICES-CHANGED-FILES.txt.

**По умолчанию новые покупки и автосписания выключены.** Никакая миграция не включает оплату, не создаёт пробные списания и не меняет старые заказы. Реальный банк, SMTP и ваш PostgreSQL из среды разработки не проверялись.

## Перед обновлением

1. Внесите исходники из каждого архива в соответствующий существующий Git-репозиторий, сделайте commit/push. Не распаковывайте Business поверх TrioZ. Сохраните предыдущие commits и рабочие сборки.
2. Проверьте фактический cwd командой `/usr/bin/pm2 show trioz`, затем `show tz-id` и `show tzbiz`. Ниже предполагаются `/var/www/trioz` и `/var/www/tzbiz`.
3. Сохраните рабочие .env, ключи TZ ID, uploads и резервные копии **обеих БД** по своей штатной процедуре. Не публикуйте .env в Git и чат. Проверяйте успех каждого шага; при ошибке остановитесь.
4. Для известной БД Business под root: `umask 077; runuser -u postgres -- pg_dump -Fc tzbiz_business > /root/tzbiz-before-services.dump`. Для БД TrioZ используйте её фактическое имя. Не угадывайте имя и не выводите DATABASE_URL/пароли в чат. Проверьте наличие непустого дампа и возможность восстановления отдельно.
5. Используем уже установленный `/opt/tzbiz-node22/current/bin/node` (>=22.12). Системный Node и остальные приложения не меняем. Не используйте `pm2 restart all`, `pm2 update`, `pm2 kill`, `db:setup`, `db:seed`, `migrate reset`, `git clean` или `git reset --hard`.

## 1. Основной проект — TrioZ и TZ ID

После git push, выполняйте блоки по порядку. Каждый блок объединён через `&&`: ошибка останавливает последующие команды этого блока.

```bash
cd /var/www/trioz &&
export PATH="/opt/tzbiz-node22/current/bin:$PATH" &&
hash -r &&
node -v &&
git pull --ff-only &&
npm ci --ignore-scripts &&
npm exec -w apps/web -- prisma generate &&
npm run test -w apps/web -- --maxWorkers=2 &&
npm run test -w apps/id &&
npm run typecheck -w apps/web &&
npm run check -w apps/id &&
npm run build
```

После резервирования БД примените добавочную миграцию основной платформы:

```bash
cd /var/www/trioz &&
export PATH="/opt/tzbiz-node22/current/bin:$PATH" &&
npm exec -w apps/web -- prisma migrate deploy
```

Ожидаемая новая миграция: `20261029000000_managed_services` — четыре новые таблицы. `migrate deploy` применяет также все более ранние неприменённые миграции; сначала проверьте штатную историю миграций, если репозиторий отстаёт. Не правьте и не помечайте старые миграции выполненными наугад.

В рабочем окружении **web-процесса TrioZ** добавьте ровно одну переменную:

```dotenv
SERVICE_HUB_ENABLED=1
```

Существующие `DATABASE_URL`, `TZ_ID_STORAGE_KEY`, подпись JWT, cookie keys и JWKS сохраняются. Ключ шифрования не ротировать: им зашифрованы клиенты и авторизации. Провайдер tz-id продолжает использовать ту же БД, что и TrioZ; отдельной новой БД не нужно.

Только после успешной сборки и миграции:

```bash
SERVICE_HUB_ENABLED=1 /usr/bin/pm2 restart trioz --update-env &&
/usr/bin/pm2 restart tz-id --update-env &&
/usr/bin/pm2 save
```

Интерпретаторы и пути существующих процессов не переопределяются. Если PM2 сообщает о неподдерживаемом Node, проверьте сохранённый interpreter каждого процесса до его изменения; не заменяйте весь PM2-daemon. После запуска проверьте `pm2 logs trioz --lines 60 --nostream` и аналогично `tz-id`. В логах не должно быть ошибок отсутствия новых таблиц.

## 2. Разрешить интеграцию существующему Business

Основная админка → **TZ ID → существующее приложение Business → Настроить**:

- Сохраните Client ID, секрет, тип серверного клиента и действующие callback-адреса.
- Сохраните **Проверять права администратора своего проекта** (`roles:read`) и **Продлевать вход без повторной авторизации**.
- Включите **Общий каталог услуг и администраторы своего проекта** (`services:manage`) и **Выдавать оплаченный доступ к услугам своего проекта** (`services:fulfill`). Подписи пунктов могут содержать пояснения; технические scope-имена приведены для однозначности.
- Сохраните. Не создавайте второй клиент вместо существующего.

Вкладка «Услуги и администраторы проектов» → выберите именно это приложение Business. Назначайте человека по точному TZ ID, а не по совпадению email. Назначение даёт права только в выбранном проекте, не глобальную роль владельца TrioZ. Отзыв применяется при следующей проверке Business; активная админская операция дополнительно проверяется центральным сервером. Для собственной админки TZ ID глобальный владелец сохраняет доступ, но в Business он тоже должен иметь явное проектное назначение.

## 4. Обязательная фоновая задача — каждую минуту

Синхронизация оплаченного доступа, письма, сверка банка и продления выполняются `npm run jobs:run`. Одна только команда PM2 restart не запускает их по расписанию.

Сначала проверьте существующий `crontab -l`. **Замените** прежнюю строку Business `jobs:run`, если она уже есть, вместо создания второй независимой задачи. Пример строки crontab:

```cron
* * * * * cd /var/www/tzbiz && PATH=/opt/tzbiz-node22/current/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin NODE_ENV=production /opt/tzbiz-node22/current/bin/node node_modules/tsx/dist/cli.mjs scripts/jobs.ts >> /var/log/tzbiz-jobs.log 2>&1
```

У cron должны быть доступ к БД и рабочему .env. Не кладите пароли в crontab. Первый диагностический запуск после миграции, пока покупки выключены:

```bash
cd /var/www/tzbiz &&
export PATH="/opt/tzbiz-node22/current/bin:$PATH" &&
npm run services:check &&
npm run jobs:run
```

`services:check` не отправляет Init, Charge или письма: проверяет конфигурацию, каталог и очереди. `jobs:run` исполняет уже накопленные задачи и после включения рекуррентов способен отправлять реальные списания — это не команда тестового платежа. Основная платформа отдельно закрывает истёкшие managed-права каждую минуту. Для VPN узел применяет список разрешённых пиров при очередной штатной синхронизации, не мгновенно в момент клика.

## 5. Заполнение каталога

1. Создайте услугу в любом из двух кабинетов. Объект появится в обоих: это одна запись, не копии с конфликтующими ценами.
2. Введите цену **за весь период** в рублях отдельно для 1/3/6/12 месяцев. Пустое поле убирает вариант. Например, цена за 3 месяца — не цена одного месяца.
3. Разрешите нужные способы: разовая оплата периода, рекуррентное продление, счёт со сверкой. Обычная разовая оплата не сохраняет согласие на будущие списания.
4. Автоматическое право **Premium** или **Надёжное соединение (VPN)** назначает глобальный владелец TrioZ в основном кабинете. Это защита от выпуска глобального Premium произвольным администратором проекта. Услуга, созданная в Business, изначально ручная. После появления подключений менять тип исполнения нельзя — создайте новую услугу.
5. Для хостинга без API исполнение ручное. После оплаты возникает задача подключить; после завершения срока — отключить. Отмечайте «выполнено» только после реального действия. Система не выключает произвольный VPS без подключённого адаптера.
6. «Досрочно запросить отключение» настраивается для услуги. Отмена **будущих списаний** доступна всегда и сохраняет оплаченный период. Досрочное отключение и возврат денег — разные действия; автоматический возврат этим релизом не добавлен.
7. Публикация разрешает новые оформления. Скрытие услуги останавливает новые подключения/будущие продления, но не отбирает уже оплаченный доступ. Новые цены не меняют старый финансовый договор.
8. На одного пользователя и одну услугу разрешено одно текущее/неразобранное подключение. Неопределённый банковский платёж блокирует повторное оформление до сверки.

## 6. Включение оплат — только после подтверждений

Не включайте рекурренты на предположении, что они разрешены. Нужны подтверждение **конкретного терминала** банком, тестовые сценарии банка, рабочая касса, согласованные документы и уведомления. T-Pay — способ оплаты, а не замена кассы. Фискальный email покупателя берётся из его аккаунта; `union@business.trioz.ru` — отправитель информационных писем. Отправителя фискальных чеков и работу кассы настраивают отдельно у банка/оператора.

В существующих настройках эквайринга нужны `TBANK_ENABLED=true`, TerminalKey/пароль, HTTPS-адрес, `TBANK_RECEIPT_MODE=bank`, реальные `TBANK_TAXATION` и `TBANK_TAX`. Не копируйте выдуманный НДС или налоговый режим из примера. Код отправляет Receipt с признаком **предоплаты**; закрывающий чек после оказания услуги, чек возврата, маркировку и особенности периодических услуг необходимо отдельно проверить/настроить с банком и бухгалтерией. Этот релиз не подтверждает наличие действующей ККТ и не реализует самостоятельный сервис закрывающих чеков.

После проверки продавца и опубликованных версий документов в админке можно включить **сначала разовую оплату**:

```dotenv
SUBSCRIPTIONS_ENABLED=1
SUBSCRIPTION_TERMS_APPROVED=1
TBANK_RECURRENT_ENABLED=0
TBANK_RECURRENT_BANK_APPROVED=0
```

Обновите те же значения в сохранённом окружении только процесса tzbiz:

```bash
SUBSCRIPTIONS_ENABLED=1 SUBSCRIPTION_TERMS_APPROVED=1 TBANK_RECURRENT_ENABLED=0 TBANK_RECURRENT_BANK_APPROVED=0 /usr/bin/pm2 restart tzbiz --update-env && /usr/bin/pm2 save
```

Лишь после письменного подтверждения банка и проверки всех чеков измените в .env оба рекуррентных флага на `1`, затем:

```bash
TBANK_RECURRENT_ENABLED=1 TBANK_RECURRENT_BANK_APPROVED=1 /usr/bin/pm2 restart tzbiz --update-env && /usr/bin/pm2 save
```

Это **боевое включение**, а не безопасный тест. Cron начнёт обрабатывать наступившие продления. Каждый клиент отдельно подтверждает сумму, период и отмену; прежние заказы/разовые платежи в автосписания не превращаются. Перед изменением текста согласия задавайте новую `SUBSCRIPTION_CONSENT_VERSION`; действующие записи сохраняют своё согласие и цену.

Отключение рекуррентов: верните оба флага на `0` в .env и в префиксе команды restart tzbiz. Это запрещает **новые** отправки Charge, но не отменяет уже принятый банком платёж. Сверка, обработка подписанного callback и завершение оплаченного срока должны продолжать работать.

## 7. Проверочный сценарий после развёртывания

На отдельном тестовом пользователе, без выдачи глобальной роли:

- Создать скрытую услугу в Business → увидеть её в TZ ID → изменить там → увидеть изменение в Business. Проверить конфликт сохранения двух открытых редакторов.
- Выдать проектную роль по точному TZ ID → войти в Business → проверить админку; отозвать → убедиться в закрытии прав. Не лишайте себя последнего администратора. Права другого проекта не должны открывать Business.
- В тестовом режиме терминала банка пройти первую оплату и подписанный callback. Адрес уведомлений у новых платежей: `https://business.trioz.ru/api/subscriptions/bank/notify`; старые платежи используют прежний callback. Не переписывайте один на другой в nginx.
- Права выдаются по подтверждённому `CONFIRMED`, а не по возврату браузера на SuccessURL. Запустить штатный worker, проверить оплаченный срок, TZ ID, Premium/VPN и письмо. Для ручного хостинга проверить задачу и письмо после подтверждения выполнения.
- До разрешённых рекуррентов протестировать разовый период. После разрешения банка — отдельно первый рекуррентный платёж, RebillId, последующий Charge, чек, отказ, отмену и конец доступа. Не сокращайте боевые периоды SQL-правками ради теста; используйте стенд и сценарии банка.
- Продление выполняется в течение часа после наступления срока. Если безопасное окно пропущено, услуга скрыта, нет RebillId или банк отказал — автооплата останавливается, повторных автоматических попыток нет. Доступ не продлевается без подтверждения.
- При потерянном ответе Init/Charge система **не повторяет** денежный запрос. В админке Business → контроль оплат найдите OrderId, возьмите PaymentId из кабинета Т-Банка и выполните «Проверить существующий платёж». Кнопка вызывает только GetState и сверяет заказ, терминал, сумму. Если банк не создавал платёж, ручное расследование с банком/разработчиком необходимо: нельзя произвольно выдавать доступ или очищать блокировку SQL-командой.
- Письма с неоднозначной SMTP-доставкой помечаются UNKNOWN: автоматической бесконечной рассылки нет. Контролируйте счётчик и SMTP-журнал. Повторная отправка после выяснения судьбы письма — отдельное действие оператора, не новое списание.

Локальные тесты в архивах проверяют код и изолированную SQLite-схему Business. Боевой PostgreSQL, VPN-узел, фактическая доставка почты, банковский терминал и чеки проверяются этим сценарием на вашем стенде.

## 8. Откат

Сначала выключите покупки/автосписания в .env **и окружении PM2 tzbiz**, сохранив сверку незавершённых платежей. Снимите свежую резервную копию: после обновления могли появиться новые оплаты. Не откатывайте только код и не теряйте callback новых платежей. Новые таблицы не удаляйте, старые данные не восстанавливайте поверх новых оплат. При необходимости возвращайте предыдущие commits/сборки по отдельному согласованному плану, сохраняя новый обработчик сверки до окончательного урегулирования операций.
