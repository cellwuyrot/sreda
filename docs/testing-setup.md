# Тесты: как устроено и как запускать

До этой правки в проекте не было ни одного теста при ~95 000 строк TS/TSX.
Здесь описана оснастка: что установлено, как гонять и как писать новые тесты,
чтобы они не разъезжались по стилю.

## Коротко

```bash
cd apps/web
npm run test           # один прогон
npm run test:watch     # следить за изменениями
npm run test:coverage   # прогон с покрытием: text в консоль, html в apps/web/coverage
```

Из корня монорепы то же самое — `npm run test -w apps/web`.

## Почему Vitest, а не Jest

Проект на ESM и TypeScript: `dev` и `start` идут через `tsx`, сборка — Next с
esbuild/SWC. Vitest использует тот же esbuild, поэтому не нужен ни `ts-jest`,
ни babel-конфиг, ни отдельный слой транспиляции под ESM. Настройка сводится к
одному файлу `vitest.config.ts`, а не к связке `jest.config` + `transform` +
`moduleNameMapper`.

## Что установлено

Дев-зависимости в `apps/web`:

| Пакет | Зачем |
|---|---|
| `vitest` | сам прогон |
| `@vitest/coverage-v8` | покрытие через V8, без инструментирования кода |
| `vitest-mock-extended` | `mockDeep<PrismaClient>()` — типизированная заглушка Prisma |
| `@testing-library/react` | рендер компонентов |
| `@testing-library/jest-dom` | матчеры вроде `toBeInTheDocument` |
| `jsdom` | DOM для компонентных тестов |

## Конфигурация

`apps/web/vitest.config.ts` заводит **два проекта в одном прогоне**:

- **`node`** — `src/lib/**`, `src/app/api/**`, `src/test/**`. Серверный код,
  DOM не нужен.
- **`jsdom`** — `src/components/**`, с `src/test/setupDom.ts` (подключает
  матчеры jest-dom).

Алиас `@/` → `src/` повторяет `paths` из `tsconfig.json`, поэтому импорты в
тестах пишутся так же, как в коде.

Покрытие считается только по `src/lib/**` и `src/app/api/**`. Считать его по
всему `src/` бессмысленно: две сотни экранов без тестов размоют цифру, и она
перестанет что-либо значить.

## База данных в тестах

**Юнит-тестам база не нужна.** `@/lib/prisma` подменяется глубоким моком:

```ts
import { prismaMock } from "@/test/prismaMock";
vi.mock("@/lib/prisma", () => ({ default: prismaMock }));

// тестируемый модуль импортируется ПОСЛЕ подмены
const { getChannelPermissions } = await import("@/lib/connectPermissions");
```

Важная тонкость: подменять надо **тот путь, который написан в самом модуле**.
`connectPermissions.ts` берёт `@/lib/prisma`, а `identity.ts` — `./prisma`;
это два разных ключа для `vi.mock`.

Проверяется логика прав и переходов состояний, а не умение PostgreSQL делать
JOIN. Реальная база сделала бы прогон медленным и хрупким — он падал бы от
чужой миграции, а не от ошибки в коде.

### Когда база всё-таки нужна

Для интеграционных проверок прав, где важны именно связи таблиц
(`groupModeration`, `uploadAccess` со сложными цепочками канал → сообщество →
роль). Поднимается **отдельной базой**, не той, что используется в разработке:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d postgres

docker compose exec postgres psql -U trioz -c "CREATE DATABASE trioz_test;"

DATABASE_URL="postgresql://trioz:ПАРОЛЬ@localhost:5432/trioz_test" \
  npx prisma migrate deploy

DATABASE_URL="postgresql://trioz:ПАРОЛЬ@localhost:5432/trioz_test" \
  npm run test
```

`prisma/schema.prisma` при этом **не трогается**: тестовая база получает те же
миграции, что и рабочая. Отдельная схема нужна ровно для того, чтобы тест мог
чистить таблицы, не задев рабочие данные.

## Как писать тесты

- Файл кладётся рядом с кодом: `src/lib/foo.ts` → `src/lib/foo.test.ts`.
- Названия тестов — по-русски, как и остальной проект: не «returns 429», а
  «отдаёт 429 на запрос сверх лимита».
- Тест описывает **договор**, а не реализацию. Если тест ломается при
  переименовании внутренней переменной — он проверял не то.
- `.skip` допустим, но только с причиной в комментарии. Красный CI хуже
  честного пропуска.

## Ограничения оснастки

- Компонентные тесты не поднимают сокет-соединение и не рендерят экраны
  целиком: тестируются выделенные функции и хуки, а не `MessageArea.tsx`
  на 2600 строк разом.
- Покрытие V8 считает строки, а не смысл. 80% в файле не означает, что
  граничные случаи разобраны.
