# TrioZ Android — отчёт и план запуска

## Вывод аудита

**Полностью нативная Android-версия пока не готова к запуску.** В исходниках два разных клиента: рабочая по назначению WebView-оболочка в `app/src/main` (её фактическая работа на сервере в этом аудите не подтверждена) и изолированное Compose-превью в `app/src/debug`. Релизный launcher запускает WebView. Сборка APK сама по себе не завершает перенос.

Этот отчёт подготовлен по архиву `trioz-android-builds-partial.zip`. Доступа к работающему серверу, действующему ключу подписи и физическому Android-устройству нет. Развёртывание и изменение production не выполняются.

| Профиль/дизайн | 5 приблизительных палитр и имя | Реальные темы/права Premium, фон и оформление сообществ/чатов, настройки, доступность, размеры шрифта, локализация и ошибки |

### Особенно важные риски

1. Нельзя удалять приложение, очищать WebView/IndexedDB, менять signing key либо включать нативный launcher до проверки миграции. Это угрожает доступу к переписке.
2. `FCM_PRIVATE_KEY` — серверный секрет, не часть APK. `google-services.json` — клиентская конфигурация Firebase, это другой файл. Пароли/ключи не передавать в чат, Git, логи и публичный каталог артефактов.
3. В API списков есть ветки, возвращающие `[]` с 200 при ошибке. Это нельзя выдавать за подтверждение пустой учётной записи.
4. POST сообщений канала пока не имеет idempotency key. При timeout после фактической записи автоматический retry способен создать дубликат; нужна явная обработка неопределённого результата.
5. Параллельная публикация/отсутствие AAB после успешного APK способны оставить разные версии публичных файлов. Одного атомарного rename APK недостаточно для транзакции набора.

## План реализации с критериями выхода

### Этап 1 — тестовый нативный вертикальный срез и надёжность сборки (этот проход)

- Сделать настоящую Android-компиляцию и запустить доступные unit/Robolectric-тесты.
- Улучшить debug-сетевой слой: отмена запросов, origin allowlist, запрет redirect и автоматических повторов записи, тестовый transport без production-запросов.
- Реализовать историю каналов и открытых ЛС, отправку обычного текста **только в каналы**, видимые ошибки и сохранение текста при ошибке; оставить E2EE/ЛС read-only.
- Добавить выход из тестовой сессии без изменения старого клиента; не хранить пароль/сессию на диске.
- Защитить сборщик от отсутствующего/пустого артефакта и одновременных запусков; добавить негативные тесты.
- Критерий: компиляция + автоматические проверки; это внутренний тест, не запуск полной версии.

### Этап 2 — архитектура и безопасная миграция (блокирует нативный release)

- Зафиксировать полную матрицу Connect/admin: сценарий → API → права → нативный экран → тест.
- Спроектировать и проверить E2EE на данных тестового пользователя, включая неизвлекаемые старые ключи. Обратная совместимость и откат не должны зависеть от переустановки.
- Разделить domain/data/UI; устойчивый lifecycle/state, шифрованное локальное хранилище, безопасная сессия, правильная стратегия резервного копирования и удаления данных.
- Критерий: после обновления тестового release доступна старая история, нет подмены ключей, откат не уничтожает данные.

### Этап 3 — мессенджер и аккаунт

- Полный вход и профиль, группы/правила/права, друзья, обычные/защищённые/деловые ЛС, файлы и операции над сообщениями.
- Совместимый realtime: доставка, порядок, дедупликация, reconnect/backfill, unread/read/privacy. Идемпотентная запись и тесты разрыва сети.
- Критерий: два устройства и веб-клиент обмениваются всеми поддерживаемыми типами сообщений, права и шифрование совпадают.

### Этап 4 — звонки, push и VPN

- Личные и групповые media-сценарии с реальным сервером и TURN, доступность на заблокированном экране, отказ разрешений и смена аудиоустройства/сети.
- Push с рабочим Firebase, logout/revocation, cold start/deep links и защита содержимого уведомлений.
- Нативное управление существующим VPN только из настроек профиля, защита ключа и проверка маршрутов на телефоне.
- Критерий: проверенные звонки в foreground/background, восстановление соединения и отсутствие утечек VPN в согласованных режимах.

### Этап 5 — админка и выпуск

- Полные согласованные админские сценарии; сервер остаётся источником прав. Внешний вид Android и десктопа по текущим темам проекта.
- Реальные формы сборки: package/version/origin/канал, Firebase client config, signing config; секреты отдельно от обычных параметров. RBAC, CSRF, шифрование, TLS, выдача привязанному агенту/задаче, ротация, отсутствие утечек в логах, очистка и аудит.
- FCM server config — только backend; согласованная инвалидация token cache при ротации. Keystore для обновления — прежний, не новый.
- Проверка подписи/версии/хэшей, staging артефактов, контролируемое продвижение и откат. Запуск сборки и публикация не должны быть неразличимым действием.
- Критерий: администратор выпускает проверенный signed APK с понятной диагностикой, пользователь обновляется без потери данных.

### Этап 6 — приёмка и запуск

- Device matrix: Android 8/12/13/14/15/16 по поддерживаемым устройствам; минимум физические устройства для звонков/VPN/push; эмулятор их не заменяет.
- Два аккаунта (обычный и администратор), два устройства, staging HTTPS, тестовая Firebase-конфигурация, TURN и VPN-узел; отказ сервера/сети, process death, Doze, разрешения, доступность.
- Пентест критических границ, подтверждение сохранности данных, подписанный release candidate, ограниченный пилот, метрики сбоев, после него публичный запуск.

## Что потребуется от владельца на интеграционном этапе

- Доступ к staging и агенту сборки, отдельные тестовые аккаунты; подтверждение реального production package ID/versionCode/сертификата подписи.
- Ключ подписи через защищённый канал/хранилище агента, не через чат; выбранный канал распространения (сайт/Play).
- Тестовый Firebase-проект, рабочие signaling/TURN/VPN endpoints, два Android-устройства.
- Согласование протокола E2EE-миграции и объёма админки. До этого этапа production не меняется.

Оценку сроков/готовности в процентах по числу файлов давать некорректно: ключевые блокеры — совместимость E2EE, lifecycle звонков и испытания обновления. Итог фактически выполненного прохода и точные команды проверок будут в `RESULTS.md` рядом с этим отчётом.
