# TrustTunnel 1.2 — подписчики, глобальный выбор и выпуск клиентов

Этот документ описывает текущий исходный код TrioZ и порядок его безопасного переноса. Владелец подтвердил, что межсерверная связь и функциональные тесты технологии уже пройдены. Это подтверждение владельца, а не повторная проверка со стороны сборщика архива: реальные серверы, Endpoint 1.1.0, turn и их фактические версии здесь не опрашивались. Android/Windows release и реальные клиентские устройства также не запускались в этой среде.

## Что реализовано

- Единая настройка `VpnSettings.activeProvider` выбирает **одну технологию для всех пользователей проекта**: `AMNEZIAWG` или `TRUSTTUNNEL`. Значение по умолчанию — AmneziaWG. Пользователь не выбирает технологию сам.
- Раздел `/admin/vpn` позволяет менять технологию только проектному `ADMIN`. Администратор группы не получает эти права. API требует same-origin, подтверждения выбора и отдельного подтверждения воздействия, использует serializable transaction + compare-and-set и аудит.
- На переход в TrustTunnel требуется `TRIOZ_TT_ENABLED=true` и корректная конфигурация серверных ключей/адреса. Это локальная проверка формата, а не live health probe. Gateway/Endpoint ACK виден отдельно в состоянии подписчика; он подтверждает применение учётных данных Endpoint, но не проверяет доступность каждого сайта.
- Выдача TrustTunnel использует свежую запись пользователя и доступ Premium, активную подписку «Надёжное соединение» или проектный `ADMIN`. Group admin сам по себе не получает доступ. При отзыве/истечении/блокировке запись исчезает из следующего успешного снимка.
- Endpoint pull-agent получает полный зашифрованный снимок. При выборе AmneziaWG, выключенном feature flag **или выключенном общем `VpnSettings.enabled`** список управляемых TrustTunnel-учётных записей становится пустым. Ошибка БД возвращает 503, а не пустой снимок. Изменение `credentials.toml` может перезапустить Endpoint и разорвать как управляемые, так и другие существующие сессии — выполнять такие действия только в согласованное окно.
- Существующий выключатель сервиса на `/admin/vpn` действует для обеих технологий: `enabled=false` запрещает выдачу TrustTunnel и приводит к пустому endpoint snapshot; повторное включение восстанавливает управление по действующим правам. При выключении TrustTunnel UI подтверждает возможное прерывание сессий и рестарт Endpoint.
- Windows: отдельный TrustTunnel Client 1.1.12, служба `TrioZTrustTunnel`, UAC и проверка SHA-256 поставляемых бинарников. Ресурсы Windows-клиента подхватываются vendor-скриптом сборки, но в этом ZIP бинарники клиента не вложены. Работа службы в Windows SCM не доказывает прохождение пользовательского трафика.
- Android: TrustTunnel SDK 1.1.12 теперь включён в source set и зависимости **debug и release**. `TrustTunnelPilotService`, bridge и запись VPN-сервиса доступны release. AAR содержит только `arm64-v8a`, поэтому все варианты Android сборки ограничены ARM64. `versionName=0.5.0`, `versionCode=4` — candidate версии исходника; перед публикацией сравнить с максимальным фактически опубликованным versionCode.
- Профили и пароли не показываются в окне подключения; web передаёт профиль непосредственно нативному мосту. Права доступа вычисляются сервером. Окно TrustTunnel фиолетовое, адаптивное, не содержит скачивания профиля и технических ключей, имеет клавиатурное закрытие и управление фокусом.
- Учёт трафика, лимиты и квоты TrustTunnel **не реализованы**. Счётчики AmneziaWG не являются данными TrustTunnel. Kill switch и защита от утечек после обрыва не подтверждены на реальных устройствах.

## Известные ограничения Discord и пинга

Подтверждённая причина пока не установлена. Успешный прямой запрос с VDS и успешный HTTP/1.1 proxy через gateway не доказывают исправность маршрута Windows TUN → TrustTunnel Client → HTTP/2 → gateway → Endpoint. Наблюдение ответа `HTTP/1.1 400` относится к одному сетевому потоку, связь с конкретным запросом Windows не доказана; происхождение необычного начала потока также не подтверждено. MTU 1200 проблему не решил; возвращённое значение 1350 не является доказательством оптимального MTU. Для высокого пинга нет численных замеров RTT/loss/jitter и отдельной UDP/голосовой диагностики. Не заявлять, что это исправлено переключением провайдера.

## До развёртывания

1. Сделать резервные копии БД, web env, endpoint `credentials.toml`, конфигурации endpoint pull-agent и gateway. Не класть env, ключи, токены, приватные профили и keystore в Git, лог или ZIP.
2. ZIP содержит исходники и SDK AAR, но не содержит Git history, production env, локальных зависимостей, Android keystore, Firebase `google-services.json` и Windows vendor executables. Пользовательский `apps/desktop/build/Makefile` сохранён.
3. Проверить, что фактические `turn.trioz.ru`, `170.168.18.20:8443`, DNS и TLS совпадают с конфигурацией клиентов и endpoint. В этом архиве доменные значения жёстко закреплены в валидаторах; смена адреса требует отдельного изменения и новой сборки клиентов.
4. На Endpoint необходимы Python 3.10+ и OpenSSL 3. Агент управляет только выделенным блоком credentials и атомарно заменяет его. Не запускать второй агент, не менять файл параллельно и заранее учитывать, что изменение credentials может перезапустить Endpoint.

## Серверное окружение

В защищённой среде всех экземпляров web задать:

```dotenv
TRIOZ_TT_ENABLED=true
TRIOZ_TT_CRED_KEY=<32 случайных байта, 64 hex>
TRIOZ_TT_SYNC_KEY=<64 hex агента; отличается от CRED_KEY>
TRIOZ_TT_SYNC_TOKEN_SHA256=<SHA-256 bearer token агента, 64 hex>
TRIOZ_TT_HOSTNAME=turn.trioz.ru
TRIOZ_TT_GATEWAY_IPV4=170.168.18.20
TRIOZ_TT_PORT=8443
NEXTAUTH_URL=<точный публичный HTTPS origin web-приложения>
```

`TRIOZ_TT_ENABLED` должен быть включён на всех web-инстансах одновременно. `CRED_KEY` и `SYNC_KEY` — разные случайные 32-байтовые ключи. Не генерировать новые значения при обычном обновлении: изменение CRED_KEY меняет производные имена/пароли всех пользователей. Хеш токена должен соответствовать bearer token, уже настроенному агенту. Реальные значения не хранить в `.env.example`.

## Обновление web и БД

```bash
npm run migrate -w apps/web
npm run build -w apps/web
```

Миграции, необходимые этой функциональности: `20261112000000_vpn_provider_control` и `20261201000000_trusttunnel_access`. В этом обновлении новых migration SQL не добавлено. Сначала проверить `prisma migrate status` и резервную копию; не использовать `migrate reset`/`db push`. Не заменять существующий production `.env`. Перезапустить web штатным способом с тем же окружением на всех экземплярах.

Если Endpoint pull-agent ещё не установлен, применить существующую инструкцию `deploy/trusttunnel/install-sync-agent.sh` и сопоставить его конфигурацию с реальными путями/службой. Установка или обновление агента — отдельное серверное действие: его не выполнять из этого архива автоматически. До первого запуска проверить, какой участок credentials будет заменён. Пустой полный снимок удалит все записи внутри управляемого блока и может перезапустить Endpoint.

## Глобальное переключение

В админке откройте «Сервисы и система → Надёжное соединение». Пока `TRIOZ_TT_ENABLED` или обязательные настройки невалидны, переключатель TrustTunnel останется заблокирован. Когда конфигурация проходит проверку, только ADMIN проекта может нажать «Переключить всех на TrustTunnel» и подтвердить влияние.

- На TrustTunnel: новые выдачи и списки пиров AmneziaWG блокируются; при следующем опросе VPN-узел получает пустой список и удаляет AWG-пиры. При текущем интервале опроса 5 секунд активные AWG-сессии отключатся примерно на следующем цикле. Это не бесшовная миграция.
- На AmneziaWG: новые TrustTunnel-профили перестают выдаваться; на следующем успешном pull Endpoint получает пустой управляемый список, применяет отзыв и может перезапустить Endpoint. Это способно оборвать активные TrustTunnel-сессии. Не делать переключение без уведомления и окна обслуживания.
- Существующий общий выключатель услуги также применяется к TrustTunnel: при `VpnSettings.enabled=false` выдача запрещена, следующий endpoint snapshot пустой; админский UI предупреждает о возможном обрыве и рестарте. Повторное включение восстанавливает разрешённые записи через следующий sync.
- При любом реальном переключении generation всех включённых `TrustTunnelAccess` записей увеличивается внутри той же DB-транзакции. Старые профили становятся недействительными, предыдущий ACK Endpoint не подтверждает новый generation. ACK обрабатываются по монотонному serial: запоздавший снимок не может перезаписать более новое успешное или неуспешное применение. После выбора TrustTunnel интерфейс ждёт свежего ACK и только затем разрешает повторную выдачу профиля.
- Старые версии клиентов не умеют автоматически переключаться. Их пользователям нужно обновить приложение и вручную переподключиться.
- Недоступность выбранной технологии не вызывает автоматический fallback. При проблеме выбранного провайдера пользователь увидит недоступность/ошибку, а не незаметный переход на другую технологию.
- Старые версии приложений, которые не знают о новой глобальной настройке, нельзя принудительно обновить API. Для них обязателен отдельный rollout обновления и ручная переподключка.

Откат: в админке выбрать AmneziaWG и подтвердить. Будьте готовы к удалению текущих TrustTunnel credentials со стороны Endpoint при следующем sync и возможному перезапуску службы. Если админка/API недоступны, восстановить предыдущую БД/код по принятой процедуре. Не выполнять ручной SQL update без резервной копии и согласованной процедуры. Записи AmneziaWG-пиров/ключей в БД не удаляются этим изменением; на узел они будут вновь выданы после выбора AmneziaWG и следующего отчёта.

## Android 0.5.0

В исходнике `apps/android/app/build.gradle.kts` выставлены `versionName=0.5.0`, `versionCode=4`, AAR TrustTunnel 1.1.12 и release bridge/service. APK/AAB здесь не собраны: в рабочем окружении архива нет Android SDK, Gradle toolchain и вашего production signing keystore. Не подписывать release временным ключом и не менять ключ уже опубликованного приложения.

На машине с JDK 17, Android SDK platform 36, build-tools 35.0.0 и существующими ключами:

```bash
cd apps/android
./gradlew testDebugUnitTest lintDebug assembleDebug
./gradlew assembleRelease bundleRelease
```

Windows: `gradlew.bat`. Release ожидает `app/keystore.properties`; использовать именно текущую совместимую подпись (или правильный Play upload key для выбранного канала). Проверьте `versionCode` в Play Console: если там уже есть значение 4 или выше, увеличить его прежде чем выпускать.

Выходные файлы:

- `app/build/outputs/apk/release/app-release.apk` — прямое обновление только при совместимой подписи.
- `app/build/outputs/bundle/release/app-release.aab` — Google Play upload; через Play signing будет отдельная подпись распространяемого APK.

AAR в архиве содержит только arm64 native library; x86/x86_64/armeabi-v7a APK не выпускаются. Перед распространением перепроверить лицензии `docs/licenses` и транзитивные зависимости. Google Play Billing для цифровой подписки не реализован, и TrustTunnel traffic accounting тоже отсутствует.

## Windows

Перед сборкой сверить `DESKTOP_VERSION` с текущим `latest.yml` и установленными версиями; он должен быть строго выше опубликованного. Vendor-скрипт `apps/desktop/scripts/vendor-trusttunnel.mjs` получает закреплённые бинарники и проверяет SHA-256. Убедиться, что `resources/trusttunnel` содержит `trusttunnel_client.exe`, `wintun.dll` и лицензии. Подпись Windows-сборки в проекте не настроена; реальная UAC/ACL/служба и обновление требуют Windows машины.

## Проверки перед публичным rollout

На отдельных тестовых Premium, VPN-only, project ADMIN и group-admin аккаунтах проверить доступ/отказ, истечение, бан, отзыв, ротацию и sync ACK. Затем проверить переключение обоих направлений, старые клиентские версии, действующие сессии, Android разрешения/фон/смену сети, Windows UAC/службу, DNS, IPv4/IPv6, реальную маршрутизацию и утечки при отключении. Отдельно снять количественные RTT/loss/jitter и UDP-voice measurements, а также повторить Discord-проверку через полный клиентский путь. Не писать, что Discord/ping исправлены, пока причина не воспроизведена и исправление не доказано.

Локальные автоматические проверки этого обновления перечислены в итоговом сообщении; их нельзя подменять заявлением о production-тестировании. Граф `.codebase-memory/graph.db.zst` сохранён как история, но старый граф не отражает эти правки — после коммита в рабочем Git выполнить штатную переиндексацию.
