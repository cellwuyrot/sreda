# TrustTunnel для подписчиков: подготовка версии 1.2.0

Это инструкция к исходникам, а не подтверждение готовности к production. Сборки Windows и Android из этого дерева, реальная работа клиента, сервера, службы Windows, сертификата и обновлений **ещё не проверены**. Не публикуйте установщик и не включайте публичный доступ до проведения проверок ниже. Этот документ актуальнее исторических файлов `TRUSTTUNNEL-*-WIP.md`.

## Что изменено

- Доступ по свежим данным аккаунта: Premium, действующая подписка «Надёжное соединение» (`vpnAccess` и `vpnAccessUntil`) или роль проектного `ADMIN`. Администратор группы сам по себе права не получает. Заблокированный или удалённый аккаунт не получает доступ. Проверка Premium опирается на существующий флаг `isPremium` и штатное обновление сроков проекта.
- Отдельные `/api/vpn/trusttunnel` и `/config`: запрос состояния, получение/обновление и отзыв собственного профиля; пароли производятся от серверного ключа, а не хранятся в БД. Отзыв, истечение, бан и выключение флага приводят к удалению управляемого пользователя при **следующем успешном** цикле агента, не мгновенно. Отзыв увеличивает поколение ключа. Старые pilot API и их отдельные учётные данные этими маршрутами не отзываются.
- Агент VDS периодически получает полный зашифрованный снимок, сохраняет неуправляемые записи в credentials.toml, атомарно обновляет управляемую часть и перезапускает Endpoint. При неудаче запуска старается восстановить файл и сервис. Ошибки сети сохраняют последнее состояние, поэтому при отсутствии связи отзыв не гарантирован. Не запускать два агента на разных хостах для одного Endpoint и не редактировать credentials параллельно с агентом.
- Windows: отдельный нативный клиент TrustTunnel 1.1.12, отдельная ручная служба `TrioZTrustTunnel`, UAC при подключении и отключении; скрипты сверяют хеши исполняемых файлов и строгий профиль. Новое подключение двух встроенных VPN одновременно блокируется. Состояние «служба подключена» не доказывает прохождение трафика. Проверка UAC, ACL и остановки службы на настоящей Windows обязательна.
- Android: только `debug`, только ARM64 (`arm64-v8a`), Android 8+. Release не включает TrustTunnel. В архиве локально собранный AAR SDK 1.1.12, не официальный подписанный бинарник; лицензии находятся в `docs/licenses` и рядом с Windows-клиентом. Условия транзитивных компонентов нужно проверить перед распространением.
- Лимиты, учёт трафика и квоты для TrustTunnel **не реализованы**. Это отдельный поток от AmneziaWG; существующий биллинг/квоты обычного VPN не следует считать действующими для него. Kill switch, защита DNS и предотвращение утечек не подтверждены на реальных устройствах; после отключения система может вернуться в обычную сеть.

## Подготовка

1. Сохраните и проверьте резервные копии основной БД, env, существующего credentials.toml, конфигураций и unit-файлов всех затрагиваемых серверов. Используйте защищённое хранение и план восстановления; не кладите секреты в Git, журналы, чат или архив. Этот ZIP не содержит Git-истории и пользовательских env.
2. Сохраните свои локальные изменения при переносе в настоящий репозиторий. Пользовательский `apps/desktop/build/Makefile` включён. Каталог `apps/desktop/resources/trusttunnel/` находится в .gitignore: если нужны эти бинарники в Git, добавляйте их явно через `git add -f` после проверки лицензий; иначе сборочный скрипт получает архив сам. Проверьте совместимость старых пилотных записей и отключите старую выдачу, если она больше не нужна; не удаляйте существующих пользователей без сверки.
3. Клиенты строго принимают только `hostname = "turn.trioz.ru"` и `170.168.18.20:8443`. Ниже env обязан совпадать с этими значениями; при изменении адреса требуется согласованно изменить оба валидатора (Android и Windows), пересобрать и перепроверить. DNS/сертификат должны соответствовать hostname и проверяться клиентом.
4. На VDS необходимы Python 3.10+ и OpenSSL 3; credentials.toml — обычный файл владельца root, например `root:trusttunnel`, 0640, каталог root и не доступен для записи группе/другим. Убедитесь, что Endpoint действительно читает этот путь и пользователь службы имеет доступ. Нужна хотя бы одна сохранённая неуправляемая учётная запись: атомарная запись специально отвергает TOML без клиентов, в том числе при пустом снимке.

## Порядок развёртывания

1. Перенесите дерево в свой Git, проверьте `git status`, примените обычный процесс обновления проекта и зависимости. В основной БД выполните `npm run migrate -w apps/web` (миграция `20261201000000_trusttunnel_access`; не `migrate reset` и не `db push`). Перед действиями на живой БД проверьте резервную копию. Соберите основной веб-проект штатной командой и проверьте ошибки. Не заменяйте существующие env.
2. Установите агент на Endpoint-хосте из этого дерева: `sudo bash deploy/trusttunnel/install-sync-agent.sh`. Установка копирует код в `/opt/trioz-tt-sync`, unit в systemd и создаёт `/etc/trioz/trusttunnel-sync.json` с правами 0600 только если его нет. Настройте в этом JSON фактический `mainUrl` (HTTPS без пути), путь credentials, имя службы, stateDir и интервалы; unit `ReadWritePaths` и `StateDirectory` должны соответствовать нестандартным путям. Скрипт при первом запуске выводит **секретный** sync key и хеш токена — не публикуйте вывод, не копируйте его в Git. Если конфиг уже есть, он не заменяется; хеш токена вычисляйте из существующего token без пробела и перевода строки в безопасной среде.
3. На веб-сервере в существующем защищённом env задайте:

```text
TRIOZ_TT_ENABLED=false
TRIOZ_TT_CRED_KEY=<независимые 32 случайных байта в 64 hex>
TRIOZ_TT_SYNC_KEY=<64 hex из конфига агента, отличается от CRED_KEY>
TRIOZ_TT_SYNC_TOKEN_SHA256=<SHA-256 токена агента в 64 hex>
TRIOZ_TT_HOSTNAME=turn.trioz.ru
TRIOZ_TT_GATEWAY_IPV4=170.168.18.20
TRIOZ_TT_PORT=8443
NEXTAUTH_URL=<точный публичный HTTPS origin основного приложения>
```

Случайный `TRIOZ_TT_CRED_KEY` создайте один раз безопасным генератором и сохраните в защищённом резервном хранилище. Все экземпляры web должны использовать одинаковые настройки. Изменение CRED_KEY меняет все управляемые имена и пароли; изменение SYNC_KEY или токена только с одной стороны остановит синхронизацию. Обновите env процесса и перезапустите web штатным способом. Не помещайте секреты в команды, историю shell или переменные клиента.
4. До запуска агента проверьте резервную копию и содержимое своего файла на совместимость с `trusttunnel_credentials.py`, учтите существующие управляемые маркеры `# BEGIN TRIOZ MANAGED CREDENTIALS v1` / `# END TRIOZ MANAGED CREDENTIALS v1`. При `TRIOZ_TT_ENABLED=false` снимок пуст: первый успешный запуск **удалит все строки внутри этого управляемого блока** и при изменении перезапустит Endpoint. Это не безобидная проверка. В окно обслуживания выполните `sudo python3 /opt/trioz-tt-sync/trusttunnel_sync_agent.py --config /etc/trioz/trusttunnel-sync.json --once`, затем проверьте состояние Endpoint и журнал без раскрытия секретов. Включите `sudo systemctl enable --now trioz-tt-sync`; проверяйте `systemctl status trioz-tt-sync` и `journalctl -u trioz-tt-sync`. Сверьте доступность системного времени и TLS.
5. После проверки агента измените флаг на `TRIOZ_TT_ENABLED=true`, обновите окружение процесса и перезапустите web. Первый запрос профиля создаёт доступ; обычно требуется до двух циклов агента (~2 минуты плюс время перезапуска и возможные задержки), чтобы применить и подтвердить состояние. Подтверждение — последний полученный ack, не проверка текущей связи; возможна задержка и устаревание. При ошибках смотрите журнал, а не секреты профилей.
6. Публичный IPv4-вход на gateway согласован владельцем, но пока не включён. После проверок защиты настройте gateway по `TRUSTTUNNEL-STAGE5-GATEWAY.md`: `TRIOZ_TT_GATEWAY_ALLOW_ANY_IPV4=true`, `TRIOZ_TT_GATEWAY_ALLOWED_IPV4` пуст, задано конкретное значение BIND и фиксированный IPv6 endpoint, порты и firewall. По умолчанию global 32, per-source 16 одновременных соединений, rate 60/мин, burst 20. Лимиты сокетов — не число пользователей и не полноценная защита от DDoS; gateway не аутентифицирует, это делает Endpoint. Проверить мониторинг, firewall и реальные ограничения в окне обслуживания.

Каждое изменение набора credentials может перезапустить Endpoint и прервать **все** действующие сессии, в том числе неуправляемые; клиенты должны переподключиться. При ошибке rollback может не удаться: немедленно проверьте сервис и защищённую резервную копию. При отключении флага агент не сможет отозвать доступ, если web или сеть недоступны. Для аварийного отзыва при необходимости оператор вручную ограничивает доступ и восстанавливает credentials по своему плану; не запускайте конкурирующие редакторы.

## Сборка и проверка пользователем

- Windows: до выпуска сравните `1.2.0` с реальным `latest.yml` и установленными версиями; номер должен быть строго больше опубликованного. В том же окне cmd задайте `set DESKTOP_VERSION=1.2.0`, затем запустите `build-desktop.bat`. Его resolver может иначе взять версию из Git. Убедитесь, что `resources/trusttunnel` содержит `trusttunnel_client.exe`, `wintun.dll` и лицензии, что сборка не сообщает ошибок, и проверьте `latest.yml`. Вендор-скрипт использует включённые проверенные файлы; при их отсутствии скачивает закреплённый официальный архив с проверкой SHA-256, либо можно указать `TRIOZ_TT_ZIP`. Не используйте `TRIOZ_TT_ALLOW_MISSING=1` для выпуска с TrustTunnel. Подписи кода нет: прежний неподписанный механизм обновления не отменён, но его источник и публикация требуют особой защиты. Не считать наличие `verifyUpdateCodeSignature` гарантией подписи без publisherName.
- Android Studio: откройте `apps/android`, синхронизируйте Gradle и соберите debug APK для ARM64; на устройство установится отдельное приложение `.debug`. Настройка `trioz.debugAppUrl` допустима только как доверенный HTTPS origin; она не меняет release. Проверьте настройки SDK/зависимости, AAR и лицензии. Release TrustTunnel не содержит.
- На отдельных тестовых аккаунтах и устройствах проверьте: отсутствие доступа обычного пользователя и группового админа, доступ Premium, отдельного VPN-плана и проектного ADMIN, истечение/бан/отзыв и ротацию, сохранность прочих клиентов, успешный ack, выключение флага и восстановление после сбоев с контролируемым прерыванием. Проверьте обе платформы: разрешения Android и UAC Windows, конфликты с AmneziaWG, повторный запуск, выход/сбой приложения, сон, переподключение и смену сети; TLS/hostname, DNS, IPv4/IPv6, LAN, реальный маршрут и утечки при обрывах. Проверьте журналы на отсутствие паролей и настоящие обновления Windows на тестовой машине. Не публикуйте до успешной проверки и согласования рисков.
