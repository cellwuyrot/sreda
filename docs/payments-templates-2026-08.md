# Платежи: шаблоны реквизитов и правка счёта без сброса подписи

Маркер в коде: `PAY-TEMPLATE`. Дата: 2026-08.

## Что было не так

1. Раздел «Админ → Платежи» был **одной формой на один набор реквизитов** (записи
   `SiteConfig`). Пока счета выставляет один человек от одного юрлица, этого хватает.
   Когда администраторов несколько, набор перестаёт быть одним — и реквизиты начинают
   дописывать в счёт руками при каждом выставлении.
2. `POST /api/admin/business` **всегда** сбрасывал подпись клиента, отметку об оплате,
   `paidCycles` и `nextDueAt`. Из-за этого счёт нельзя было отредактировать: исправление
   опечатки в описании стоило потерянной подписи и повторного ознакомления с документами.

## Что появилось

### Модель `PaymentRequisite`

Миграция `prisma/migrations/20260917000000_payment_requisites`.

- `ownerId = null` → **общий** шаблон проекта (виден всем администраторам).
- `ownerId = <userId>` → **личный** шаблон администратора (виден только владельцу).
- `isDefault` — подставляется, когда шаблон в форме счёта не выбран. Уникальность
   поддерживается в коде (`clearDefaults`), а не ограничением БД: «по умолчанию» бывает
   отдельно для личных и отдельно для общих.
- Поля реквизитов (`orgName`, `inn`, `kpp`, `bank`, `bik`, `account`, `corrAccount`,
   `purpose`), блоки СБП и эквайринга, `comment`.
- `bodyOverride` — свой текст целиком. Если заполнен, побеждает поля: агентский договор,
   НДС и ссылку на приложение в поля не уложить.
- `scope` — `BUSINESS` или `PREMIUM`.
- `usedCount` / `lastUsedAt` — видно, какой шаблон рабочий, а какой пора удалить.
- `BusinessPayment.requisiteId` — только след происхождения (`onDelete: SetNull`).
   **Условия счёта живут в снимке текста внутри самого счёта**, поэтому удаление шаблона
   не меняет уже выставленные счета.
- Лимит: `MAX_REQUISITES_PER_OWNER = 30` на владельца.

### Приоритет подстановки реквизитов

`resolveRequisites()` в `src/lib/paymentRequisites.ts`:

1. текст, введённый в форме руками;
2. выбранный шаблон;
3. шаблон по умолчанию — сначала личный администратора, затем общий;
4. общие реквизиты проекта из вкладки «Бизнес» (`SiteConfig`);
5. пусто.

Шаг 4 оставлен намеренно: счёт без реквизитов — самая частая причина того, почему клиент
«собирался, но не заплатил».

Готовый текст всегда считает **сервер** (`requisiteText`, поле `preview`). Форма показывает
ровно то, что уйдёт клиенту, а не вторую сборку того же текста в браузере.

### API

- `GET /api/admin/payment-requisites` → `{ requisites, settingsPreview, limit }`
- `POST /api/admin/payment-requisites` — создать; поддерживает `copyFromId` (дублирование)
  и `fromSettings: true` (перенос текущих реквизитов проекта в шаблон). Ограничение
  частоты: 30 запросов в минуту на администратора.
- `PATCH /api/admin/payment-requisites/[id]` — правка, переключение личный/общий,
  «сделать основным».
- `DELETE /api/admin/payment-requisites/[id]`

Все четыре — **только ADMIN**. Личный шаблон другого администратора недоступен даже
администратору: 403 «Это личный шаблон другого администратора».

Журнал действий: `payments.requisite.create` / `.update` / `.delete`.

### Правка счёта без сброса подписи

`POST /api/admin/business` сравнивает новые значения с текущими и считает
`termsChanged` по **существенным** условиям:

- сумма, валюта;
- способ выставления (разовый / подписка);
- период и число периодов;
- услуга (а значит и комплект документов).

- `termsChanged = true` → как раньше: `status = UNPAID`, `paidCycles = 0`,
  `nextDueAt` пересчитан, подпись/заявление/оплата обнулены. Уведомление «Счёт к оплате».
- `termsChanged = false` → меняются только название, описание и реквизиты.
  Подпись клиента сохраняется. Уведомление «Счёт обновлён».

Ответ содержит `termsChanged`, `signatureReset`, `requisiteSource`, `requisiteId`,
`templateId` — форма показывает честный итог.

### Интерфейс

- «Админ → Платежи» → третья вкладка **«Шаблоны счетов»**
  (`src/components/admin/PaymentRequisiteManager.tsx`): список личных и общих шаблонов,
  создание, правка, дублирование, «сделать основным», удаление, создание из реквизитов
  проекта, серверный предпросмотр текста, счётчик лимита.
- Форма выставления счёта (`AdminBusiness.tsx` → `PaymentFormModal`): выбор шаблона,
  кнопка «Подставить», флажок «Сохранить эти реквизиты как шаблон» с названием и
  переключателем личный/общий, а предупреждение о сбросе подписи теперь появляется
  только тогда, когда сброс действительно произойдёт.

## Что нужно сделать при развёртывании

```bash
cd apps/web
npx prisma migrate deploy
npx prisma generate
```

Без `prisma generate` типы `prisma.paymentRequisite` не появятся и сборка упадёт.

## Что осталось как было

- TURN-сервер, голосовой чат и медиасервер не тронуты.
- `POST /api/admin/business` остаётся доступным **только ADMIN**: редактор не выставляет
  счета и не видит платёжные данные.
- Клиентские компоненты не импортируют `@/lib/paymentRequisites` и `@/lib/paymentSettings`:
  это серверные модули, они тянут Prisma в браузерный бандл.
