# Копирование TZ ID в списке пользователей

## Что изменено
- В `/admin/users` у каждой записи появилась кнопка «TZ ID». Доступна только ADMIN; EDITOR её не видит.
- GET `/api/admin/users/[id]/tz-id` проверяет серверную сессию и роль ADMIN до запроса к БД. Возвращает только `{tzId: User.id}`; ответ не кешируется.
- В буфер попадает ровно существующий `User.id`, который используется TZ ID как OIDC `sub`, без имени, email, префиксов и пробелов. Это строковый идентификатор, не новый числовой номер.
- Предусмотрены подтверждение успеха, отказ в доступе, отсутствие пользователя и ошибка буфера обмена. Успех показывается только после успешной записи.
- Кнопка имеет доступную подпись и область нажатия не меньше 44px. Действия в карточке переносятся на узких экранах.
- Новые миграции, зависимости и изменения процесса TZ ID для этой функции не нужны. Предыдущие изменения интеграции и удаления CloudPayments сохранены.

## Граница ограничения доступа
Именно новая кнопка и новый endpoint доступны только ADMIN. Существующие API уже используют `User.id` для адресации пользователей, в том числе в редакторской панели. Этот выпуск не превращает технический идентификатор в секрет и не обещает скрыть его во всех прежних API. Для полного сокрытия потребовалась бы отдельная переработка идентификаторов и контрактов; она здесь не выполнялась.

## Установка
Основа полного архива — ранее предоставленный исходник и предыдущий выпуск интеграции, а не свежая выгрузка вашего GitHub. Не затирайте им вслепую более новые независимые изменения.
В `FILES.txt` перечислены только пять файлов текущей функции. При наличии свежих изменений в репозитории перенесите именно их, сверив страницу пользователей. В `update.patch` — точечный diff относительно предыдущего архива: сначала `git apply --check`, затем `git apply`, если проверка прошла. При конфликте не используйте force — перенесите изменения вручную.
Не копируйте production `.env` из архивов и не удаляйте существующую БД. Ранние удаления CloudPayments перечислены отдельно в `../DELETED-FILES.txt`; наложение полного ZIP поверх старого репозитория само по себе не удаляет старые файлы.

После коммита и push в main на сервере:
```bash
cd /var/www/trioz && git pull --ff-only origin main && npm ci --ignore-scripts --include=dev && NODE_OPTIONS="--max-old-space-size=4096" npm run build && pm2 restart trioz --update-env
```
Для этой функции миграции не нужны и процесс `tz-id` не менялся. Если предыдущая интеграция с миграцией ещё не установлена, отдельно выполните её порядок обновления из STAGE-2.md после резервной копии БД.
