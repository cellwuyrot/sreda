# Business + TZ ID: удаление провайдера и административный вход

## Результат этапа

Подготовлены согласованные исходники двух проектов. Это этап **удаления CloudPayments и прав администратора через TZ ID**, а не запуск нового эквайринга. Ничего не установлено на сервер; GitHub и production-БД не менялись.

Основа: предоставленный `sreda-main-tz.zip` и доработанная версия Business из предыдущей поставки. Существующий OIDC/API проверен по локальным исходникам, не по рабочему домену.

### Что реализовано

1. Удалены клиентская форма CloudPayments, платёжный API, административный API настройки уведомлений, четыре webhook-маршрута и серверные модули провайдера. Удалены относящиеся только к этой интеграции тесты и две устаревшие инструкции. На странице настроек вместо checkout показана честная недоступность онлайн-оплаты.
2. Убраны специфичные настройки провайдера и его значения по умолчанию. Новая миграция отключает настроенные группы этого провайдера, удаляет специфичные Public ID и очищает связанные секреты. Конфигурации других банков не очищаются. Старые неиспользованные/зарезервированные/ожидающие подтверждения ссылки этого провайдера становятся DISABLED; записи и сведения о заявленной оплате сохраняются.
3. Исторические таблицы заказов и транзакций остаются на месте. Prisma-модели названы LegacyPaymentOrder / LegacyPaymentTransaction с отображением на прежние физические таблицы. Исторические миграции не редактировались. Уже выданные Premium/VPN не отменяются при удалении провайдера.
4. Добавлены отдельные назначения администратора **конкретного приложения TZ ID**. Они не наследуются от глобального User.role TrioZ. Управление — в основной платформе `/admin/tz-id`, блок «Администраторы проектов».
5. Business проверяет это назначение на сервере и использует существующую полноценную админку и те же защищённые API. Не создавалась отдельная урезанная SSO-админка.
6. Убрана небезопасная возможность выдавать подписку по одному нажатию «Я оплатил». Ручные банковские ссылки и СБП сохранены, но заявление плательщика только ожидает сверки администратором. Это не автоматическая проверка банка.
7. В PM2-конфигурации основной платформы найден встроенный пароль Redis. Вместо него оставлена ссылка на серверное окружение; значение не воспроизводится в отчёте. Перед установкой нужно настроить REDIS_URL и заменить ранее хранившийся в репозитории пароль.

## Как теперь работает администратор

### Назначение в основной платформе

- Глобальный администратор TrioZ открывает `/admin/tz-id` и выбирает confidential client Business.
- Для клиента разрешает новое право `roles:read` (интерфейс позволяет обновить и уже зарегистрированного клиента без смены его секрета).
- Вводит точный TZ ID пользователя — `sub`, существующий User.id, а не email/ник. Подтверждает назначение.
- Назначение и запись аудита сохраняются одной транзакцией. Повторное назначение обновляет ту же пару client/user. Отзыв сохраняет запись, устанавливая revokedAt.
- Нельзя назначить несуществующего/удалённого пользователя, public client, отключённый клиент или клиент без разрешения roles:read. Отзыв уже существующего назначения остаётся доступен и для выключенного клиента.

### Новый ограниченный API

`GET https://id.trioz.ru/api/v1/project-role`

Требуется пользовательский access token, выданный confidential client с зарегистрированным scope `roles:read` и согласием пользователя. Ответ:

```json
{"sub":"<USER_ID>","clientId":"<BUSINESS_CLIENT_ID>","role":"ADMIN"}
```

При отсутствии или отзыве назначения роль — `USER`. Пользователь и клиент берутся исключительно из токена. Query-параметры другого пользователя/проекта не дают чужую роль. Глобальная роль TrioZ, email и секретные поля не возвращаются. Ответ не кешируется. Действуют существующие проверки токена/сеанса/клиента и общий лимит project API.

Это **новый реализованный endpoint данного этапа**. Он не был частью исходного документа API и не является сервисным биллингом или API выдачи Premium/VPN.

### Проверка в Business

- Сохраняются OIDC Authorization Code, PKCE S256, state, nonce, проверка iss/sub и userinfo.sub. Добавлен запрос `roles:read`.
- Каждый защищённый запрос SSO проверяет действительность токена и затем текущую роль только своего клиента и своего sub. Redirect на ответе API запрещён; таймаут — 5 секунд.
- Назначение ADMIN даёт эффективную роль ADMIN для обычной `/admin` и административных API. При обычном входе в аккаунт администратор направляется в `/admin`; выбранное до входа предложение сохраняет приоритет перехода.
- Отзыв, неверный client/sub, отсутствие scope, 401/403/429/500 или сбой проверки не сохраняют административные права. Постоянное повышение User.role не записывается, поэтому после отзыва не остаётся «залипший» ADMIN.
- Это проверка на очередном серверном запросе, а не обещание мгновенного удаления уже показанного HTML из открытой вкладки. Уже начатую операцию отзыв не отменяет задним числом.
- Обычный клиент не получает административных прав. Совпадение email не связывает аккаунты.
- Если аккаунт Business уже существует: войти его локальным паролем → `/account` → «Связать существующий аккаунт с TZ ID» → подтвердить пароль → вход TZ ID. После назначения роли дальнейший вход через TZ ID открывает админку.
- Локальный парольный ADMIN остаётся отдельным восстановительным доступом. Отзыв назначения TZ ID его не отзывает. Оператор должен учитывать этот путь при полном отключении сотрудника.
- Сохранилось прежнее ограничение SSO-сеанса Business: до 5 минут, без refresh. Это не долговечная сервисная авторизация.

## Обязательный порядок установки

**Не накладывать новый ZIP поверх старых файлов без удаления исключённых маршрутов.** Лучше применить изменения в Git, включая удаления из `docs/business-integration/DELETED-FILES.txt`, и выкладывать коммит. Иначе старые webhook/checkout-маршруты могут остаться на сервере.

1. Резервные копии обеих БД, файлов и конфигурации. Сначала staging.
2. Если старый провайдер когда-либо использовался: остановить новые продажи через него, отдельно отключить активные автосписания в кабинете/по официальной процедуре провайдера и сверить незавершённые операции. Удаление нашего кода **не отменяет платёжные поручения у провайдера**. До финальной сверки не очищать нужные для неё реквизиты и не отключать старый обработчик. Подготовленная миграция очищает конфигурацию, поэтому её запуск — только после этой процедуры.
3. Подготовить окружение Redis вне Git, сменить старый встроенный пароль и согласовать настройки Redis/приложения. Секреты не отправлять в чат и не коммитить.
4. Обновить основную платформу: установить зависимости без lifecycle scripts, явно применить миграции, собрать приложение, перезапустить web и TZ ID. В корневой поставке есть PM2-имена `trioz` и `tz-id`; фактические пути и процессы проверить на сервере.
5. В админке TZ ID разрешить Business scope roles:read, назначить нужного пользователя. У существующего клиента секрет не меняется. Если issuer кеширует метаданные клиента, перезапустить TZ ID после изменения разрешений.
6. Обновить Business и перезапустить `tzbiz`. Его БД для этого этапа новой миграции не требует, но все миграции прошлой поставки должны быть применены. Если обновление идёт сразу с исходной версии, нужна 0007 предыдущего этапа.
7. Пройти новый вход/consent. У старых access tokens новое разрешение не появится автоматически. Проверить реального ADMIN, обычного пользователя, отзыв назначения и явную привязку старого аккаунта.
8. Утвердить изменённую предварительную политику Business draft-5 и настройки продавца. Инструкции cron/SMTP и ограничения предыдущего этапа остаются в силе.

Пример последовательности **для staging основной платформы**, не команда для безусловного запуска на production:

```bash
npm ci --ignore-scripts --include=dev
npm run migrate -w apps/web
npm run build
npm run check -w apps/id
```

У этого репозитория apps/web postinstall сам запускает migrate deploy. Поэтому в инструкции выбран `--ignore-scripts` и отдельная миграция, чтобы не применять её незаметно при установке пакетов. Prisma generate выполняет build. Desktop/Electron этими командами не собирался и не проверялся как приложение.

Business: `npm ci --include=dev` → `npm run db:deploy` → `npm run build` → перезапуск `tzbiz`. Не запускать db:setup/db:seed на рабочей базе ради обновления. Настройки TZ_ID_CLIENT_ID/SECRET, ключ шифрования токена и точный callback остаются серверными.

Все 21 падающее утверждение воспроизведены в тех же шести файлах из неизменённого исходного архива на том же дереве зависимостей. Это VPN desktop, notification grouping, DM, upload и тест даты продления VPN. Исходный проблемный набор провайдера удалён вместе с самой интеграцией; он не учитывается как исправленный тест. Оставшиеся ошибки и ошибки типов тестовых fixtures не устранены этим этапом.

Миграция проверена на DDL исходной схемы с синтетическими записями в **PGlite (PostgreSQL WASM)**: отключение провайдера, очистка его секрета, сохранение другого банка, старого PAID-заказа и Premium, отключение старого checkout без удаления сведений об оплате, назначения и отзыв. Это не испытание миграции на production PostgreSQL, существующей нагрузке или реальной резервной копии.

UI управления ролями проверен в изолированном React-стенде на синтетическом mock API: desktop 1440 px, mobile 390 px, назначение/отзыв с подтверждением, отсутствие горизонтального переполнения и браузерных исключений. Формы и модальные диалоги осмотрены визуально; кнопки подтверждения доведены до 44 px. Это не сквозной вход в работающий TZ ID.

Рабочий код web проверяется отдельным строгим `tsconfig.build.json`, который исключает тестовые fixtures, но не отключает проверку ошибок приложения. Next build использует именно его. Исходная полная проверка типов тестов остаётся доступна как `npm run test:types -w apps/web`; в ней есть существующие проблемы типов fixtures, их исправление не объявляется выполненным.

Не проверялись: реальный HTTPS/OIDC Business↔TZ ID, production PostgreSQL/Redis, настройки proxy, боевой домен, сторонний эквайринг, внешние списания, реальные Premium/VPN-выдача и возвраты. Для новой основной платформы не выполнялся отдельный полный аудит зависимостей. Результаты аудита прежнего Business нельзя переносить на весь монорепозиторий.

## Что остаётся следующим этапом

- Выбрать нового платёжного провайдера и правила чеков/автопродления.
- Согласовать каталог/технические коды прав Premium и VPN. Свободный externalProductId на витрине сам по себе не является проверенным каталогом основной платформы.
- Реализовать нейтральные заказ, платёжный учёт, checkout, проверенный webhook, возвраты и защиту от повторной выдачи.
- Добавить ограниченный S2S-контракт для реальной выдачи/продления/отзыва Premium/VPN в проекте-получателе, outbox и сверку. Его не заменяют пользовательские project API.
- Только после этого включать кнопки покупки/продления в кабинете TZ ID и обещать автоматическую активацию.

Предыдущая модель трёх режимов предложений Business и редактируемые витринные названия сохранены. Реальная онлайн-покупка по-прежнему закрыта: она не подменена фиктивным checkout или статусом из URL.
