# Админка: подписки, журналы и единый каркас

## Что исправлено

1. **Подписки пользователей:** серверная выдача по 15 пользователей. Кнопки
   «Назад» и «Далее», номер страницы и число найденных пользователей.
   Поиск имени, ника и email ищет по всей базе, а не только по открытому листу.
   Новый поиск возвращает на первый лист. Устаревший запрос отменяется;
   ввод не теряет фокус при загрузке. Ошибка API больше не выглядит как пустой список.
2. **Логи редактора сайта:** строго 15 записей, серверный подсчёт и ограничение
   номера страницы. `?limit=100000` не отменяет ограничение. Фильтр действия
   сбрасывает страницу. Длинные описания переносятся, а не обрезаются.
3. **Последний месяц:** используется скользящее окно **последних 30 суток**,
   включая нижнюю границу, без будущих дат. Это ограничение чтения, не удаление
   строк из базы. На страницу журналов, её счётчик, сводку редактора и действия
   в карточке пользователя действует одна политика `lib/projectAudit.ts`.
   История входов и исторических IP в карточке также ограничена 30 сутками;
   действующие сеансы сохраняются независимо от даты их создания.
4. **Приватность:** проектный журнал выбирает только известные проектные
   типы событий. `Group`, `group`, `WallPost`, `DirectConversation`, `E2EEKey`,
   `MailMessage`, смена личной почты и неизвестные типы не попадают в выдачу.
   Учитывается тип события, а не текущая роль автора: личное действие
   администратора внутри сообщества тоже не становится проектным событием.
   Закрыты альтернативные пути через `/api/editor/overview` и
   `/api/users/[id]/activity`. Фильтры применяются на сервере, до выдачи данных.
   Редактор продолжает видеть лишь собственные проектные действия;
   параметр `userId` не позволяет обойти это правило.
5. **Пользователи:** общий список приведён к тем же 15 строкам и общему
   компоненту листания. Исправлен разбор дробных/отрицательных параметров,
   которые раньше могли дать размер страницы 0. Добавлен второй ключ сортировки
   `id`, чтобы одинаковое время создания не перемешивало соседние страницы.
   Старый ответ-массив `/api/users` без параметров сохранён для выбора значков.
6. **Общий каркас админки:** через серверный `admin/layout.tsx` все разделы
   получают `.admin-workspace`: одинаковые внешние отступы, предельную ширину
   основного содержимого 1152px и шкалу заголовков, фон активной темы. На мобильном
   оставлен запас под нижнюю навигацию. Селекторы ограничены внешним каркасом;
   ширина модальных окон и внутренние сетки форм не унифицируются насильно.
   Общий `AdminPagination` используется в пользователях, подписках и журнале.
   В подписках поправлены контраст светлой темы, поля и статусы; таблица
   прокручивается внутри своего блока, не расширяя всю мобильную страницу.

## Что показало изучение структуры

- В подписках использовалась устаревшая загрузка всего массива `/api/users`,
  хотя в API уже существовало серверное листание для другого экрана.
- У журнала листание было, но по 50 записей; не было ограничения периода,
  верхней границы размера листа и разделения проектных/личных событий.
- Только исправления `/api/admin/logs` было бы недостаточно: сводка редактора
  и карточка активности читали ту же таблицу без такого разделения.
- Страницы админки имели разные внешние ширины (`max-w-2xl`…`max-w-6xl`),
  отступы и заголовки. Общий каркас теперь задаёт базовую геометрию, сохраняя
  проектные карточки, акценты тем и специализированные формы.
- История платежей отдельного пользователя и карточки подписок не являются
  журналом редактирования сайта: оплаченные сроки, подтверждения и суммы
  намеренно не ограничены 30 сутками и не удалены.
- Журналы сборок принадлежат отдельным заданиям. Их текст также не усечён
  политикой аудита: он необходим для диагностики соответствующей сборки.

## Границы изменений

Изменений схемы БД и новых миграций **нет**. Логика расчёта/продления Premium
и VPN, оплаты, ключи TZ ID, WebRTC и маршруты входа не изменены. На рабочий
сервер изменения автоматически не устанавливались.

Старые записи остаются в БД. Автоматическую очистку/архивацию истории следует
вводить отдельно, после выбора срока хранения и резервного копирования.
Для нового типа проектного события надо явно расширить разрешённый список
в `projectAudit.ts` и добавить тест. Неизвестные типы скрываются по умолчанию.

## Проверки

- Производственная сборка `npm run build` — успешно.
- `npm run typecheck -w apps/web` — успешно.
- `npm run lint -w apps/web` — успешно.
- `npm run check -w apps/id` — успешно.
- **43 новых теста проходят.** До изменений: 2223 теста, 2202 успешных,
  21 падение. После: 2266 тестов, 2245 успешных, те же 21 падение;
  новых падений нет. Список прежних проблем: `admin-review-results.json`.
  Это не полностью зелёный общий набор: прежние сбои десктопного VPN,
  загрузки вложений, DM, группировки уведомлений и датозависимого теста VPN
  не исправлялись в рамках этой задачи.
- Локальный браузер: 1440px и 390px, светлая/тёмная темы обоих экранов,
  15 строк, переход страниц, ошибки/пустые списки и форма выдачи подписки.
  Горизонтального переполнения страницы и ошибок JS не обнаружено.
  Использованы реальные компоненты и CSS проекта, тестовые данные и сессия.
  Проверка с реальной PostgreSQL и боевыми учётными записями не проводилась.

## Приёмка после установки

1. Открыть «Подписки пользователей»: максимум 15 пользователей, следующий лист.
2. На втором листе ввести имя человека с другого листа: поиск возвращает
   результат на первый лист. Проверить пустой поиск и сброс строки.
3. Открыть журнал: максимум 15 событий за последние 30 суток.
4. Под аккаунтом, который одновременно администратор сайта и владелец
   приватного сообщества, изменить это сообщество. В глобальном журнале,
   сводке редактора и карточке активности это действие появиться не должно.
5. Изменить контент сайта — соответствующее проектное событие должно появиться.
6. Проверить редактора: лишь его события; обычный пользователь получает 403.
7. Проверить те же экраны на телефоне и в обеих темах.

Команды установки — `ADMIN-DEPLOY.md`.
