## Что проверено интеграционно

- Парольный и QR-вход в кабинет и внешнее OIDC-приложение: один существующий User, PKCE S256, state, nonce, consent; QR действительно декодировался zbar из изображения.
- Одноразовое потребление QR, истечение/связь с браузером, явное подтверждение; телефонная cookie не копируется на другой браузер.
- Изменение общего профиля отражается в userinfo. Контакт доступен только с отдельным scope; ID token не принимается как access token.
- Идемпотентность и изоляция подписок/уведомлений разных клиентов, запрет чужого userId/clientId, безопасные ссылки, отключение уведомлений и отзыв доступа.
- Внешние подписки не изменяют Premium, VPN, peer, оплату и трафиковые ограничения TrioZ.
- Основной сайт редактирует тот же контакт, использует существующую форму сотрудничества. Старый Credentials-вход, смена пароля, отзыв сеансов, обезличивание пользователя и сохранение содержимого сообществ проверены.
- Кабинет и основные состояния просмотрены на desktop и ширине 390px: меню, профиль, адреса, подписки, сервисы, уведомления, безопасность, сотрудничество, QR-подтверждение. Нет горизонтального переполнения и ошибок JS. Исправлен отступ между фильтром и карточкой уведомления. Часть скриншотов с искусственными тестовыми данными приложена в hub-screenshots.

## Границы готовности

- 2FA не реализована и не включена; UI явно показывает «пока недоступна».
- Другие проекты не подключаются автоматически: каждый регистрирует client, реализует стандартный OIDC callback и backend API. Пример — [examples/project-api.ts](examples/project-api.ts). Их исходников в этом проекте нет.
- Регистрация остаётся существующей регистрацией TrioZ: общая центральная запись User, без копирования пароля или второго аккаунта.
- Аватар/email и управление паролем/сеансами используют существующий интерфейс TrioZ. На issuer есть соответствующие переходы.
- Кабинет объединяет последние 100 уведомлений; фильтр работает по этому списку, не по всей истории. Это не замена мессенджеру и не email/push-рассылка.
- Доступные API-права задаются при регистрации клиента. Старый клиент без этих прав не получает их автоматически; новые consent/scopes требуют явной настройки.
- Реальная доставка аудио, VPN-трафик и работа API чужих production-проектов не тестировались. VPN, voice-модули и платёжные карточки в рамках этой доработки не переписывались.

## Повторение тестов

Для unit-тестов: `npm run test -w apps/web -- --run src/lib/tzId.test.ts src/lib/tzIdHub.test.ts src/lib/tzIdQr.test.ts src/lib/tzIdProjectApi.test.ts src/app/api/tz-id/manage/route.test.ts`, `npm run test -w apps/id`.

Для browser integration нужен Node >=22.12, отдельная PostgreSQL БД **tzid_test** на localhost, итоговая schema, Playwright/Chromium; для нового QR-теста также `zbarimg`. Скрипты создают и удаляют искусственные данные; НИКОГДА не выполнять на production-БД. Переменные DATABASE_URL, PLAYWRIGHT_MODULE, CHROMIUM_PATH, TZ_ID_TEST_DIR задаются для локального тестового окружения. Команды из корня: `npm run test:hub:integration -w apps/id`, `npm run test:web:integration -w apps/id`, `npm run test:integration -w apps/id`. Не запускать их одновременно: они используют одинаковые локальные порты. Тестовые секреты/браузерные дампы в архив не включены.
