# Структура ролей и деловой кабинет (август 2026)

Документ описывает фактическое поведение кода после правок. Если код и документ
расходятся — верным считается код (`src/lib/roles.ts`).

## 1. Роли

| Роль | Ранг | Назначение |
|---|---|---|
| `USER` | 1 | Обычный посетитель |
| `CONSULTANT` | 2 | Партнёр, личный кабинет `/partner` |
| `EDITOR` | 3 | Редактор, рабочая панель `/editor` |
| `ADMIN` | 4 | Полный доступ |

Единый источник истины — `src/lib/roles.ts`: `APP_ROLES`, `ROLE_RANK`, `isStaffRole`,
`isAdminRole`, `isPartnerRole`, `assignableRolesFor`, `canAssignRole`, `canActOnUser`,
`EDITOR_ADMIN_SECTIONS`, `canOpenAdminPath`.

## 2. Выдача ролей

- `ADMIN` может выдать любую роль.
- `EDITOR` может выдать только `USER` и `CONSULTANT`.
- Нельзя действовать на пользователя с равным или более высоким рангом
  (раньше сравнение было нестрогим — редактор мог переписать равного).
- Значение роли валидируется по списку (`isAppRole`) — произвольную строку
  в базу больше не запишешь.
- Премиум выдаёт только `ADMIN`.

## 3. Разделы панели

Редактору разрешены только: `users`, `badges`, `appeals`, `projects`,
`notifications`, `logs`. Остальные разделы закрыты `layout.tsx` с `AdminOnlySection`
(`about, ai, broadcast, builds, content, ecosystem, games, payments, premium, servers,
services, vpn, welcome, windows`) — защита на сервере, а не спрятанные кнопки.

Границы редактора:

- Логи — только свои действия (`GET /api/admin/logs` сам добавляет `userId`).
- Нет доступа к платежам, премиуму, рассылке, настройкам ИИ, серверам, VPN,
  сборкам, статистике системы и содержимому сайта.
- Нет доступа к активности посетителей (`/api/users/[id]/activity` — только `ADMIN`).

## 4. Кабинет партнёра (`/partner`)

Доступ: `CONSULTANT` или `ADMIN` (`app/partner/layout.tsx`, серверная проверка).

Структура ведения бизнеса закреплена на сервере, а не в переписке делового чата:

| Блок | Модель | API |
|---|---|---|
| Счета и оплаты | `ProjectInvoice` | `/api/projects/[id]/invoices`, `.../invoices/[invoiceId]` |
| Документы и договоры | `ProjectDocument` | `/api/projects/[id]/documents`, `.../documents/[docId]` |
| Сроки и ответственный | `PartnerProject.dueDate`, `responsibleId` | `PATCH /api/projects/[id]` |
| История этапов | `ProjectEvent` | `/api/projects/[id]/history` |
| Сводка по проектам | — | `/api/projects/summary` |

Правила:

- Суммы хранятся в минорных единицах (копейках) целым числом.
- Создавать счета, менять их статус, добавлять и убирать документы, ставить сроки
  и брать проект на себя может только сотрудник (`ADMIN`/`EDITOR`).
- Владелец проекта видит свои данные и может только сообщить об оплате
  (`{ declare: true }`) — статус «оплачено» ставит только сотрудник.
- Файлы документов принимаются только из `/uploads/projects/` (`isProjectUploadUrl`),
  иначе через поле `url` можно было бы подсунуть чужой путь.
- Каждое действие пишет запись в `ProjectEvent` и уведомление владельцу.

## 5. Обращения и проекты в панели

- Поиск по списку и кнопка обновления рядом с полем поиска.
- По 10 записей на страницу (`PER_PAGE = 10`).
- Безвозвратное удаление: `DELETE /api/projects/[id]`, `DELETE /api/appeals/[id]`
  (оба только для `ADMIN`/`EDITOR`, оба пишут в аудит-лог).
- При удалении обращения деловой чат не удаляется: у разговора снимается
  связь `appealId` в одной транзакции с удалением.

## 6. Что требуется при развёртывании

1. `npx prisma migrate deploy` — миграция `20260916000000_partner_business_cabinet`.
2. `npx prisma generate` — новые модели в клиенте Prisma.
3. Обычная сборка `next build`.
