# VPN-узел: сохранение сети и диагностика

## Причина и границы исправления

На дочернем сервере работали два независимых подключения: нативный `awg0`
(10.8.0.0/24, UDP 51820) и контейнер `amnezia-awg2` (UDP 31558).
У нативного интерфейса отсутствовал MASQUERADE; после добавления правила связь
восстановилась. Рукопожатие само по себе не подтверждает выход клиента в Интернет.

В установщике найден воспроизводимый путь потери NAT: очистка обычного WireGuard
удаляла правило по общей подсети, а уже поднятый AWG не выполнял PostUp повторно.
Это подтверждённый дефект кода, но не доказательство точного момента удаления
правила на конкретном сервере. Контейнер переносить или создавать второй не нужно.

## Изменения

- Установщик больше не удаляет общий NAT при очистке WireGuard и не сохраняет
  глобальный снимок iptables вместе с динамическими правилами Docker.
- PostUp проверяет наличие правил перед добавлением. Перезапуск агента не
  означает пересоздание интерфейса.
- Локальный помощник проверяет интерфейс, фактический UDP-порт, IPv4 forwarding,
  исходящий маршрут, NAT, оба направления FORWARD и входящее правило UDP.
- Без `--apply` / `--repair` проверки только читают состояние. Автовосстановление
  в агенте включается явно через `WG_NETWORK_REPAIR=1`; старые установки сами
  этот режим не получают.
- После безопасного подключения помощника systemd принимает уже работающий
  интерфейс без down/up, проверяет сеть при запуске. Агент повторяет проверку
  каждые 30 секунд и восстанавливает только отсутствующие необходимые правила
  и IPv4 forwarding. Сетевые запросы ограничены по времени.
- В админке серверов состояние агента отделено от состояния сети VPN. Есть
  подсказка (?), время проверки и агрегированные показатели рукопожатий/трафика.
  Старый агент, ошибки доступа и устаревший отчёт отображаются как неизвестное
  состояние, а не как исправный сервер. Обновление — каждые 30 секунд.

Ключи, профили, порты, Docker, подписки, платежи и мониторинг партнёрских проектов
не переносились и не переписывались. Миграций БД нет; Business обновлять не нужно.
В отчёты не добавляются ключи клиентов или необработанные ошибки команд.

## Обновление основного сервера

Сначала перенесите исходники из архива в свой репозиторий, проверьте `git diff`,
сделайте commit и push. Команды ниже предполагают, что новая версия уже в Git,
рабочее дерево сервера чистое и имя процесса PM2 — `trioz`.
Сделайте обычную резервную копию перед развёртыванием.

```bash
cd /var/www/trioz &&
export PATH="/opt/tzbiz-node22/current/bin:$PATH" &&
git pull --ff-only &&
ELECTRON_SKIP_BINARY_DOWNLOAD=1 npm ci --include=dev &&
npm run build &&
pm2 restart trioz --update-env &&
pm2 save
```

Основной сервер показывает диагностику, но сам не исправляет сеть дочернего.

## Обновление существующего дочернего сервера

Не запускайте полный установщик `awg-node.sh` или `--reset` для этого исправления.
Сначала узнайте каталог реально работающего агента:

```bash
systemctl show trioz-vpn-agent -p WorkingDirectory --value
```

Если это `/opt/trioz/apps/vpn`, используйте `/opt/trioz`. При другом пути используйте
соответствующий корень репозитория. Нужен Node.js >=20 в PATH root; при необходимости
передайте `NODE_BIN=/полный/путь/к/node` через `sudo env`.

```bash
cd /opt/trioz && git pull --ff-only
sudo bash deploy/awg-network-repair.sh --iface=awg0
```

Вторая команда — только диагностика. Код выхода 2 означает неполную/неисправную
конфигурацию; 1 — ошибку аргументов или выполнения. Изучите JSON.
Порт читается с работающего интерфейса; если заданный `--port` не совпадает,
изменения запрещены. При неоднозначном маршруте, неподнятом интерфейсе, ошибках
доступа или блокировки iptables помощник не угадывает настройки.

Чтобы применить восстановление и подключить его к systemd:

```bash
sudo bash deploy/awg-network-repair.sh --iface=awg0 --apply
```

Помощник сначала исправляет и перепроверяет сеть, затем создаёт только свои
`20-trioz-network.conf` для `awg-quick@awg0` и `trioz-vpn-agent`. Предыдущие версии
этих файлов копируются в `/var/backups/trioz-vpn-network/<UTC>-<PID>/`.
Основной unit с токенами и сторонние override не перезаписываются.
Работающий `awg0` принимается без пересоздания, перезапускается только агент.
Docker не останавливается. Нет flush таблиц или глобального восстановления правил.
Не запускайте параллельно несколько установщиков/помощников.

## Проверка результата

```bash
systemctl is-active awg-quick@awg0 trioz-vpn-agent
sysctl net.ipv4.ip_forward
sudo bash /opt/trioz/deploy/awg-network-repair.sh --iface=awg0
iptables -t nat -L POSTROUTING -n -v --line-numbers
```

В течение 30–60 секунд проверьте карточку VPN-узла в админке. Ожидаются свежий
отчёт и проверенные настройки. Подключите клиента к этому серверу, откройте
несколько HTTPS-сайтов, проверьте DNS и внешний IP. При работе счётчики нужного NAT
должны расти. Нулевые счётчики при отсутствии клиентского трафика допустимы.

Важно: локальные проверки подтверждают настройки, но не прохождение пакетов через
все более ранние правила firewall, сеть провайдера, DNS или MTU. Количество
рукопожатий — за последние 180 секунд, двусторонние счётчики — накопленные, а не
число пользователей, которые прямо сейчас открывают сайты. Проверки относятся к
IPv4; сложная policy routing/несколько неоднозначных подсетей требуют ручного
разбора. После Docker-перезапуска восстановление возможно на следующем цикле
агента, а не мгновенно; таймауты команд могут увеличить задержку.

Отдельно в согласованное окно обслуживания проверьте перезагрузку узла и
перезапуск Docker с повторной проверкой обоих VPN. Эти действия могут прервать
соединения; в рамках подготовки архива на реальном сервере они не выполнялись.
Не удаляйте рабочие правила на продакшене специально для проверки восстановления.

## Отключение и откат

Чтобы остановить фоновое восстановление, измените только собственный agent override
`/etc/systemd/system/trioz-vpn-agent.service.d/20-trioz-network.conf`:
установите `Environment=WG_NETWORK_REPAIR=0`, затем выполните `systemctl daemon-reload`
и `systemctl restart trioz-vpn-agent`. Диагностика продолжит работать.

Это НЕ выключает стартовую проверку `ExecStartPost` у awg-quick. Для полного отката
верните прежние собственные override из указанной резервной копии; если файла
раньше не было, удалите только соответствующий новый `20-trioz-network.conf`.
Затем `systemctl daemon-reload`. Не перезапускайте и не останавливайте VPN-интерфейс
ради отката; согласуйте последующую перезагрузку отдельно. Другие override,
Docker, ключи и действующие правила iptables не удаляйте и не восстанавливайте
глобальным снимком. Откат исходников делайте согласованно на основном и дочернем
сервере. Папка резервной копии может быть пустой при первой установке.

## Проверки версии

- Vitest: 194 файла, 2621 тест — успешно.
- Проверка типов web, shared и desktop — успешно.
- Полный ESLint web и повторная проверка изменённых web-файлов — успешно.
- Production build основного проекта — успешно. Сохранились существующие
  предупреждения Next.js о middleware и широком file tracing; связанные с
  проектами маршруты ради подавления предупреждений не изменялись.
- 26 тестов сетевого помощника: потеря NAT, идемпотентное восстановление,
  неизвестные ошибки, выбор интерфейса/маршрута, несовпадение порта, сохранение
  Docker и безопасное принятие работающего интерфейса.
- Shell lifecycle проверен с изолированными командами и временной файловой системой:
  preview не пишет, повторное применение сохраняет credentials, отказ не создаёт
  persistent-настройки. Это не испытание реального systemd/ядра.
- Визуальные проверки реального компонента: узкий/широкий экран, две темы,
  исправность, отсутствие NAT, неизвестные/старые данные и старый агент.

Результат production build указан при передаче архива. Скриншоты, node_modules,
логи тестов и сборки в поставку не включаются; ранее очищенные QA-артефакты не
возвращаются. Запись об изменениях находится только в docs.
