# Обновление и откат — 2026-10-27

## Перед установкой

1. Работать сначала на изолированном staging. Ничего из этого отчёта не применялось к production пользователя.
2. Сделать согласованную резервную копию PostgreSQL и приватных/публичных uploads, проверить доступ к копиям и тестовое восстановление. Пример: `pg_dump --format=custom --file=backup.dump "$DATABASE_URL"`. Хранить копии вне web-root с шифрованием и ограниченными правами. Сам dump не резервирует файлы uploads или приватные браузерные E2EE-ключи.
3. Не очищать IDB браузера. Сохранить несинхронизированные холсты до обновления. Непроверенный общий legacy-кеш канала не переносится автоматически в аккаунтный namespace: он может принадлежать другому пользователю. Серверные снимки от этого не удаляются.
4. Сохранить предыдущий образ/исходники и настройки. Новый формат PUT требует обновить web и desktop-клиенты совместно. Старому клиенту вернётся 428: требуется перезагрузка/обновление, а не обход контроля версии.

## Миграции

`npm ci` больше не меняет БД. Выделенный deployment-шаг:

```sh
npm ci
npm run build:shared
npx prisma generate --schema apps/web/prisma/schema.prisma
npx prisma migrate status --schema apps/web/prisma/schema.prisma
npx prisma migrate deploy --schema apps/web/prisma/schema.prisma
npm run build
```

Команды миграций требуют настроенного DATABASE_URL. Новая миграция для данного пакета исправлений не требуется: CAS использует уже существующий updatedAt. Это **не означает**, что вся историческая цепочка проверена на реальных данных.

Если production раньше обновлялся через `db push`, нельзя слепо объявлять миграции applied или запускать их поверх существующих таблиц. На копии БД сопоставить `_prisma_migrations`, текущую схему и SQL; устранить drift/baseline по фактической схеме. Не применять `migrate reset` к production. Остановить rollout при несоответствии схемы.

## Realtime

- Одна реплика web/realtime, один процесс Socket.IO/voice, PM2 fork/instances=1.
- `REALTIME_REPLICAS=1`, `WEB_CONCURRENCY=1` при наличии, не включать cluster-mode.
- Redis здесь не является Socket.IO adapter и не делает in-memory voice/presence распределёнными. Для нескольких машин нужна отдельная реализация состояния/адаптера/планировщика и проверка сбоев.

## Redis

- При включении REDIS_PASSWORD настроить согласованный REDIS_URL (URL-encode спецсимволы пароля).
- Healthcheck должен быть healthy и с паролем, и без. Проверить `PONG` на стенде.
- Используется noeviction: контролировать used_memory/maxmemory и ошибки записи; AOF не заменяет отдельную резервную копию.

## TURN

1. Создать случайный TURN_AUTH_SECRET самостоятельно, например `openssl rand -hex 32`. Не публиковать секрет и не помещать его в Git.
2. Передать **одинаковый** секрет web-приложению и coturn, пересоздать оба процесса. Для GitLab добавить masked/protected CI variable TURN_AUTH_SECRET.
3. Задать TURN_URL как реальный URI или список через запятую, например `turn:relay.example.org:3478?transport=udp,turn:relay.example.org:3478?transport=tcp`. `turns:...:5349?transport=tcp` добавлять только при реально работающем TLS listener с сертификатом.
4. Выполнить relay-only звонок между разными сетями, затем long-call/ICE-restart. Проверить expiry credentials, разрыв/возврат сети и новый вход после длительной фоновой вкладки.
5. Пока TURN_AUTH_SECRET пуст, допустим прежний TURN_USERNAME/TURN_CREDENTIAL: это совместимость, **не устранение долгоживущего секрета**. После успешного перехода отозвать старый static credential, проверить настройки realm/listeners coturn.

## Поведение, о котором нужно сообщить пользователям

- Закрытие окна/вкладки больше не удаляет все защищённые разговоры на аккаунте. Удаление — явное, для выбранного SECURE-разговора. TTL пока отсутствует.
- Новые nonextractable E2EE-ключи не экспортируются. Удаление данных устройства может навсегда лишить доступа к старой переписке. Замена ключа не расшифровывает историю, зашифрованную для прежнего.
- При одновременном редактировании одной карточки действует local-wins; это не Google Docs-подобный протокол символов/операций.
- Локально сохранённый offline-снимок не означает успешную запись на сервер: нужно проверить подтверждение/сообщения ошибки после возврата сети.

## Приёмка на staging

- Все автоматические команды из VALIDATION.md, затем авторизация двух реальных аккаунтов в двух отдельных браузерах.
- Отзыв роли: calendar list/create/update/delete и прежняя ссылка на вложение должны быть запрещены согласно ACL; public avatars остаются доступны.
- Холст: независимые и одновременные изменения, удаление против правки, rename + move, создание пустой доски, пятая/шестая доска, отключение сети, delayed ответы и восстановление сокета. Проверять серверный итог и историю, не только видимый экран.
- E2EE: импорт при 500, 409, потере ответа и запрете IDB; смена аккаунта; две вкладки; подтверждение старого fingerprint. Не использовать реальные ключи в тестовом стенде.
- Превью: публичный HTTPS, публичный redirect, redirect в private address, медленное тело/заголовки, большое тело; проверять отсутствие исходящего запроса к private destination средствами стенда.
- Electron: только доверенный origin/main frame вызывает native bridge; iframe/чужое окно/внешний URL не вызывают. Проверить screen source picker, fullscreen, WASAPI и listen-only на целевых ОС.

## Откат

1. Остановить новые записи/развёртывание; сохранить диагностику и актуальный снимок БД/файлов.
2. Вернуть предыдущий образ и согласованные настройки TURN/Redis. Отдельной новой schema migration в этой поставке нет, но уже применённые исторические миграции нельзя «откатывать» автоматическим reset.
3. Не удалять IDB: прежние identity, history и pending могут быть единственным способом восстановления. Если приходится откатывать формат key namespace, сначала разработать и проверить перенос ключей — не копировать ключ другого аккаунта вручную.
4. Безопаснее откатить frontend вместе с backend. Старый frontend против нового API будет получать 428; старый backend снова допускает last-write-wins и массовый beacon-delete, поэтому простой rollback возвращает исходные риски.
5. Если потребовалось восстановление из backup, восстанавливать БД и uploads согласованно и отдельно проверять доступность локальных E2EE-ключей. Отмена замены серверного публичного ключа не восстанавливает утраченный приватный.
