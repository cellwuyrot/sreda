# Sreda / TrioZ — дополнительный технический аудит

**Режим: только анализ, без правок кода.** 27 октября 2026.

## Краткий вывод

Первый разбор закрыл отдельные пользовательские симптомы, но не заменяет проверку целостности данных, единой модели доступа, жизненного цикла ключей и готовности инфраструктуры. Основной недостающий слой анализа — **поведение системы при смене состояния**: отзыв роли, потеря сети, два устройства/две вкладки, смена аккаунта, отказ Redis/БД, повторная доставка и частично успешная операция.

Главные следующие приоритеты:
1. Проверить права каждого API напрямую, а не только видимость кнопок и каналов.
2. Устранить риски потери данных: конфликтующие снимки холста, импорт/восстановление ключей, глобальное удаление защищённых чатов.
3. Проверить SSRF и ограничения времени/ресурсов внешних запросов.
4. Сделать релиз воспроизводимым: обязательные тесты, согласованные миграции, восстановление из резервной копии.
5. До масштабирования определить архитектуру realtime-состояния: текущий Redis не делает Socket.IO и голосовые комнаты распределёнными.

**Это рекомендации и находки, а не внесённые исправления.** Ни одна из новых проблем не исправлялась в рамках этого запроса.

## 1. Основание и ограничения

Проверена текущая локальная копия проекта после предыдущей поставки исправлений. Дополнительно прочитаны исходники API календаря, ссылочных превью, E2EE, сессий, Socket.IO, прав вложений, TURN, Electron IPC, конфигурации Redis, GitHub/GitLab CI и деплоя. Инвентаризация обнаружила 236 файлов `route.ts` в web API и 102 каталога SQL-миграций с `migration.sql`. Наличие файла не означает, что весь его код проверен.

Проверка была **выборочной по важным цепочкам**, а не полным pentest/формальной верификацией всего продукта. Не использовались production-аккаунты, рабочая БД, реальные секреты или административный доступ к серверу. Нагрузка, восстановление БД, Android/Electron-сборки, Windows VPN и TURN между сетями не запускались.

Новая исполняемая проверка: локальный вызов существующего URL-фильтра без сетевых запросов. Полный набор тестов повторно не запускался. Результат предыдущего прогона: 2266 успешных и 21 падающий тест; те же 21 падение были воспроизведены на исходниках до предыдущих исправлений. Это исторический результат предыдущего этапа, не показатель покрытия всех перечисленных ниже рисков.

Уровни доказательности:
- **Код:** поведение непосредственно следует из прочитанной реализации; рабочий E2E не запускался.
- **Локально:** воспроизведено безопасной локальной проверкой.
- **Условный риск:** зависит от конфигурации, продуктовой политики или пути эксплуатации; не объявляется готовой уязвимостью без проверки.

Приоритет P1 — до активного расширения/релиза соответствующей функции; P2 — плановый hardening и эксплуатационная надёжность. Обоснований объявлять новую подтверждённую P0-аварию в рамках этой проверки нет.

## 2. Новые и дополнительно уточнённые находки

### T01. API календаря расходится с общей моделью доступа — P1

**Доказательность: код.**

**Файлы:**
- `apps/web/src/app/api/calendar/route.ts:14–32,109–120`.
- `apps/web/src/app/api/calendar/[id]/route.ts:10–24`.
- Для сравнения: `apps/web/src/lib/connectPermissions.ts:100–165`.

GET календаря проверяет, что пользователь состоит в группе. При этом не вычисляются `hidden`, `isRestricted`, `readAccess`, разрешённые теги и ограничения родительского канала — всё это учитывает общий `getChannelPermissions`. PATCH/DELETE также авторизуются по членству и роли/авторству, а не по актуальному доступу к каналу.

**Сценарий:** пользователь остаётся обычным участником сообщества, но не имеет роли для закрытого календарного канала. Зная ранее полученный channelId, вызывает API напрямую. По показанному пути серверной проверки достаточно членства, чтобы получить события. UI-скрытие не является защитой прямого API.

**Что проверить:** restricted/hidden/readAccess и закрытая категория для GET/POST/PATCH/DELETE; снятие тега, выход/исключение, замороженная группа, блокировка пользователя. Отдельно определить политику редактирования собственных событий после потери доступа.

**Критерий закрытия:** разрешения канала одинаковы в UI, API и realtime; обычный участник без доступа получает отказ при прямом запросе. Нужны интеграционные отрицательные тесты, а не только unit-тест CRUD.

### T02. SSRF-защита проверяет имя, но не гарантирует безопасный адрес соединения — P1

**Доказательность: локально для фильтра; эксплуатация серверного запроса не проверялась.**

**Файлы:** `apps/web/src/lib/urlSafety.ts:12–36`; `apps/web/src/app/api/link-preview/route.ts:73–108`; `apps/web/src/app/api/link-preview/image/route.ts:44–73`.

`safeUrl` проверяет строку hostname. Нет проверки результатов DNS/всех адресов и привязки фактического соединения к проверенному адресу. Также не блокируются некоторые специальные формы IP.

Безопасный офлайн-результат существующей функции:

| Адрес | Принят фильтром |
|---|---|
| `http://127.0.0.1/` | Нет |
| `http://[::ffff:127.0.0.1]/` | Да |
| `http://[::]/` | Да |
| `http://100.64.0.1/` | Да |

Первый разрешённый IPv6-адрес представляет IPv4 localhost. Это **подтверждённый пропуск фильтра**, но не доказательство чтения секретов: итоговая достижимость зависит от ОС, IPv6 и egress-защиты. Для домена с приватным DNS-ответом строковый фильтр также недостаточен.

**Что проверить:** IPv4-mapped IPv6, A/AAAA, несколько DNS-ответов, DNS rebinding, redirects, нестандартные порты, отказ egress на приватные/служебные сети. Проверять только на изолированном стенде, без обращений к cloud metadata рабочего сервера.

**Критерий закрытия:** проверяется адрес назначения соединения на каждом переходе, а не только исходное имя; запрещённые диапазоны недостижимы и на сетевом уровне.

### T03. Таймаут картинки-превью заканчивается до чтения тела — P2, при большой нагрузке P1

**Доказательность: код.**

**Файл:** `apps/web/src/app/api/link-preview/image/route.ts:44–74,88–114`.

`fetchImage` возвращает Response после получения заголовков и в `finally` снимает 8-секундный таймер. Тело читается затем в GET через `reader.read()` вне этого дедлайна. Размер ограничен, однако медленно передаваемое или зависшее тело может удерживать обработчик дольше заявленного лимита. Ошибка во время чтения тела также не преобразуется здесь в контролируемый ответ.

**Что проверить:** сервер отдаёт заголовки сразу, затем задерживает каждый байт; поток обрывается; Content-Length отсутствует/ложный; 120 одновременных медленных запросов. Предел размера не заменяет предел времени.

**Критерий закрытия:** дедлайн покрывает DNS/подключение/редиректы/тело, есть отмена upstream и ограничение параллелизма/потребления памяти.

### T04. Импорт E2EE-ключа неатомарен и может потерять старую локальную пару — P1

**Доказательность: код.**

**Файлы:** `apps/web/src/lib/e2ee.ts:321–353`; `apps/web/src/app/api/e2ee/route.ts:90–165`.

`importKeysFromJSON` сначала записывает новую пару поверх единственного значения в IndexedDB, затем отправляет серверный POST. При 401/429/500 или сетевой ошибке возвращает false, но прежний локальный ключ уже заменён. Сервер может продолжить публиковать старый публичный ключ. Старый ключ не сохраняется как отдельная версия, откат не выполняется. Соответствие переданных public/private частей пары явно не проверяется.

**Сценарий:** начать импорт другого ключа и отключить сеть перед POST; после ошибки проверить старые зашифрованные сообщения и отпечатки на обоих концах.

**Критерий закрытия:** staged import с проверкой пары, сохранением старого ключа и явным протоколом подтверждения/отката. Сбой на любом шаге не уничтожает последнее читаемое состояние.

### T05. Локальный E2EE-ключ не разделён по аккаунтам — P1 для устройств с несколькими пользователями

**Доказательность: код; влияние на конкретный UI-сценарий требует E2E.**

**Файлы:** `apps/web/src/lib/e2ee.ts:3–5,21–49`; `apps/web/src/components/dm/DMPanel.tsx:483–498`.

База и `KEY_ID = "identity-keypair"` одинаковы для всех пользователей одного origin. `getOrCreateKeyPair()` не получает userId. При входе другим аккаунтом DMPanel получает ту же локальную пару и пытается опубликовать её для нового аккаунта. Если у нового аккаунта ключа ещё нет, аккаунты могут получить одинаковую криптографическую идентичность на этом устройстве. При импорте одного аккаунта заменяется общий локальный слот.

Это не доказательство удалённого взлома E2EE. Это нарушение ожидаемой изоляции аккаунтов на одном профиле браузера.

**Критерий закрытия:** namespace по аккаунту/устройству; тест A → logout → B → logout → A; определённая политика хранения ключей и очистки при выходе. Простое удаление IndexedDB при logout без стратегии восстановления опасно.

### T06. Обещания резервного копирования не согласованы с неизвлекаемым ключом — P1 для восстановления данных

**Доказательность: код.**

**Файл:** `apps/web/src/lib/e2ee.ts:36–40,290–316`.

Новая приватная пара создаётся с `extractable: false`. Стандартный WebCrypto не позволяет экспортировать такой private key, поэтому `exportKeysToJSON` ожидаемо завершится ошибкой для обычного нового ключа. Защита неизвлекаемого ключа сама по себе полезна, но создаёт продуктовый вопрос: как восстановить переписку после очистки профиля/потери устройства? Создание другой пары не делает сообщения, зашифрованные для прежней, читаемыми.

**Критерий закрытия:** документированная модель device identity, key history и восстановления; UX не обещает невозможного; тест восстановления с нуля и чтения старой истории. Решение — не автоматически сделать ключ извлекаемым, а спроектировать угрозы и recovery.

### T07. Закрытие одной вкладки удаляет защищённые чаты других вкладок/устройств — P1, зависит от продуктового замысла

**Доказательность: код; ожидаемость требует решения владельца продукта.**

**Файлы:** `apps/web/src/components/dm/DMPanel.tsx:501–512`; `apps/web/src/app/api/dm/secure-cleanup/route.ts:16–28`.

DMPanel вызывает общий cleanup на `beforeunload`, `pagehide` и размонтировании. POST удаляет все SECURE-разговоры пользователя, а не одну вкладку/одну сессию. Поэтому уход из DM в одном окне может удалить разговор, который ещё открыт в другом, а также его серверные сообщения для собеседника. Последовательные удаления сообщений и разговоров не оформлены одной транзакцией.

**Что решить:** эфемерность означает «до закрытия этой вкладки», «до выхода всех участников» или «любой выход уничтожает всё»? Сейчас реализовано последнее широкое поведение без привязки к конкретной вкладке.

**Критерий закрытия:** явная семантика, lifetime/session ownership или серверный TTL, тест двух вкладок и двух устройств, тест частичного сбоя удаления.

### T08. CI не использует существующий набор тестов как release gate — P1

**Доказательность: конфигурация.**

**Файлы:** `.github/workflows/ci.yml:56–61`; `.gitlab-ci.yml:1–48`; `apps/web/package.json:13–17`.

В показанных pipeline выполняются lint/build, но нет обязательного `npm test`. Отдельный web typecheck также не выделен как явный gate. Нельзя считать большое количество тестов защитой от регрессий, если изменения можно выпустить, их не запуская.

**Критерий закрытия:** требуемые проверки PR/релиза — unit/integration/typecheck; явный процесс разбора 21 существующего падения; без бесконтрольного «ignore failures». Тестовый отчёт должен сохраняться как артефакт.

### T09. Пути изменения схемы БД противоречат друг другу — P1

**Доказательность: конфигурация.**

**Файлы:** `apps/web/package.json:11–12`; `.github/workflows/ci.yml:54`; `.gitlab-ci.yml:181–182`; `apps/web/prisma/migrations/`.

`postinstall`/`migrate` используют `prisma migrate deploy`, тогда как CI и GitLab deployment — `prisma db push`. В репозитории есть SQL-миграции. `db push` синхронизирует схему, но не заменяет выполнение миграционного SQL и backfill/constraints, отсутствующих в Prisma schema. Обычный `npm ci` также способен менять доступную через env БД из-за postinstall.

**Критерий закрытия:** единый документированный миграционный путь; создание пустой БД с нуля и обновление с предыдущего релиза; проверка кастомных индексов/ограничений/backfill; совместимость старого и нового приложения на время выкладки. Само наличие 102 migration.sql не доказывает, что они применяются в production.

### T10. Горизонтальное масштабирование realtime сейчас не обосновано — P1 перед вторым процессом

**Доказательность: архитектура кода; не утверждение о текущем production-инциденте.**

**Файлы:** `apps/web/server.ts:115,179,790–800`; `apps/web/src/lib/socketEmit.ts`; `ecosystem.config.cjs`; `apps/web/src/lib/rateLimit.ts`.

`voiceRooms`, пользователи сокетов и часть состояния живут в памяти процесса. Socket.IO создаётся без распределённого adapter; API emit использует локальный `globalThis.__socketio`. Redis применяется для других задач, но сам по себе не объединяет socket-комнаты.

При двух процессах пользователи одной группы могут оказаться на разных островах realtime, а API-запрос — на инстансе, где нет нужного сокета. Sticky sessions не делают общими карты комнат и состояния звонков.

**Критерий закрытия:** явно поддерживаемая single-instance topology либо проект распределения adapter + presence/voice/call ownership + revoke/permission invalidation. Для второго варианта — тест двух инстансов, перезапуска одного и недоступности Redis. Fail-open локов фоновых задач требует отдельной проверки идемпотентности, а не вывода, что все задачи обязательно дублируются.

### T11. Redis healthcheck не согласован с включением пароля — P2

**Доказательность: условие в конфигурации.**

**Файл:** `docker-compose.yml:39–45,114–115`.

Redis может стартовать с `--requirepass`, однако healthcheck всегда выполняет `redis-cli ping` без авторизации. При заданном пароле такой запрос не подтверждает `PONG`, а получает ошибку аутентификации. Приложение зависит от `service_healthy`.

**Важно:** будет ли контейнер помечен unhealthy или получится ложноположительный healthcheck, зависит от exit-кода используемой версии redis-cli. Это не проверялось запуском контейнера. Нельзя без проверки обещать один конкретный исход.

**Критерий закрытия:** проверить compose без пароля и с паролем; healthcheck должен подтвердить настоящий PONG, не раскрывая секрет в логах. Дополнительно проверить восстановление соединения после длительного отказа Redis и поведение `allkeys-lru` для счётчиков/локов.

### T12. Права вложений и запись индекса имеют окно несогласованности — P2, политика отзыва может поднять до P1

**Доказательность: код.**

**Файлы:** `apps/web/src/lib/uploadAccess.ts:37,56–83,96–106`; `apps/web/server.ts:29–33`.

Результат canAccessUpload кешируется на 60 секунд, явной инвалидации этого кеша при смене прав в просмотренном пути нет. После отзыва доступа ранее разрешённый файл может оставаться доступным по кешу до TTL. Это требует определения допустимого SLA отзыва.

`recordUpload` глушит ошибку записи строки владельца, хотя файл уже записан и отдан клиенту. При строгом режиме неизвестный файл затем закрыт. Итог: успешная загрузка в UI и недоступный файл после частичной ошибки БД. При отключённом strict эффект иной — ослабление контроля неизвестных файлов.

**Критерий закрытия:** failpoint на запись файла/индекса/offload; согласованное состояние «готов/обрабатывается/ошибка» и reconciliation; немедленный отзыв либо явно принятый TTL; Range/скачивание/удаление после отзыва.

### T13. TURN использует общий долгоживущий credential — P2, зависит от сетевых ограничений

**Доказательность: конфигурация и API.**

**Файлы:** `apps/web/src/app/api/voice/turn/route.ts:11–32`; `turnserver.conf`; `docker-compose.yml`, coturn.

Одинаковые env-credentials выдаются вошедшим пользователям и используются coturn. Хранение значения вне репозитория исправляет утечку из исходников, но пользователь всё равно получает credential для подключения. Отзыв учётной записи приложения не делает уже выданное общее значение индивидуально недействительным.

**Что проверить:** ограниченный lifetime, квоты, relay abuse, запрет приватных peer-адресов, изоляция по пользователю, UDP/TCP/TLS через реальные сети, разбор TURN_URL с query и отличающимися портами TLS/UDP. Взлом coturn здесь не воспроизводился.

**Критерий закрытия:** принята модель краткоживущих credentials/ротации и квот; сняты метрики relay/ошибок/стоимости; соединения проверены не только на одном локальном браузере.

### T14. Native bridge и разрешения требуют отдельного trust-boundary аудита — P1 перед расширением desktop-возможностей

**Доказательность: условный риск по коду, не подтверждённый RCE.**

**Файлы:** `apps/desktop/src/main/ipc.ts:28–105`; `apps/desktop/src/main/screenShare.ts:74–104`; `apps/desktop/src/main/mainWindow.ts:205–212,322+`; `apps/desktop/src/main/config.ts`; `apps/desktop/src/shared/navigation.ts`.

В основном окне включены contextIsolation, sandbox и выключен nodeIntegration — это хорошо. Но проверенные IPC handlers нередко игнорируют senderFrame, а media/clipboard-разрешения выдаются по имени permission без явной проверки origin в этих handlers. Доступный appUrl и дочерние окна увеличивают важность проверки доверенного отправителя.

Само наличие таких handlers не доказывает обход: важны preload, доступность bridge во фреймах, allowlist навигации и источник контента. Поэтому отдельный отчёт должен проследить полную цепочку renderer → preload → IPC → main → ОС.

**Критерий закрытия:** negative tests чужого origin/iframe/popup, проверка senderFrame для привилегированных операций, runtime-валидация аргументов, отсутствие shell-инъекций в VPN/путях/сохранении файлов, подпись обновлений и rollback. На Windows/macOS/Linux это проверяется отдельно.

## 3. Что остаётся от первого аудита

Не потерять в новом списке прежние открытые пункты:
- Конфликтующие целые снимки холста: нет гарантированной атомарной версии/CAS и безопасного merge/retry.
- Удаления/переименования/пустые холсты не полностью представлены в dirty-алгоритме; нужны правила конфликтов и операции/tombstones.
- Недостаточно строгая схема incoming состояния boards/cards/edges/view.
- IDB-кеш канала не разделён по пользователю, а fallback после 401/403 требует пересмотра.

Эти пункты остаются более важными для потери данных, чем косметические улучшения холста. Не следует объявлять всю синхронизацию исправной только потому, что камера больше не прыгает.

## 4. Что ещё нужно исследовать системно

### 4.1. Карта данных и доверия

Составить карту: browser/desktop/Android → proxy → web API/socket → PostgreSQL/Redis → файлы/S3/TURN/почта/VPN/агенты. Для каждого потока указать владельца, tenant, секреты, право чтения/записи, внешние запросы, retention и журнал аудита.

Важно отделить group roles, глобальные роли, роли проекта и tag roles. Нужна матрица «роль × действие × ресурс», а не поиск слова ADMIN по коду.

### 4.2. Целостность, идемпотентность и транзакции

Проверить повторную отправку сообщения после потери ответа, параллельную выдачу ролей, вступление по invite с лимитом, смену ответственного бизнес-чата, подтверждение платежей/счётов, публикацию отложенного сообщения. Для каждой команды определить idempotency key/уникальное ограничение и атомарную границу. Не считать Redis-лок заменой ограничения в БД.

### 4.3. Производительность и ресурсы

Нужны EXPLAIN ANALYZE для ленты сообщений, membership/role lookup, notification aggregation, больших списков каналов и uploadedFile. Измерить CPU/memory/event-loop lag, p95/p99 API, payload/частоту snapshots, время запуска desktop, число peer connections и upload-bitrate на участника. Синхронный JSON.stringify и криптографические операции исследовать профилировщиком, а не объявлять bottleneck по одному размеру файла.

### 4.4. Наблюдаемость и инциденты

В просмотренной конфигурации не установлена доказанная система метрик/трейсинга/алертов. Это не означает, что её нет снаружи приложения. Запросить фактическую схему мониторинга: correlation ID HTTP/socket/background job, error rate, reconnect, ICE failure, rejected saves, DB pool saturation, Redis fallback, failed uploads, очередь почты/уведомлений. Нужны SLO и понятное различие readiness/liveness.

### 4.5. Резервные копии и восстановление

В просмотренных scripts/CI не обнаружен подтверждённый runbook восстановления. Внешний backup-сервис мог быть настроен вне репозитория; проверить это у владельца инфраструктуры. Требуются RPO/RTO и проверенный restore PostgreSQL + private uploads + storage metadata + ключи шифрования. Отдельно — восстановление после потери ENCRYPTION_SECRET: fallback на NEXTAUTH_SECRET связывает ротацию auth-секрета с доступностью зашифрованной серверной конфигурации.

### 4.6. Поставка, зависимости и происхождение сборок

Проверить SCA/SBOM, лицензии, секреты в истории/архивах, pinned версии CI actions/base images, reproducible build, подпись installers/update feed, доступ на публикацию, downgrade/rollback. В этом этапе актуальная база CVE и npm audit не запускались: подтверждённого списка текущих уязвимых пакетов здесь нет.

### 4.7. Правила удаления и приватность

Установить единые правила soft delete/hard delete/export, удаления вложений, backups retention, аудита действий, очистки кеша и уведомлений после удаления. Удалённое из UI не обязательно удалено из файлового хранилища и резервных копий. Для E2EE отдельно проверить push, вложения, reply previews и server-side exports: шифрование текста не доказывает шифрование всей переписки.

## 5. Минимальная программа испытаний на стенде

| Направление | Сценарии | Что считать успешным |
|---|---|---|
| Доступ | Снять роль/тег, скрыть канал, исключить участника при открытой вкладке; повторить прямой API и socket | Данные и новые события недоступны по принятому SLA |
| Сессии | Logout одной/всех сессий, смена пароля, global/group ban, вторая вкладка, старый JWT | HTTP, файлы и socket отзываются согласованно |
| Совместная работа | 2–3 клиента, offline/online, задержка/перестановка/повтор событий, одновременно delete/edit | Нет молчаливой потери изменений; конфликты разрешаются по спецификации |
| Ключи | A/B на одном устройстве; lost device; import + отказ сервера; несовпадающая пара | Старый рабочий ключ не уничтожается ошибкой; изоляция аккаунтов сохраняется |
| Эфемерные чаты | Две вкладки/два устройства, закрыть только одно; partial cleanup failure | Семантика удаления соответствует продукту, нет неожиданного удаления чужой активной сессии |
| Внешние URL | Изолированный controlled DNS/redirect/slow body/IPv6 | Нет private-network SSRF и бесконечного ожидания тела |
| Вложения | БД падает после записи файла; отозвать права; Range; offload недоступен | Нет фиктивно успешных битых вложений и несанкционированной выдачи |
| Realtime | Два инстанса за балансировщиком; рестарт одного; Redis недоступен | Либо сценарий поддержан и проходит, либо конфигурация явно запрещена |
| БД/релиз | Пустая БД → релиз; предыдущий релиз → новый; restore из backup | Миграции воспроизводимы, данные и кастомные ограничения сохранены |
| Голос | Без микрофона, deny, unplug/replug, force mute, reconnect, TURN-only, разные NAT | Корректное состояние и доступ, работа звука/камеры/экрана |
| Native | Windows/macOS/Linux, права ОС, origin/iframe/popup, update/rollback | Нет доступа чужого контента к privileged bridge и неожиданных захватов |
| Нагрузка | Реалистичные сообщения/холсты/файлы/голос, slow clients | Соблюдены заранее согласованные latency/resource SLO |

## 6. Порядок дальнейшей работы — без автоматических исправлений

**Этап A: согласовать требования.** Семантика эфемерных чатов, recovery E2EE, SLA отзыва доступа, ожидаемая конкуренция на холсте, число одновременных процессов/пользователей, RPO/RTO.

**Этап B: зафиксировать доказательства.** Negative API integration tests для T01, изолированный SSRF/slow-upstream стенд T02/T03, failure-injection импорта T04, A/B key isolation T05, multi-tab secure lifecycle T07. Не проводить проверки инфраструктуры против production без отдельного согласования.

**Этап C: оценить и согласовать исправления.** Сначала доступ и сохранность данных; затем CI/миграции/recovery; далее масштабирование и производительность. Для каждого изменения отдельный план, миграционная совместимость и rollback.

**Этап D: приёмка.** Полный автоматический прогон, staging E2E, восстановление backup и release checklist. Не превращать общий список hardening в один большой неконтролируемый patch.

Нужные входные данные: фактическая схема деплоя и число процессов; версии PostgreSQL/Redis/coturn/proxy; обезличенные метрики и ошибки; целевые ОС/браузеры; требования к удалению и восстановлению; backup/runbook; нагрузочный профиль. Пароли и приватные ключи для подготовки плана не нужны.

## 7. Что нельзя переносить из старого CODE-REVIEW.md без перепроверки

В репозитории есть более раннее ревью. Часть его замечаний уже не описывает текущий код:
- Восстановление private screen share передаёт allow-list после voice-joined.
- Пустые attachments нормализуются проверкой длины массива.
- DM PATCH/DELETE повторно проверяют доступ и ban; удаление очищает attachments.
- Удаление ответа уменьшает threadCount в транзакции.
- Календарь валидирует даты и учитывает пересечение диапазонов, PATCH проверяет end/start.
- `sessionTokenFrom` уже вызывает `liveSession`, включая проверку passwordChangedAt. Нельзя объявлять Socket.IO полностью лишённым проверки отзыва сессий.

Их не нужно заново считать открытыми только на основании текста старого отчёта. Реальные оставшиеся вопросы могут находиться в соседних слоях — например, ACL самого календарного канала и многопроцессной инвалидации.
