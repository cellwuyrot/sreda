# TrustTunnel: экспериментальный локальный контур применения

Это рабочая наработка, **не инструкция для продакшена** и не готовый релиз. Функция пилота должна оставаться выключенной. Ниже описаны локально проверенные компоненты и их границы.

## Состав

- `scripts/trusttunnel-pilot-stage.py`: формирует закрытый каталог снимка. Нужен Node.js на машине подготовки; учётные данные и сопоставление администраторов содержат пароли. Скрипт не сверяет ID с реальной БД.
- `scripts/trusttunnel-pilot-apply.py`: экспериментальное локальное применение снимка на Endpoint, с предварительной сверкой файла и точных параметров systemd unit, локальной блокировкой, журналом, резервной копией, проверкой состояния службы и откатом. Перезапуск может прервать текущие соединения. Реальный unit и фактическое применение не подтверждены.
- `apps/vpn/src/trusttunnel_pilot_stage_verify.py` и `trusttunnel_pilot_gcm.py`: сверяют снимок и аутентифицируют AES-256-GCM через системную библиотеку `libcrypto.so.3`, без запуска Node.js на стороне проверки VDS. Если библиотека недоступна, проверка завершается отказом. Совместимость с конкретной VDS ещё не подтверждена. Исключения и содержимое снимков не выводятся.
- `apps/web/src/lib/trustTunnelPilotSecret.ts`: загрузка совмещённого ключа и контейнера из защищённого файла `TRIOZ_TT_PILOT_SECRET_FILE`; файл так же конфиденциален, как открытый пароль. Пути и разрешения проверяются; значения не печатаются. Файл ещё нужно безопасно доставить и привязать к рабочему процессу web.
- `scripts/trusttunnel-pilot-verify-secret.mjs`: локальная проверка такого файла на connect с помощью Node.js.
- `apps/desktop/src/shared/trustTunnelPilotProfile.ts`: проверка формата профиля Windows. Это не запуск клиента и не интеграция VPN.

## Важные ограничения

- Нет распределённой транзакции или безопасной доставки между VDS и connect. Флаг оператора об остановке выдачи сам по себе ничего не отключает и не доказывает отсутствие запросов в обработке. Перед применением необходим отдельно разработанный и проверенный протокол закрытия выдачи, ожидания завершения запросов, применения, доставки, сверки и открытия. Не использовать подготовленную операцию на живой системе до этого.
- Процесс systemd `active` не доказывает, что учётные данные приняты и туннель функционирует. Контрольный перезапуск не является тестом сетевого подключения.
- Локальная блокировка кооперативная: другие редакторы могут изменять файл вне неё. Каталог транзакций содержит старые пароли в открытом виде. Результаты восстановления при отключении питания и реальные права systemd необходимо проверить на совместимой тестовой среде.
- Права в приложении и allowlist ограничивают повторную выдачу профиля, но не отзывают пароль, уже полученный клиентом. Отзыв требует отдельно корректно обновить Endpoint; сохранённые копии тоже остаются секретами.
- Пилот доступен только администраторам проекта с ролью ADMIN и явно указанным ID. Администраторы групп не получают доступ только по признаку своей групповой роли.
- Gateway сейчас разрешает только подтверждённый IPv4 источника; произвольный мобильный адрес не пройдёт. Нельзя просто утверждать готовность подключения или открывать gateway всем без отдельного плана защиты. Firewall Endpoint и существующая Amnezia-конфигурация не изменены.
- Windows-сервис/IPC/интерфейс TrustTunnel не реализованы; Electron-пакет и фактический механизм обновления на Windows не проверены. Нельзя выпускать приложение на основе этого снимка.

## Проверки на фиктивных данных

В среде разработки: 51 Python unit-тест сценариев подготовки и локальной транзакции; 4 Node-теста упаковки и совместимости. Тесты не подключались к серверам и не подтверждают реальную работу VPN. Проверка Android debug, лицензия SDK и её ограничения описаны в `TRUSTTUNNEL-ANDROID-SERVICE-WIP.md`. Граф codebase-memory необходимо переиндексировать в реальном репозитории.
