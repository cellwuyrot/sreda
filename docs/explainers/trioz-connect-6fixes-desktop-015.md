# TZ Connect — фикс-пакет из 6 багов + десктоп 0.1.5

> **TL;DR.** Разделы главного сообщества снова строго повторяют список услуг из
> админки; выход из админки ведёт в `/connect`; примитивные системные окна
> (`confirm`/`alert`) заменены фирменной модалкой; тёмные выпадающие списки стали
> читаемыми; исправлено задвоение личных сообщений; композер ЛС теперь идентичен
> групповому (с сохранением E2EE). Версия десктоп-приложения поднята до **0.1.5**.

---

## Background

### Для тех, кто видит проект впервые

**TZ Connect** — это Discord-подобная коммуникационная платформа. Технически это
монорепозиторий (`npm workspaces`) из трёх частей:

- `apps/web` — основное Next.js-приложение (App Router, React, Tailwind, Prisma,
  Socket.IO). Здесь живёт вся логика: страницы, API-маршруты (`src/app/api/**`),
  React-компоненты (`src/components/**`).
- `apps/desktop` — тонкая Electron-обёртка, которая просто открывает то же
  веб-приложение в окне. Своего UI у неё почти нет; когда веб-страница вызывает
  `window.confirm()`, Electron рисует **нативное** окно ОС (то самое серое окошко
  из скриншота).
- `packages/shared` — общий контракт Socket.IO-событий.

Несколько понятий, которые понадобятся ниже:

> **Группа (Group)** — сообщество. У каждой группы есть каналы (`Channel`).
> **Главное сообщество** — единственная группа с флагом `isMain = true`
> («TZ Connect»), в которую автоматически попадают все пользователи.
>
> **Услуга (Service)** — запись в админском справочнике «Управление услугами»
> (`/admin/services`): заголовок, описание, иконка, порядок, флаг активности.
>
> **Раздел («Разделы»)** — правая колонка в главном сообществе
> (`SectionsPanel.tsx`). Каждый «раздел» — это верхнеуровневый текстовый канал.

### Узкий контекст: как услуги превращаются в разделы

Разделы главного сообщества не заводятся руками — они **синхронизируются** из
услуг функцией `syncServicesToMainCommunity()` (`apps/web/src/lib/mainCommunity.ts`).
На каждую услугу заводится ровно три канала:

```
"{Услуга}"                — NEWS-канал (шапка/лента раздела)
"{Услуга} — Обсуждение"   — TEXT
"{Услуга} — Вопросы"      — TEXT
```

`SectionsPanel` группирует их по общему префиксу до « — », поэтому в UI это
выглядит как один раздел с двумя под-каналами. `ChannelSidebar` группирует те же
каналы по `serviceId`.

Личные сообщения (ЛС) — отдельная подсистема (`apps/web/src/components/dm/**`) со
своим списком сообщений, композером (`DMMessageComposer`) и сквозным шифрованием
(E2EE): текст шифруется на клиенте ключом собеседника и хранится/передаётся уже
зашифрованным.

## Intuition

Шесть проблем независимы, поэтому проще разобрать каждую на «игрушечном» примере.

### 1. Разделы ≠ услуги

Старая синхронизация была «однократной»: при создании услуги каналы заводились,
но **при переименовании услуги каналы не переименовывались** — обновлялся только
флаг «скрыт/показан». Плюс сортировка разделов была алфавитной, а не по порядку
услуг. Итог: админ переименовал «CRM Интеграция» → «CRM 2.0», а в сообществе всё
ещё висит «CRM Интеграция», да ещё и не на своём месте.

Интуиция фикса: сделать синхронизацию **авторитетной** — на каждом прогоне
привести имя, иконку, порядок и видимость каналов в точное соответствие с
услугой, дозавести пропавшие каналы и удалить лишние. И запускать её не только
по действию админа, а ещё и при загрузке списка групп — тогда состояние
«само-лечится».

> **Игрушечный пример.** Услуги: `[Знак(order 1), CRM(order 2)]`. Прогон
> синхронизации проставит каналам `sortOrder`: `Знак`→10/11/12, `CRM`→20/21/22.
> Переименовали `CRM`→`CRM 2.0` — следующий прогон найдёт TEXT-канал,
> оканчивающийся на «Вопросы», и переименует его в «CRM 2.0 — Вопросы», не
> плодя дубликат.

### 2. Выход из админки

Кнопка «назад» в шапке админки вела на `/` (лендинг). Достаточно поменять цель
ссылки на `/connect`.

### 3. Примитивные окна

`confirm("Удалить статью?")` рисует нативное окно ОС. Идея: один раз написать
красивую модалку и дать императивную функцию `confirmDialog()`, возвращающую
`Promise<boolean>`, чтобы менять вызовы точечно:

```ts
if (!confirm("Удалить?")) return;              // было
if (!(await confirmDialog("Удалить?"))) return; // стало
```

### 4. Белый выпадающий список

Нативный `<select>` в тёмной теме открывал белый список с белым текстом. Лечится
CSS-свойством `color-scheme: dark`, которое переключает нативный контрол (включая
всплывающий список) в тёмную палитру.

### 5. Задвоение ЛС

Классическая гонка «оптимистичного» рендера и сокета. Клиент рисует сообщение
сразу (`opt-…`), а сервер, сохранив, шлёт это же сообщение обратно **и
отправителю**. Если сокет-эхо приходит раньше ответа на POST, дедуп по `id` не
срабатывает (у оптимистичного другой `id`) — и сообщение оказывается в списке
дважды. В групповом чате это уже решено «заменой плейсхолдера»; в ЛС — нет.

### 6. Композер ЛС ≠ групповой

Композер ЛС был построен иначе, чем групповой (другая вёрстка, иконки, поведение).
Идея: переписать `DMMessageComposer` так, чтобы он повторял разметку и поведение
группового композера из `MessageArea.tsx`, оставив уникальным только индикатор
E2EE.

## Code

### Задача 1 — синхронизация «Разделы ↔ Услуги»

`apps/web/src/lib/mainCommunity.ts` — `syncServicesToMainCommunity()` переписана
как **идемпотентная авторитетная** сверка. Каналы одной услуги определяются по
роли (NEWS — по типу; «Вопросы»/«Обсуждение» — по стабильному суффиксу), после
чего имя/иконка/тип/видимость/порядок приводятся к текущей услуге; недостающие
создаются, лишние — удаляются:

```ts
const news = existing.find((c) => c.type === "NEWS");
const questions = existing.find((c) => c !== news && c.name.endsWith("Вопросы"));
const discussion = existing.find((c) => c !== news && c !== questions);

const desired = [
  { role: news,       name: service.title,                       type: "NEWS", icon: service.icon || NEWS_ICON, sortOrder: base },
  { role: discussion, name: `${service.title} — Обсуждение`,      type: "TEXT", icon: DISCUSSION_ICON,           sortOrder: base + 1 },
  { role: questions,  name: `${service.title} — Вопросы`,         type: "TEXT", icon: QUESTIONS_ICON,            sortOrder: base + 2 },
];
// для каждого: нет роли → create(); есть и что-то «поехало» → update();
```

`apps/web/src/app/api/groups/route.ts` (GET) — добавлен само-лечащий вызов после
`ensureMainCommunity()`/`autoJoinMainCommunity()`:

```ts
await syncServicesToMainCommunity().catch(() => {});
```

`SectionsPanel.tsx` — сортировка разделов теперь учитывает `sortOrder`
(унаследованный от порядка услуг), а алфавит — лишь запасной вариант:

```ts
.sort((a, b) => {
  const so = (a.sortOrder ?? 0) - (b.sortOrder ?? 0);
  return so !== 0 ? so : a.name.localeCompare(b.name, "ru");
});
```

Поле `sortOrder?: number` добавлено в типы `Channel` (`sidebarTypes.ts`,
`groupTypes.ts`).

### Задача 3 — фирменные модалки вместо `confirm`/`alert`

Новый модуль `apps/web/src/components/ui/ConfirmDialog.tsx` даёт императивный API
и хост, который монтируется один раз в `Providers.tsx`:

```ts
export function confirmDialog(opts: string | ConfirmOptions): Promise<boolean>;
export function alertDialog(opts: string | ConfirmOptions): Promise<void>;
export function ConfirmDialogHost(): JSX.Element | null;
```

Хост рендерит тёмную карточку с бэкдропом, поддерживает Enter/Escape и авто-фокус
на основной кнопке. Если хост ещё не смонтирован (SSR), происходит откат на
нативный диалог. Заменены **все 13 `confirm()` и 2 `alert()`** в вики, задачах,
файлах, календаре, инвайтах, админке, настройках, играх и экране входа.

### Задача 4 — читаемые `<select>` в тёмной теме

`apps/web/src/app/globals.css`:

```css
.dark select { color-scheme: dark; }
.dark select option,
.dark select optgroup { background-color: #14141c; color: #e8eaf0; }
```

### Задача 5 — задвоение ЛС

`apps/web/src/components/dm/DMPanel.tsx`, обработчик `dm-message` — вместо
слепого добавления теперь **замена оптимистичного плейсхолдера** (как в группах):

```ts
if (prev.some((m) => m.id === msg.id)) return prev;
if (msg.userId === currentUserId) {
  const i = prev.findIndex((m) => m.id.startsWith("opt-") && m.userId === currentUserId);
  if (i !== -1) { const next = [...prev]; next[i] = { ...msg, status: "sent" }; return next; }
}
return [...prev, msg];
```

### Задача 6 — композер ЛС = групповой

`apps/web/src/components/dm/DMMessageComposer.tsx` переписан по образцу композера
`MessageArea.tsx`: та же скруглённая «оболочка» с `focus-within`-кольцом, та же
скрепка/геолокация/тумблер форматирования, тот же авто-растущий `textarea`
(`input-field`) и кнопка отправки (`btn-primary`) либо голосовая запись. Props
не изменились, поэтому `DMPanel` править не пришлось. Уникальным оставлен лишь
индикатор **E2EE** в панели форматирования.

### Десктоп 0.1.5

`apps/desktop/package.json`: `version` `0.1.4` → `0.1.5` (electron-updater
раздаст обновление). Отдельного кода под задачу 3 в десктопе не нужно — нативные
окна исчезли вместе с `window.confirm()` на веб-стороне.

**Ручная проверка (для QA после деплоя):**

1. **Разделы = услуги.** Админка → «Управление услугами»: переименуйте услугу,
   поменяйте иконку, порядок, отключите одну. Откройте «TZ Connect»: разделы
   справа повторяют список услуг — имена, иконки, порядок; отключённая услуга
   скрыта у обычного пользователя и видна у админа.
2. **Выход из админки.** В админке нажмите стрелку «назад» → попадаете в
   `/connect`, а не на лендинг.
3. **Модалки.** В десктоп-версии удалите статью в Вики (и задачу/файл/событие) —
   вместо серого окна ОС появляется тёмная фирменная модалка; Enter
   подтверждает, Escape отменяет.
4. **Выпадающие списки.** Настройки → «Конфиденциальность»: раскройте
   «Кто видит мой онлайн-статус» — пункты читаемы (тёмный фон, светлый текст).
5. **ЛС без дублей.** Откройте диалог, отправьте несколько сообщений подряд (в
   т.ч. в защищённом режиме) — каждое появляется ровно один раз.
6. **Композер ЛС.** Сравните поле ввода в ЛС и в канале группы: скрепка,
   геолокация, форматирование, авто-рост, голос — идентичны; в ЛS дополнительно
   виден бейдж E2EE.

## Alternatives

### Задача 1 — где держать «источник правды» для разделов

| Выбранный подход: авторитетная синхронизация услуг → каналы | Альтернатива: рендерить разделы напрямую из `Service` |
| --- | --- |
| **+** Разделы остаются обычными каналами: работают чат, права, вложения, задачи | **+** Ноль рассинхронизации по определению |
| **+** Минимальные изменения UI (панель уже умеет каналы) | **+** Не нужны три канала на услугу |
| **−** Требуется аккуратная сверка (сделана идемпотентной) | **−** Большой рефактор `SectionsPanel`/`ChannelSidebar`/сообщений |
| **−** Само-лечение стоит пары SELECT-ов на загрузку списка групп | **−** Каналы-услуги теряют «настоящесть» (нет истории/прав) |

### Задача 3 — как заменить `confirm()`

| Выбранный подход: императивный `confirmDialog()` + хост | Альтернатива: React-контекст `useConfirm()` |
| --- | --- |
| **+** Точечная замена: `confirm(x)` → `await confirmDialog(x)` | **+** «Каноничный» React без модульного синглтона |
| **+** Работает и вне компонентов | **−** Требует хук в каждом компоненте и проброс |
| **−** Модульный слушатель-синглтон | **−** Больше правок на каждом call-site |

- **A.** Разделы кешировались в localStorage.
- **B. ✅** Старая синхронизация на существующих каналах обновляла только
  `isRestricted`, но не `name`/`icon`/`sortOrder`, поэтому переименование услуги
  не доходило до каналов.
- **C.** `SectionsPanel` фильтровал каналы услуг.
- **D.** Услуги и каналы хранятся в разных БД.

Верно **B**: правки распространялись лишь на флаг видимости. Теперь сверка
авторитетная и приводит все поля к текущей услуге.
