# Группировка уведомлений и исчезновение прочитанного

Про два бага, которые видно на живом мессенджере: пять сообщений подряд из
одного чата давали пять уведомлений и «5» в колокольчике, а прочтение одного из
них не гасило остальные из того же чата. Читать перед правками в
`lib/createNotification.ts`, `api/notifications`, `api/dm/read`, `api/messages`
и в колокольчиках (`components/ui/Navbar.tsx`,
`components/mobile/MobileNotificationBell.tsx`,
`app/settings/notifications/page.tsx`).

Это продолжение истории из `notifications.md` (предмет уведомления `actorId` +
`entityType`/`entityId`). Тот документ объяснял, *почему прочитанное не
пропадало*; этот — *почему уведомления не группировались и почему бейдж
«залипал»*.

## Background

### Для тех, кто видит систему впервые

Уведомление в TZ.Connect — это строка в таблице `Notification`: кому (`userId`),
какого вида (`type`: `dm`, `mention`, `appeal`…), заголовок, текст, ссылка и флаг
`read`. Рождаются они в **одном месте** — `lib/createNotification.ts`
(`createNotification` для одного получателя, `createNotificationsBulk` для
рассылки). Оттуда уведомление идёт тремя путями сразу:

1. **В базу** — чтобы жить в истории (страница `/settings/notifications`).
2. **По Socket.IO** событием `new-notification` в персональную комнату
   `dm-<userId>` — чтобы живой клиент мгновенно поднял счётчик и показал тост.
3. **В службу доставки телефона** (`lib/push.ts`) — чтобы догнать человека в
   закрытом приложении.

Красную цифру у колокольчика (бейдж) держат два компонента: `Navbar` на десктопе
и `MobileNotificationBell` на телефоне. Оба при старте спрашивают у сервера
`GET /api/notifications?unread=true` (получают `unreadCount`), а дальше живут на
событиях: `new-notification` увеличивает счётчик, а `tz-notifications-read`
(DOM-событие внутри вкладки) и пересинхронизация по фокусу его выравнивают.

> [!NOTE]
> **Предмет уведомления.** У записи есть `entityType` + `entityId` — «о чём» она:
> `dm:<id разговора>`, `channel:<id канала>`, `appeal:<id заявки>`. По предмету
> уведомления точно гасят (`markSubjectNotificationsRead`) и убирают
> (`deleteSubjectNotifications`), не гадая по тексту ссылки. Это фундамент, на
> котором стоит вся эта правка.

### Узко про баги

Хотя предмет уже существовал, `createNotification` **всегда делал `INSERT`**.
Значит, каждое личное сообщение — отдельная строка. Пришло пять сообщений подряд
от одного человека — пять строк, `unreadCount = 5`, пять пунктов в центре
уведомлений. Никакой группировки: она есть только у нативного пуша (по метке
`tag`), но не в самом журнале и не в бейдже.

Второй баг — прямое следствие первого плюс дыра в синхронизации:

* В центре уведомлений клик по записи звал `markRead(id)`, который помечал
  прочитанной **ровно одну** строку. Остальные четыре из того же чата оставались
  непрочитанными.
* А `POST /api/dm/read` (его зовёт панель ЛС при открытии разговора) хоть и гасил
  в базе все уведомления беседы по предмету, **не сообщал об этом колокольчику**:
  возвращал `{ ok: true }` без остатка непрочитанного и не рассылал
  `tz-notifications-read`. Бейдж узнавал правду только при следующем фокусе
  вкладки. Отсюда ощущение «прочитал, перешёл — а непрочитанное висит».

Показательно: у обращений (`api/appeals/[id]`) эта связка **уже была** — GET
заявки возвращал `unreadLeft`, а `AppealsPanel` рассылал `tz-notifications-read`.
У личных сообщений её просто забыли протянуть.

## Intuition

Ядро идеи — **одна беседа = одно живое уведомление**. Пока по предмету висит
непрочитанное, новое событие не создаёт вторую строку, а обновляет первую:
поднимает счётчик схлопнутого (`count`), перетирает заголовок/текст/ссылку на
свежие и всплывает наверх ленты (`createdAt = now`). Прочитал — строка «закрыта»;
следующее сообщение начнёт новую.

Крохотный пример. Андрей пишет Борису три раза подряд:

```
t0  msg#1 → нет непрочитанного по conv-1 → INSERT  (count=1, read=false)  бейдж +1 = 1
t1  msg#2 → есть непрочитанное по conv-1 → UPDATE   (count=2)              бейдж = 1
t2  msg#3 → есть непрочитанное по conv-1 → UPDATE   (count=3)              бейдж = 1
```

Борис видит **одно** уведомление «Новое сообщение от Андрея · 3 новых» и цифру
**1**, а не 3. Он открывает чат:

```
POST /api/dm/read → гасит conv-1 по предмету → unreadLeft=0
                  → dispatch tz-notifications-read {unreadCount: 0}
бейдж = 0   (сразу, не дожидаясь фокуса вкладки)
```

Чтобы бейдж не рос на «обновление», сервер помечает событие флагом:

> [!IMPORTANT]
> **`isNew`** в событии `new-notification` — это «появилась ли НОВАЯ строка в
> журнале». `true` — счётчик колокольчика растёт; `false` (сгруппировали) — нет.
> Без этого флага пять сообщений подряд снова накрутили бы бейдж до 5, даже при
> одной строке в базе.

## Code

### 1. Схема: счётчик схлопнутого

`prisma/schema.prisma` + идемпотентная миграция
`20260914000000_notification_group_count`:

```prisma
model Notification {
  // …
  entityType String? @db.VarChar(32)
  entityId   String?
  count      Int      @default(1)   // сколько событий схлопнуто в это уведомление
  createdAt  DateTime @default(now())
}
```

### 2. Группировка в единственной точке рождения уведомлений

`lib/createNotification.ts`. Если задан предмет — сначала ищем своё непрочитанное
уведомление того же вида и о том же предмете; нашли — обновляем, нет — создаём:

```ts
let notification: Awaited<ReturnType<typeof prisma.notification.create>> | undefined;
let isNew = true;
if (params.entityType && params.entityId) {
  const existing = await prisma.notification.findFirst({
    where: { userId: params.userId, type: params.type,
             entityType: params.entityType, entityId: params.entityId, read: false },
    select: { id: true },
    orderBy: { createdAt: "desc" },
  });
  if (existing) {
    notification = await prisma.notification.update({
      where: { id: existing.id },
      data: { title: params.title, body: params.body, link: params.link, actorId,
              count: { increment: 1 }, createdAt: new Date() },
    });
    isNew = false;
  }
}
if (!notification) {
  notification = await prisma.notification.create({ /* …как раньше… */ });
}

io?.to(`dm-${params.userId}`).emit(SOCKET_EVENTS.NEW_NOTIFICATION, { ...notification, pushEnabled, isNew });
```

`createNotificationsBulk` (рассылка `@everyone`/из админки) всегда вставляет
новые строки — там `isNew: true`. Ключ группировки — `userId + type + предмет`,
поэтому личное сообщение и ответ по обращению об одной сущности не схлопнутся, а
чужие записи не тронутся.

### 3. Бейдж уважает `isNew`

`components/ui/Navbar.tsx` и `components/mobile/MobileNotificationBell.tsx`:

```ts
socket.on("new-notification", (payload?: { isNew?: boolean }) => {
  if (payload?.isNew === false) return; // сгруппировано — новой строки нет
  setUnread((c) => c + 1);
});
```

### 4. Открытие чата гасит бейдж сразу

`api/dm/read` теперь возвращает остаток непрочитанного, а панель ЛС рассылает то
же событие, что и страница уведомлений с обращениями:

```ts
// api/dm/read/route.ts
const read = await markSubjectNotificationsRead({ userId, entityType: "dm", entityId: conversationId, legacyWhere });
return NextResponse.json({ ok: true, unreadLeft: read.unreadLeft });
```

```ts
// components/dm/DMPanel.tsx — общий помощник для двух точек (открытие чата и live-сообщение)
const markConversationRead = useCallback((convId: string) => {
  fetch("/api/dm/read", { method: "POST", /* … */ body: JSON.stringify({ conversationId: convId }) })
    .then((r) => (r.ok ? r.json() : null))
    .then((d) => {
      if (d && typeof d.unreadLeft === "number")
        window.dispatchEvent(new CustomEvent("tz-notifications-read", { detail: { unreadCount: Math.max(0, d.unreadLeft) } }));
    })
    .catch(() => {});
}, []);
```

### 5. Клик в центре гасит всю беседу

`api/notifications` (PATCH) научился помечать по предмету и возвращать свежий
`unreadCount`; страница `/settings/notifications` при клике шлёт предмет
уведомления (а не только `id`) и гасит соседей из того же чата в локальном
состоянии, а остаток берёт у сервера. В списке у непрочитанного показывается
«N новых», когда `count > 1`.

### 6. Каналы — за компанию

Адресные упоминания и `@everyone` теперь несут предмет `channel:<id>`, поэтому
повторные упоминания группируются, а очистка при открытии канала (`api/messages`
GET) гасит их и по предмету (ветка по тексту ссылки осталась для старых записей).

**Ручная проверка (QA).**

1. Попросите второй аккаунт прислать вам 3–4 сообщения подряд в ЛС, приложение
   держите свёрнутым/на другом разделе. Ожидание: в колокольчике **+1** (а не
   +4), в центре уведомлений — одна запись «Новое сообщение от … · N новых».
2. Откройте этот чат из уведомления. Ожидание: бейдж гаснет **сразу**, все
   уведомления этого чата стали прочитанными.
3. Повторите, но вместо перехода нажмите на уведомление в
   `/settings/notifications`. Ожидание: гаснет вся беседа, счётчик обновляется
   числом с сервера.
4. Проверьте, что сообщения из **разных** чатов по-прежнему дают разные
   уведомления и суммируются в бейдже.
5. Прочитайте чат, затем получите ещё сообщение. Ожидание: появляется **новое**
   уведомление (счётчик снова +1), а не обновляется прочитанное.

## Alternatives

**А. Группировать на клиенте (по `entityId`), не трогая базу.**

| За | Против |
|---|---|
| Без миграции и без изменения сервера | Бейдж по-прежнему считает строки — «5» вместо «1», а его правят два компонента и десктоп-оболочка |
| Меньше кода на бэкенде | Пуш и запись в журнале остаются разрозненными; группировка живёт только там, где её нарисовали |
| | Логика группировки дублируется в каждом клиенте и неизбежно разъезжается |

**Б. Отдельная таблица «тредов уведомлений» (заголовок + счётчик + связь на события).**

| За | Против |
|---|---|
| Честная модель «беседа → много событий» | Заметно больше схемы, миграций и запросов ради двух багов |
| Легко показывать историю схлопнутого | Переусложнение: `count` на существующей строке закрывает задачу |

Выбран путь «обновляем строку по предмету + `count` + `isNew`»: правка в
единственной точке рождения уведомлений, а бейдж, центр, пуш и десктоп получают
согласованную картину без дублирования логики.

## Quiz

<details>
<summary>1. Почему бейдж не растёт на второе сообщение из того же чата?</summary>

- **A.** Клиент дедуплицирует события по `entityId`. — Нет, клиент так не делает.
- **B. Сервер группирует запись (не создаёт новую строку) и шлёт `isNew=false`, а колокольчик по нему не увеличивает счётчик.** — Верно: группировка в `createNotification`, флаг `isNew` в событии.
- **C. `/api/notifications` перестал считать непрочитанные.** — Нет, считает как прежде.
- **D. Второе сообщение не создаёт уведомления вовсе.** — Неверно: уведомление есть, просто это то же самое, с `count+1`.
</details>

<details>
<summary>2. Что именно возвращать стал `POST /api/dm/read` и зачем?</summary>

- **A. `unreadLeft` — остаток непрочитанного, чтобы панель ЛС сразу выровняла бейдж через `tz-notifications-read`.** — Верно.
- **B.** Список прочитанных id. — Нет.
- **C.** Ничего нового, поменялся только клиент. — Неверно: раньше был `{ ok: true }` без остатка.
- **D.** Полный счётчик по всем разделам. — Нет, только непрочитанные уведомления пользователя.
</details>

<details>
<summary>3. По какому ключу ищется «уже висящее» уведомление для группировки?</summary>

- **A.** Только `entityId`. — Недостаточно: схлопнулись бы разные виды и чужие записи.
- **B.** `userId + link`. — Нет, от догадок по ссылке как раз ушли.
- **C. `userId + type + entityType + entityId + read=false`.** — Верно.
- **D.** `userId + read=false`. — Слишком широко: слились бы все беседы в одну.
</details>

<details>
<summary>4. Почему прочитанные уведомления не участвуют в группировке?</summary>

- **A.** Так быстрее запрос. — Не в этом суть.
- **B. Человек их уже видел; новое событие обязано снова зажечь бейдж, поэтому создаётся новая строка (`read=false`, `count=1`).** — Верно.
- **C.** Прочитанные удаляются сразу. — Нет, остаются в истории.
- **D.** Prisma не умеет обновлять `read`-строки. — Неверно.
</details>

<details>
<summary>5. Зачем `createNotificationsBulk` жёстко ставит `isNew: true`?</summary>

- **A.** Рассылка всегда делает `INSERT` (по строке на получателя), и у каждого счётчик должен вырасти — в отличие от сгруппированного обновления одиночного пути.** — Верно.
- **B.** Чтобы отключить пуш в рассылке. — Нет, пуш управляется отдельно (`pushEnabled`).
- **C.** Bulk тоже группирует, и флаг это подавляет. — Неверно: bulk не группирует.
- **D.** Это косметика, флаг ни на что не влияет. — Неверно: по нему колокольчик решает, растить ли бейдж.
</details>
