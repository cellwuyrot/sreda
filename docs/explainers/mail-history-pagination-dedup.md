# Почта админки: история ящика вместо десяти последних писем

Раздел «Сервисы и система → Email и обработка данных» показывал почту девяти
ящиков домена. Показывал ровно десять писем на ящик — и ни одного больше,
никогда. При этом список ящиков украшали значки `↓ 7 ↑ 3`, которые росли от
нажатий на ящик, будто интерфейс считал не письма, а щелчки мыши.

Разберёмся, почему так вышло, и как одна сломанная строка дедупликации
превратилась в «счётчик по нажатию».

## Background

### Для начала: как почта попадает в админку

Пропустите этот раздел, если уже работали с почтовым разделом.

Ящики домена (`info@trioz.ru`, `sales@`, `support@`, ещё шесть) созданы на
хостинге руками. Приложение их не создаёт — оно только знает их список:
`apps/web/src/lib/projectMail.ts`, константа `PROJECT_MAILBOXES`. Список
захардкожен намеренно: адрес, которого нет на почтовом сервере, в интерфейсе
только вводил бы в заблуждение.

Письма попадают в базу двумя путями:

| Путь | Кто инициирует | Файл |
|------|----------------|------|
| **IMAP-опрос** — приложение само заходит в ящик и читает INBOX | кнопка «Проверить почту» или cron | `api/mail/poll/route.ts` → `lib/mailImap.ts` |
| **Вебхук** — почтовый сервис сам присылает письмо | внешний сервис `acoulbot/smtp` | `api/mail/ingest/route.ts` |

Оба пути пишут в таблицу `MailMessage`: направление (`incoming`/`outgoing`),
адреса, тему, предпросмотр, тело, `messageId` и `sentAt`. Исходящие письма
добавляет туда же роут отправки. Экран `/admin/mail` читает эту таблицу
через `GET /api/admin/mail/[address]`.

> [!NOTE]
> **Message-ID** — заголовок письма из RFC 5322, уникальный идентификатор,
> который присваивает отправляющий сервер. Выглядит как `<abc123@example.com>`.
> Именно по нему принято отличать «то же письмо» от «похожего письма»: если
> опрос ящика повторился, письмо с уже известным Message-ID записывать не нужно.
> Заголовок формально обязателен, но на практике его не присылают рассылочные
> движки и часть корпоративных релеев.

### Теперь ближе: три решения, которые дали сбой

**Первое.** Одна константа отвечала за два разных вопроса:

```ts
/** Сколько писем показываем в листинге по каждому направлению. */
export const MAIL_LISTING_LIMIT = 10;
```

Её читал листинг (`take: MAIL_LISTING_LIMIT`) — и она же была окном чтения
INBOX в `fetchRecent(localPart, limit = MAIL_LISTING_LIMIT)`. То есть из ящика
в базу попадало десять писем, и эти же десять показывались. Сколько бы писем
ни лежало на сервере, история приложения начиналась и заканчивалась десятком.

**Второе.** Дедупликация стояла под условием:

```ts
if (msg.messageId) {
  const dup = await prisma.mailMessage.findUnique({ where: { messageId: msg.messageId } });
  if (dup) continue;
}
await prisma.mailMessage.create({ /* … */ });
```

Нет заголовка — нет проверки. Письмо создаётся заново при каждом опросе.

**Третье.** Опрос запускался сам:

```ts
const loadRows = useCallback(async (localPart, which, sync = which === "incoming") => {
  if (sync) await syncIncoming(localPart);
  /* … */
});
```

Значение `sync` по умолчанию — «да, если смотрим входящие». А `loadRows`
вызывался при выборе ящика, при переключении вкладок и каждые 30 секунд по
таймеру.

Сложите три решения вместе. Клик по ящику → IMAP-опрос → письма без Message-ID
записываются повторно → в базе копии → `groupBy` в сводке считает их все →
значок `↓ 7` становится `↓ 8`. Счётчик действительно реагировал на нажатие —
только считал он не письма, а число проверок почты.

## Intuition

Основная мысль правки: **разделить то, что было склеено**, и **дать письму
ключ, который всегда есть**.

### Разделить окно чтения и размер страницы

Это два разных числа с разной природой. Сколько писем показать за раз — вопрос
интерфейса (25). Сколько писем забрать из INBOX за один опрос — вопрос почтового
сервера (100). Если второе меньше первого, листать нечего:

```
INBOX: 137 писем
                 ┌── было: окно = 10 ──┐
[.....................................|▓▓▓▓▓▓▓▓▓▓]
                                        в базе 10 → страница 10 → конец истории

                 ┌── стало: окно = 100 ─────────────┐
[.....................|▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓]
                       в базе 100 → страницы 25+25+25+25 → «Показать ещё»
```

### Дать письму ключ, который всегда есть

Если Message-ID не пришёл, посчитаем его сами — от полей, которые у одного и
того же письма не меняются между опросами: ящик, отправитель, тема, дата, тело.

Возьмём письмо и опросим ящик трижды:

```
Письмо: info | client@x.ru | «Вопрос по счёту» | 2026-09-11T09:00:00Z | «Здравствуйте»

было:   опрос 1 → messageId = null → пишем    (в базе 1 копия)
        опрос 2 → messageId = null → пишем    (в базе 2 копии)
        опрос 3 → messageId = null → пишем    (в базе 3 копии)

стало:  опрос 1 → synthetic:8e2d37d0… → пишем       (в базе 1)
        опрос 2 → synthetic:8e2d37d0… → уже есть    (в базе 1)
        опрос 3 → synthetic:8e2d37d0… → уже есть    (в базе 1)
```

Ключ узнаваем по префиксу `synthetic:` — в базе видно, что это наш ключ, а не
заголовок письма.

### Сузить область уникальности

Осталась тонкость. Уникальность `messageId` была объявлена на всю таблицу:

```prisma
messageId String? @unique
```

Письмо, адресованное двум ящикам домена (`To: info@`, `Cc: sales@`), приходит в
оба ящика с одним и тем же Message-ID. Глобальный индекс пускал первую запись и
отвергал вторую — письмо навсегда пропадало из истории второго ящика. Правильная
область уникальности здесь — пара «ящик + письмо»:

```prisma
@@unique([mailboxId, messageId])
```

> [!IMPORTANT]
> Уникальный индекс — не только защита от дублей, но и разметка того, что
> считается «одной и той же сущностью». Глобальный индекс говорил: «письмо —
> это письмо». Реальность раздела: «письмо — это письмо *в ящике*».

## Code

### 1. Константы: одно число вместо двух ролей

`lib/projectMail.ts`

```ts
/** Размер страницы листинга по умолчанию. */
export const MAIL_PAGE_SIZE = 25;

/** Потолок размера страницы: в строке листинга едет ещё и preview. */
export const MAIL_PAGE_SIZE_MAX = 100;

/** Сколько последних писем ящика читаем из INBOX за один опрос. */
export const MAIL_IMAP_FETCH_LIMIT = 100;
```

`MAIL_LISTING_LIMIT` удалена — именно её двойная роль и была ловушкой.

### 2. Ключ дедупликации

`lib/projectMail.ts`

```ts
export function syntheticMessageId(parts: {
  localPart: string;
  fromAddr: string;
  subject: string;
  sentAt: Date;
  bodyText: string;
}): string {
  const material = [
    parts.localPart,
    parts.fromAddr,
    parts.subject,
    parts.sentAt.toISOString(),
    parts.bodyText,
  ].join("\u0000");
  return `synthetic:${createHash("sha256").update(material, "utf8").digest("hex")}`;
}
```

Разделитель между полями обязателен: без него `fromAddr: "ab", subject: "c"`
и `fromAddr: "a", subject: "bc"` дали бы один ключ. Для этого есть отдельный
тест.

`lib/mailNormalize.ts` — тип стал строже, `messageId` больше не `null`:

```ts
messageId: parsed.messageId
  ? String(parsed.messageId).slice(0, 400)
  : syntheticMessageId({ localPart: fallbackTo.split("@")[0], fromAddr, subject, sentAt, bodyText }),
```

### 3. Запись письма: дедуп в пределах ящика и терпимость к гонке

`api/mail/poll/route.ts` (так же устроен `api/mail/ingest/route.ts`)

```ts
const dup = await prisma.mailMessage.findFirst({
  where: { mailboxId: mailbox.id, messageId: msg.messageId },
  select: { id: true },
});
if (dup) { duplicates += 1; continue; }
try {
  await prisma.mailMessage.create({ /* … */ });
  stored += 1;
} catch (error) {
  // Кнопка и cron могли дойти до create одновременно.
  if (isUniqueViolation(error)) duplicates += 1;
  else throw error;
}
```

`findFirst` вместо `findUnique` — потому что уникальность теперь составная, и
ключ сам по себе больше не уникален. Проверка перед записью осталась как
быстрый путь, но последнее слово за индексом: ошибку `P2002` считаем дублем.
Раньше она уходила в `errors` и одно письмо роняло опрос всего ящика.

### 4. Листинг: страница, поиск и фильтры на стороне базы

`api/admin/mail/[address]/route.ts`

```ts
const params = new URL(req.url).searchParams;
const limit  = intParam(params.get("limit"),  MAIL_PAGE_SIZE, 1, MAIL_PAGE_SIZE_MAX);
const offset = intParam(params.get("offset"), 0, 0, Number.MAX_SAFE_INTEGER);

const [total, messages] = await Promise.all([
  prisma.mailMessage.count({ where }),
  prisma.mailMessage.findMany({
    where,
    orderBy: [{ sentAt: "desc" }, { id: "desc" }],
    skip: offset,
    take: limit,
    select: { /* … */ },
  }),
]);

return NextResponse.json({ messages, total, offset, limit, hasMore: offset + messages.length < total });
```

Три детали стоят внимания.

**Добор по `id` в сортировке.** Письма одного опроса часто имеют одинаковый
`sentAt`. Сортировка по одному лишь `sentAt` не задаёт порядок внутри такой
пачки, и Postgres вправе вернуть их по-разному на разных страницах: письмо
покажется дважды или не покажется вообще.

**`searchParams` из `req.url`, а не из `req.nextUrl`.** Побочная, но полезная
перемена: `nextUrl` есть только у `NextRequest`, поэтому два теста листинга
падали на `Cannot read properties of undefined` — и фильтрация по направлению
фактически не была покрыта.

**Поиск и фильтр папки ушли в базу:**

```ts
const search = query ? { OR: [
  { subject:  { contains: query, mode: "insensitive" } },
  { fromAddr: { contains: query, mode: "insensitive" } },
  { toAddr:   { contains: query, mode: "insensitive" } },
  { preview:  { contains: query, mode: "insensitive" } },
] } : null;
```

Раньше `matchesSearch()` и `matchesFolder()` фильтровали уже загруженные
строки — «поиск по ящику» искал среди десяти писем.

### 5. Миграция: снять индекс, заполнить ключи, убрать копии

`prisma/migrations/20261005000000_mail_dedup_per_mailbox/migration.sql`

Порядок шагов здесь — не стилистика, а условие работоспособности.

```sql
-- 1. Старый индекс снимается первым: пока он на месте, шаг 2 падает на дубле.
DROP INDEX IF EXISTS "MailMessage_messageId_key";

-- 2. Ключ по содержимому для писем без Message-ID.
UPDATE "MailMessage" m
SET "messageId" = 'synthetic:sql:' || md5(
    m."mailboxId" || E'\x01' || m."fromAddr" || E'\x01' || m."subject" ||
    E'\x01' || to_char(m."sentAt", 'YYYY-MM-DD"T"HH24:MI:SS.MS') || E'\x01' || m."bodyText")
WHERE m."messageId" IS NULL;

-- 3. Копии внутри ящика: оставляем самую раннюю запись.
DELETE FROM "MailMessage" m USING "MailMessage" keep
WHERE m."mailboxId" = keep."mailboxId" AND m."messageId" = keep."messageId"
  AND (keep."createdAt", keep."id") < (m."createdAt", m."id");

-- 4. Новая область уникальности.
CREATE UNIQUE INDEX "MailMessage_mailboxId_messageId_key" ON "MailMessage"("mailboxId", "messageId");
```

> [!WARNING]
> Разделитель полей — `E'\x01'`, а не `E'\x00'`. Postgres не хранит NUL-байт
> в `text`, и первая версия миграции падала с `invalid byte sequence for
> encoding "UTF8": 0x00`. Найдено прогоном на живой базе, а не вычитыванием.

Миграция удаляет строки — но удаляет ровно копии одного письма в одном ящике,
оставляя самую раннюю. Письма с настоящим Message-ID она не трогает.

### 6. Интерфейс

`app/admin/mail/page.tsx`. Загрузка списка стала одной функцией с тремя
режимами вместо `loadRows` со скрытым побочным эффектом:

```ts
const load = useCallback(async (mode: "replace" | "append" | "silent") => {
  const offset = mode === "append" ? loadedRef.current : 0;
  const limit  = mode === "silent" ? Math.max(PAGE_SIZE, loadedRef.current) : PAGE_SIZE;
  const ticket = ++requestRef.current;
  /* … */
  if (ticket !== requestRef.current) return; // ответ отставшего запроса
  setRows((prev) => (mode === "append" ? [...prev, ...page] : page));
}, [selected, tab, archiveDir, query, activeFolder]);
```

`replace` — смена ящика, вкладки, поиска или папки. `append` — «Показать ещё».
`silent` — фоновое обновление: перечитывает **уже открытое окно** (поэтому
`loadedRef`), не мигая спиннером и не сворачивая открытое письмо.

Сравните с прежним поведением по существу:

| Действие | Было | Стало |
|----------|------|-------|
| Клик по ящику | IMAP-опрос + чтение базы | чтение базы |
| Переключение вкладки | IMAP-опрос + чтение базы | чтение базы |
| Раз в 30 секунд | IMAP-опрос + чтение базы | чтение базы |
| «Проверить почту» | IMAP-опрос | IMAP-опрос |
| Глубина истории | 10 писем | страницами по 25, пока есть письма |

Сборка параметров запроса вынесена в `lib/mailListing.ts` — это чистая функция
с содержательными правилами (например, «направление вкладки главнее
направления папки, иначе папка „исходящие“ на вкладке „Входящие“ даёт пустой
список»), и её место там, где до неё дотягиваются тесты.

Остальное в интерфейсе:

* «Показать ещё (осталось N)» и строка «Показано X из Y»;
* в архиве появился переключатель «Все / Входящие / Исходящие» — раньше архив
  сваливал направления в одну кучу;
* значки `↓ ↑` из списка ящиков убраны, вместе с `groupBy` в `GET /api/admin/mail`;
* в карточке письма — `sentAt` вместо `createdAt` (роут `message/[id]/view`
  отдавал время записи в базу, и у писем, подтянутых задним числом, дата в
  списке расходилась с датой в карточке);
* строка-уведомление гаснет через 6 секунд.

* **дедуп** — поиск дубля в пределах ящика (`{ mailboxId, messageId }`),

  полю и к сдвигу границы между полями;
* **сборка параметров** — приоритет направления вкладки над папкой, обрезка
  пустого поиска, границы окна выборки.

Починены четыре теста, красных на `main`: два падали на `req.nextUrl`, два
посылали в роут отправки поле `text`, которое роут не читает уже давно.

### Проверка миграции на живой Postgres

Миграция прогнана на настоящей базе (Postgres 16, схема из
`20261003000000_project_mail`). Данные: три копии одного письма без Message-ID
в ящике `info`, отдельное письмо без Message-ID и письмо с настоящим
Message-ID.

```
DROP INDEX
UPDATE 4
DELETE 2
CREATE INDEX

 id | subject |            key
----+---------+----------------------------
 d1 | Вопрос  | synthetic:sql:38c44e01510b   ← осталась самая ранняя из трёх копий
 r1 | Счёт    | <real@x>                     ← настоящий Message-ID не тронут
 u1 | Другое  | synthetic:sql:8e2d37d06fe6   ← другое письмо не удалено
```

Затем проверена новая область уникальности:

```
-- то же письмо во второй ящик
INSERT … ('r1-sales','box-sales', … ,'<real@x>', …);   → OK
-- повтор в тот же ящик
INSERT … ('r1-dup','box-info', … ,'<real@x>', …);
→ ERROR: duplicate key value violates unique constraint "MailMessage_mailboxId_messageId_key"
```

И пагинация на 33 письмах, из которых 30 с одинаковым `sentAt`:

```
offset=0  limit=25 → p30,p29,…,p06   (25 строк)
offset=25 limit=25 → p05,p04,p03,p02,p01,r1,u1,d1   (8 строк)
```

Ни пересечений, ни пропусков: 25 + 8 = 33.

> [!NOTE]
> Скриншотов интерфейса в этой правке нет, и причина внешняя: загрузка
> движков Prisma в окружении сборки закрыта (`binaries.prisma.sh` отвечает
> `403 Forbidden`), поэтому `prisma generate` не проходит и приложение не
> поднимается. Поэтому логика, которую обычно видно глазами, вынесена в чистые
> функции и покрыта тестами, а база проверена настоящими SQL-прогонами.

### Ручная проверка

1. `npm run migrate` — применить `20261005000000_mail_dedup_per_mailbox`.
   В логе ожидаются `DROP INDEX`, `UPDATE n`, `DELETE n`, `CREATE INDEX`.
   Число в `DELETE` — это и есть накопленные копии писем.
2. Открыть **Админ-панель → Сервисы и система → Email и обработка данных**.
3. В списке ящиков слева **нет значков `↓ ↑`**.
4. Выбрать ящик с историей длиннее 25 писем. Под шапкой — «Показано 25 из N»,
   внизу списка — «Показать ещё (осталось N−25)». Нажать: дописываются
   следующие 25, строка обновляется. Дойти до конца — кнопка исчезает.
5. Нажать на ящик 5–10 раз подряд, возвращаясь на него. Число в «Показано X из
   Y» **не меняется**. Это и есть исчезнувший «счётчик по нажатию»: проверьте
   в базе, что копий не появилось —
   `SELECT "messageId", count(*) FROM "MailMessage" WHERE "mailboxId"=… GROUP BY 1 HAVING count(*)>1;`
   должен вернуть ноль строк.
6. «Проверить почту» — по-прежнему тянет почту по IMAP и пишет, сколько писем
   получено. Строка гаснет сама через несколько секунд.
7. Ввести в поиск слово из **давнего** письма (глубже 25-й строки). Письмо
   находится: поиск идёт по всей истории ящика, а не по видимой странице.
8. Вкладка **Архив** → переключатель «Входящие / Исходящие»: в каждом
   направлении своя история, страницы листаются так же.
9. Открыть любое письмо. Дата в шапке карточки совпадает с датой в строке
   списка.
10. Отправить письмо с ящика: после отправки открывается вкладка «Исходящие»,
    письмо в начале списка.

## Alternatives

### Курсорная пагинация вместо offset

Вместо `skip: offset` передавать курсор последнего письма
(`cursor: { id }, skip: 1`).

| За | Против |
|----|--------|
| Не «съезжает», если во время листания пришло новое письмо | Нельзя перейти на произвольную страницу — только «дальше» |
| `OFFSET` не сканирует пропущенные строки: ровный план на больших таблицах | Сложнее считать «показано X из Y»: нужен отдельный `count` и своя арифметика |
| Устойчиво к совпадающим `sentAt` без добора по `id` | Больше состояния в клиенте: курсор, а не просто число |

Выбран offset: письма ящика — это тысячи строк, не миллионы, индекс
`(mailboxId, direction, archived, sentAt)` уже есть, а добор по `id` закрывает
проблему одинаковых дат. Возможный сдвиг на одну строку при фоновом обновлении
здесь безобиднее, чем усложнение UI.

### Отдельная колонка `dedupKey` вместо переиспользования `messageId`

Хранить настоящий Message-ID как есть, а ключ дедупликации положить в новую
колонку с уникальным индексом `(mailboxId, dedupKey)`.

| За | Против |
|----|--------|
| `messageId` остаётся честным заголовком письма, без наших `synthetic:` | Ещё одна колонка и миграция, которая заполняет её для всей истории |
| Можно менять формулу ключа, не портя данные письма | Два поля вместо одного нужно держать согласованными в трёх местах записи |
| `buildEml` брал бы `messageId` без оглядки на префикс | Для писем с настоящим Message-ID колонка дублировала бы его |

Выбрано переиспользование: у писем без заголовка `messageId` всё равно был
`null`, а префикс `synthetic:` делает происхождение значения очевидным.
`buildEml` уже нормализует значение (`replace(/[<>]/g, "")`), и синтетический
ключ в выгруженном `.eml` честнее пустого заголовка.

## Quiz

<details>
<summary>1. Почему одного поднятия <code>MAIL_LISTING_LIMIT</code> с 10 до 100 было бы недостаточно?</summary>

**а)** Достаточно: и листинг, и IMAP читали эту константу, обе проблемы
решились бы разом.
**б)** Листинг всё равно отдавал бы одну страницу без `total` и `hasMore`, а
интерфейсу нечем показать «Показать ещё».
**в)** Константу нельзя менять: она участвует в миграции.
**г)** Prisma не принимает `take` больше 50.

**Правильный ответ: б.**

Вариант **а** описывает ровно ту ловушку, из которой выросла ошибка: одно число
отвечало за два разных вопроса, и «поднять лимит» лишь поменяло бы размер
единственной доступной страницы — с десяти писем на сто, по-прежнему без
возможности пролистать дальше. Пагинация — это API (`offset`, `total`,
`hasMore`) и элемент управления, а не значение константы. **в** неверно:
миграция не ссылается на константы кода. **г** — вымысел, у `take` такого
ограничения нет.
</details>

<details>
<summary>2. Клик по ящику увеличивал счётчик писем. Какое звено было первопричиной?</summary>

**а)** `groupBy` в `GET /api/admin/mail` неправильно считал строки.
**б)** Счётчик кешировался в состоянии React и не сбрасывался.
**в)** Клик запускал IMAP-опрос, а дедуп пропускал письма без Message-ID —
в базе появлялись реальные копии.
**г)** Таймер на 30 секунд считал клики.

**Правильный ответ: в.**

`groupBy` (**а**) считал верно — он честно показывал число строк, которых
действительно становилось больше. Счётчик был не иллюзией интерфейса (**б**),
а отражением испорченных данных: клик → опрос → `if (msg.messageId)` не
срабатывает → `create` → копия. Поэтому правка состоит из трёх частей: убрать
опрос с клика, дать письму ключ всегда, сузить область уникальности до ящика.
**г** путает следствие с причиной: таймер усугублял, но копии плодил сломанный
дедуп.
</details>

<details>
<summary>3. Зачем в <code>orderBy</code> добавлен второй ключ <code>{ id: "desc" }</code>?</summary>

**а)** Чтобы новые письма были сверху.
**б)** `sentAt` не уникален, и без второго ключа порядок внутри писем с
одинаковой датой не определён — страницы могут пересекаться и терять письма.
**в)** Prisma требует минимум два ключа сортировки при `skip`.
**г)** Чтобы `count` и `findMany` возвращали согласованные числа.

**Правильный ответ: б.**

Письма одного опроса часто получают одинаковый `sentAt`. `ORDER BY "sentAt"
DESC` не задаёт порядок внутри такой пачки, и на разных запросах СУБД вправе
вернуть её по-разному — при листании через `OFFSET` письмо покажется дважды или
не покажется вообще. За «новые сверху» (**а**) отвечает `sentAt: "desc"`, второй
ключ лишь делает порядок полным. **в** — таких требований у Prisma нет. **г**
неверно: согласованность `count` и `findMany` обеспечивает общий `where`, а не
сортировка.
</details>

<details>
<summary>4. Почему в миграции <code>DROP INDEX</code> стоит до <code>UPDATE</code>, а не после?</summary>

**а)** Ради скорости: `UPDATE` без индекса выполняется быстрее.
**б)** Порядок не важен, это вопрос стиля.
**в)** Старый индекс уникален на всю таблицу, и `UPDATE` упал бы на первой же
паре копий, получивших одинаковый синтетический ключ.
**г)** Postgres не даёт удалять индекс после `UPDATE` в одной транзакции.

**Правильный ответ: в.**

В этом и суть шага: три копии одного письма получают один и тот же ключ по
содержимому — ровно то, что нужно для дальнейшего `DELETE`, и ровно то, что
запрещает старый глобальный уникальный индекс. Первая версия миграции падала
именно так: `duplicate key value violates unique constraint
"MailMessage_messageId_key"`. Скорость (**а**) здесь побочна, **г** — вымысел,
**б** опровергается прогоном на живой базе.
</details>

<details>
<summary>5. Письмо пришло на <code>info@trioz.ru</code> с копией на <code>sales@trioz.ru</code>. Что происходило до правки и что происходит теперь?</summary>

**а)** Было: письмо в обоих ящиках. Стало: только в `info`, дедуп стал строже.
**б)** Было: письмо только в одном ящике, второй `create` отвергал глобальный
уникальный индекс. Стало: письмо в истории обоих ящиков.
**в)** Ничего не изменилось: оба ящика опрашиваются независимо.
**г)** Было: две копии в одном ящике. Стало: одна.

**Правильный ответ: б.**

Оба ящика опрашиваются независимо (как и говорит **в**) — но у письма один
Message-ID, а `messageId String? @unique` объявлял уникальность на всю таблицу.
Кто успел первым, тот и получил письмо; второй ящик терял его навсегда.
`@@unique([mailboxId, messageId])` переопределяет «одно и то же письмо» как
«одно письмо *в пределах ящика*» — и оба ящика видят свою копию, при этом
повторный опрос по-прежнему дубля не создаёт. **г** описывает другой баг —
копии в одном ящике из-за отсутствия ключа.
</details>
