# Уведомления: почему прочитанное не пропадало

Про колокольчик, полосу состояния в десктопной оболочке и два бага, которые
пользователь увидел своими глазами. Читать перед правками в
`lib/createNotification.ts`, `api/notifications`, `api/dm/read`, `api/appeals/[id]`
и `apps/desktop/src/preload/statusBar.ts`.

## Что было сломано

**Первое: «перешёл, прочёл — уведомление не пропало».**

Уведомление хранило только замороженный текст и ссылку. Пометка «прочитано»
искала записи **сопоставлением текста ссылки**:

```ts
// api/dm/read — как было
where: { userId, read: false, type: "appeal", link: { contains: "section=business" } }
where: { userId, read: false, type: "dm", OR: [{ link: { contains: `dm=${peerId}&` } }, ...] }
```

Для обращений в админке ссылка — `/admin/appeals`, то есть раздел целиком.
Совпасть с ней могло либо всё сразу, либо ничего. Ничего и совпадало: обычный
путь (перешёл в обращения, открыл карточку, прочитал) уведомление не гасил
вообще. Погасить его можно было ровно одним способом — нажать на него в списке
на `/settings/notifications`.

**Второе: «удалил тестовый аккаунт — уведомление осталось».**

О человеке в записи оставался только текст («andycoulbot: Сотрудничество»).
Связи с аккаунтом не было никакой, поэтому удаление аккаунта уведомление о нём не
задевало: оно продолжало висеть и вести в заявку, которой больше нет.

**Третье (то, что видно на снимке): полоса состояния в десктопной оболочке умела
только появляться.**

`apps/desktop/src/preload/statusBar.ts` держал `{ latest, count }` и не сбрасывал
ни то, ни другое НИКОГДА: `state.count += 1` на каждое событие, `latest`
перезаписывался только следующим уведомлением. Прочитанное уведомление оставалось
внизу окна навсегда — и именно эту полосу человек и видел после того, как всё
прочитал.

## Как сделано

У уведомления появились два признака, и оба отвечают на вопросы, которые раньше
приходилось угадывать по тексту:

| Поле | Вопрос | Что даёт |
|---|---|---|
| `actorId` | из-за кого | каскад: удалили аккаунт — уведомления о нём исчезли |
| `entityType` + `entityId` | о чём | точная пометка «прочитано» и уборка вместе с предметом |

Дальше — три места, где это работает:

1. **Открытие заявки гасит её уведомления.** `GET /api/appeals/[id]` вызывает
   `markSubjectNotificationsRead` по этой заявке и возвращает `unreadLeft`.
   Открытие карточки и есть «прочитал» — ждать нажатия в списке уведомлений
   незачем.
2. **Прочитанная переписка гасит свои.** `POST /api/dm/read` теперь ищет по
   предмету (разговору), а не по подстроке ссылки. Прежнее сопоставление
   осталось только для записей, созданных до появления предмета: без этого у людей
   висело бы вечное «непрочитанное» просто по дате создания.
3. **Полоса состояния слушает страницу.** Приложение и раньше сообщало остаток
   непрочитанного событием `tz-notifications-read` (его слушает колокольчик в
   шапке). Теперь то же событие слушает preload, и ноль непрочитанных гасит и
   счётчик, и саму запись. Нажатие на полосу тоже снимает запись: человек пошёл
   читать.

Почему polling из preload не годится: у него нет ни сессии, ни права ходить в API
от имени человека, а второй источник правды о непрочитанном неизбежно разошёлся бы
с колокольчиком. Поэтому источник один — приложение, канал — событие в DOM,
который preload и страница делят.

## Что важно не сломать

- **`actorId` никогда не равен получателю.** Такая связь ничего не добавляет
  (запись и так уйдёт с получателем по `userId`), зато сбивает смысл поля: оно про
  того, чьё действие вызвало уведомление.
- **Гасятся только свои уведомления.** Открыв заявку, администратор гасит своё, а
  не уведомление коллеги, которому ещё предстоит её прочитать.
- **Сбой пометки не ломает открытие заявки.** Карточка важнее, чем отметка о
  прочтении, поэтому ошибка глотается с записью в журнал.
- **Старые записи не брошены.** У них нет предмета, и они гасятся прежним
  способом. Убирать эту ветку можно будет, когда старых записей не останется.

## Выкладка

Веб-часть — обычная выкладка (миграция едет сама в `postinstall`). Правка полосы
состояния — в **десктопной оболочке**: она попадёт к людям только со следующей
сборкой приложения, поэтому до неё полоса будет вести себя по-старому, а
колокольчик — уже правильно.
