# Связка серверов: что она делает и чего не делает

Про раздел **Сервисы и система → Серверы**. Написано после прямой проверки кода
и обновлено, когда хранилище перестало быть пометкой.

## Что связка делает

| Действие | Работает |
|---|---|
| Реестр узлов: добавить, выключить, удалить | да |
| Токен агента: выпуск, перевыпуск, хранение только хеша | да |
| Отчёт узла раз в минуту и отметка «на связи» | да |
| Состояние узла в панели (готов, нет ключа, не отчитывался) | да |
| **VPN: выбор узла для нового доступа и раздача пиров** | **да** |
| Закрепление внешнего адреса выхода за пиром | да |
| **Хранилище: загруженные файлы уезжают на узел** | **да** |

## Приоритет узла хранения

Правило одно и читается в одну строку:

> **Нет дочернего узла хранения — файлы на главном сервере. Появился — новые идут
> на него, накопленные переносятся. Узел пропал — загрузка не падает, файл
> остаётся на главном сервере и уедет позже.**

Как это устроено:

1. Файл всегда сначала пишется на диск главного сервера — как и раньше. Человек
   не ждёт чужую машину, и загрузка не зависит от её доступности.
2. Сразу после записи, если настроенный узел есть, файл копируется на него,
   в базе проставляется место, и локальная копия удаляется. Именно в этом
   порядке: копия → указатель → удаление. Любой другой порядок теряет файлы.
3. Адрес файла при переезде **не меняется**: как был `/uploads/messages/…`, так и
   остался. Где искать, знает только раздатчик в `server.ts`.
4. Право на файл проверяется по-прежнему в приложении (`lib/uploadAccess`), до
   того как что-то будет прочитано. Узел отдаёт файл не человеку, а нам; поток
   проксируется, включая `Range` для перемотки голосовых и видеозаметок.

Чего это стоит: узел разгружает **диск**, но не канал главного сервера — поток
идёт через него. Так сделано намеренно: прямая ссылка на узел означала бы, что
адрес узла известен клиенту и что право на файл проверяет не приложение.

### Что считается настроенным узлом

Узел участвует в выборе, только если у него заполнено всё: назначение
«Хранилище», роль дочерняя, включён, задан адрес хранилища, корзина,
идентификатор ключа и секретный ключ. Недонастроенный узел молча пропускается —
файлы просто остаются на главном сервере.

Хранилище — S3-совместимое (например MinIO на этой же машине). Почему так, а не
свой протокол: у дочерних узлов намеренно нет входящего API, связка построена «на
вытягивание», чтобы узел мог жить за NAT. Файл же нужно именно положить на узел.
Готовый протокол даёт права доступа, проверенные реализации и возможность при
желании подключить внешнее хранилище вместо своей машины.

### Когда узел не отвечает

* **При загрузке** — файл остаётся на главном сервере, узел на минуту исключается
  из выбора, в журнале строка `[storage] файл … остался на главном сервере`.
* **При выдаче уже переехавшего файла** — ответ 503, а не 404. Это разные вещи:
  404 в интерфейсе выглядит как «вложение удалили», и человек начинает искать,
  кто его стёр.
* **При переносе накопленного** — порция обрывается на первом отказе, чтобы не
  ждать ответов от мёртвой машины.

### Перенос накопленного и возврат

В разделе «Серверы» появился блок **Файлы**: сколько файлов где лежит и куда
пойдут новые. Перенос идёт порциями по нажатию, а не сам по себе: фоновая
перекладка сотен гигабайт — работа, которую никто не видит и никто не может
остановить, когда она мешает. Повторное нажатие продолжает с места остановки.

Обратное действие — «Вернуть на главный сервер» — тоже порциями. Оно обязательно
перед выводом узла из работы: **узел с файлами удалить нельзя**, маршрут отвечает
409 и называет число файлов. Запись узла — единственное, что связывает адрес
вложения с машиной, где файл лежит.

## Чего связка НЕ делает

**Назначения «Медиа» и «Вычисления» по-прежнему ни на что не влияют.** Это
пометки в реестре.

Где лежат файлы, которые переезд не затрагивает:

| Что | Куда пишется |
|---|---|
| Аватары, иконки, баннеры | `apps/web/public/uploads` на главном сервере |
| Инсталляторы и APK | `apps/web/public/desktop` там же |

Публичные картинки остаются на главном сервере намеренно: они и должны
открываться без входа (письма, предпросмотр ссылок, страница входа), и проверять
на них нечего.

## Как настроить узел хранения

1. Поднять на отдельной машине S3-совместимое хранилище, создать корзину и пару
   ключей только на неё.
2. Закрыть машину: `./deploy/firewall.sh files` и доступ к порту хранилища только
   с адреса главного сервера. Корзина не должна быть публичной — раздаёт файлы
   приложение, а не хранилище.
3. В админке: **Серверы → Добавить узел**, назначение «Хранилище».
4. В карточке узла: **Адрес хранилища** (адрес, корзина, регион) и **Ключ
   доступа** (идентификатор и секрет). Секрет хранится зашифрованным
   `ENCRYPTION_SECRET` и наружу не отдаётся никогда — в панели видно только, что
   он задан.
5. Проверить: загрузить вложение в переписке и убедиться, что в блоке «Файлы»
   счётчик узла вырос, а файл открывается.
6. Нажать **Перенести** столько раз, сколько нужно, чтобы остаток на главном
   сервере дошёл до нуля.

## Как проверить самому

```bash
# правило выбора места и его проверки
sed -n '1,40p' apps/web/src/lib/storagePlacement.ts

# порядок действий при переносе (копия → указатель → удаление)
grep -n "put\|pointer\|unlink" apps/web/src/lib/uploadOffload.test.ts

# что читает реестр узлов
grep -rl "serverNode" apps/web/src --include=*.ts --include=*.tsx | grep -v test
```

На сервере: `SELECT "nodeId", count(*) FROM "UploadedFile" GROUP BY 1;` — видно,
сколько файлов на главном (`NULL`) и сколько на узлах.
