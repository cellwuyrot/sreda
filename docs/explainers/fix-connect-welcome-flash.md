# Explainer — Мелькание «окна приветствия» при переходе сервер→сервер

> 🎯 **TL;DR** — При переключении между сообществами (сервер→сервер / группа→группа)
> на не-первом входе на долю секунды мелькало «окно приветствия» группы
> (`GroupInfoPanel` с её правилами) — или, если правила/приветствие не заполнены,
> просто пустое окно. Причина: канал приземления выбирался **асинхронным
> эффектом внутри `GroupInfoPanel`** уже *после* того, как окно нарисовалось.
> Чиним так: канал приземления выбирается **атомарно** в момент прихода данных
> новой группы — тем же батчем, что и подмена `groupDetail`. Изменён один файл:
> `apps/web/src/app/connect/page.tsx`.

---

## Background

### Для тех, кто видит проект впервые

**TZ.Connect** — раздел-мессенджер экосистемы TrioZ (по духу — Discord/Slack).
Слева направо интерфейс состоит из колонок:

1. **NavRail** — вертикальная панель разделов (Сообщества / Друзья / ЛС).
2. **Колонка 2** — либо список групп («сообществ» = «серверов»), либо список
   каналов внутри выбранной группы (`ChannelSidebar`).
3. **Колонка 3** — область чата (`MessageArea`) выбранного канала. Если канал не
   выбран, здесь показывается «окно» состояния: гейт правил (`GroupRulesGate`),
   информационная панель группы (`GroupInfoPanel`) или приветствие всего раздела
   (`ConnectWelcome`).

Вся раскладка живёт в одном большом клиентском компоненте — `ConnectPageInner`
в `apps/web/src/app/connect/page.tsx`. Ключевые единицы состояния:

```ts
const [selectedGroup, setSelectedGroup]     = useState<string | null>(null); // id группы
const [groupDetail, setGroupDetail]         = useState<GroupDetail | null>(null); // её данные
const [selectedChannel, setSelectedChannel] = useState<string | null>(null); // id открытого канала
```

> 📖 **Важная деталь потока данных.** `selectedGroup` — это просто **id**. Полные
> данные группы (`groupDetail`: каналы, участники, правила) подгружаются
> **асинхронно** по сети: `fetchGroupDetail(groupId)` дёргает `GET /api/groups/:id`.
> Между «пользователь выбрал группу» и «данные группы применены» всегда есть
> зазор в один-два кадра.

Область чата (Колонка 3) выбирает, что показать, по такому правилу (упрощённо):

```tsx
{selectedChannel && selectedChannelData
  ? <MessageArea .../>            // есть выбранный канал и его данные найдены
  : selectedGroup && groupDetail
    ? (rulesGated ? <GroupRulesGate/> : <GroupInfoPanel/>)  // группа открыта, канал не выбран
    : <ConnectWelcome .../>}      // ничего не выбрано → приветствие раздела
```

### Что такое «окно приветствия» группы

`GroupInfoPanel` — это карточка группы, которая показывается, когда группа
выбрана, но конкретный канал ещё не открыт. Она рисует иконку, название,
владельца, число участников и **правила сообщества** (то самое «приветственное
сообщение», которое пишет владелец). Если правил нет — секция правил пустая.

Но задумано так, что на этой панели пользователь надолго не задерживается:
`GroupInfoPanel` при монтировании **сам** просит родителя открыть первый текстовый
канал. Делалось это эффектом:

```tsx
// GroupDialogs.tsx → GroupInfoPanel
useEffect(() => {
  if (onAutoSelectChannel) onAutoSelectChannel();   // → выбрать первый TEXT-канал
}, [onAutoSelectChannel]);
```

а сам `onAutoSelectChannel` в родителе выбирал первый текстовый канал группы:

```tsx
onAutoSelectChannel={() => {
  const firstText = groupDetail.channels.find(c => c.type === "TEXT");
  if (firstText) handleChannelClick(firstText);
}}
```

### Что уже чинили раньше (и почему этого не хватило)

Родственный баг — «мелькание пустого чата при переключении **каналов** разных
групп» — уже лечили (`FIX-GRPSWITCH2`, см.
[`fix-connect-group-switch-flash.md`](./fix-connect-group-switch-flash.md)).
Там сброс `selectedChannel` перенесли в момент подмены данных, чтобы он
происходил **одним рендером** с `setGroupDetail`:

```tsx
if (prevLoaded && prevLoaded !== data.id) setSelectedChannel(null);
```

> ⚠️ **Ключевой недосмотр.** Тот фикс убрал промежуточный кадр `MessageArea` (старый
> чат → пустой чат → новый), но **сам приземлил переключение прямо на
> `GroupInfoPanel`**: канал обнулён, данные новой группы применены → рисуется окно
> приветствия. А открытие первого канала происходит только **следующим** кадром
> (эффектом внутри `GroupInfoPanel`). Вот этот один кадр окна приветствия
> пользователь и видит как «мелькнуло и пропало».

## Intuition

Разберём на игрушечном примере. Пользователь читает **канал A1** в группе **A** и
кликает группу **B** (в B у него уже принятые правила, есть текстовый канал B1).

Порядок состояний в старом коде:

| Шаг | `selectedGroup` | `groupDetail` | `selectedChannel` | Колонка 3 |
|-----|-----------------|---------------|-------------------|-----------|
| 1. клик по B | `B` | `A` (устар.) | `A1` | `MessageArea(A1)` — старый чат, притемнён |
| 2. пришли данные B (один рендер) | `B` | `B` | **`null`** | **`GroupInfoPanel(B)` ← мелькающее окно!** |
| 3. эффект `GroupInfoPanel` открыл B1 | `B` | `B` | `B1` | `MessageArea(B1)` — финал |

Виновник — **шаг 2**. Данные группы применились, а канал в этот момент `null`,
поэтому один кадр рисуется окно приветствия группы B. И только потом, **после
отрисовки**, `useEffect` внутри `GroupInfoPanel` выбирает первый канал.

> 💡 **Почему `useEffect` = лишний кадр.** Эффекты в React выполняются **после**
> коммита и отрисовки. Значит, между «`GroupInfoPanel` нарисовался» и «эффект
> выбрал канал» браузер успевает показать пользователю ровно один кадр (~16 мс при
> 60 fps) — то самое «на миллисекунду появилось и пропало».

Идея фикса: **не откладывать выбор канала на эффект после отрисовки.** Раз мы уже
знаем каналы новой группы в тот момент, когда применяем `groupDetail`, — там же и
выбираем канал приземления. React батчит `setGroupDetail(B)` и
`setSelectedChannel(B1)` в один рендер, и промежуточному окну просто негде
появиться:

| Шаг | `selectedGroup` | `groupDetail` | `selectedChannel` | Колонка 3 |
|-----|-----------------|---------------|-------------------|-----------|
| 1. клик по B | `B` | `A` (устар.) | `A1` | `MessageArea(A1)` притемнён |
| 2. данные B (один рендер) | `B` | `B` | `B1` | `MessageArea(B1)` — **сразу** финал |

А что с двумя другими случаями «нет канала»?

- **Правила не приняты** (первый вход участника): канал приземления **не**
  выбираем — оставляем `null`, чтобы честно показать `GroupRulesGate`. Условие
  «гейта» в фиксе повторяет условие рендера один-в-один.
- **В группе вообще нет текстовых каналов**: выбирать нечего, оставляем `null` —
  показывается `GroupInfoPanel` (это корректно, а не баг).

## Code

Изменён единственный файл: `apps/web/src/app/connect/page.tsx`, единственная
функция — `fetchGroupDetail`.

### Было

```tsx
const prevLoaded = loadedGroupIdRef.current;
loadedGroupIdRef.current = data.id;
setGroupDetail(data);
// Переключились на другую группу: ранее открытый канал ей не принадлежит.
if (prevLoaded && prevLoaded !== data.id) setSelectedChannel(null);
```

### Стало

```tsx
const prevLoaded = loadedGroupIdRef.current;
loadedGroupIdRef.current = data.id;
setGroupDetail(data);
// FIX-WELCOMEFLASH: при РЕАЛЬНОЙ смене группы (или первом входе в неё) сразу
// выбираем «канал приземления» в том же батче, что и подмену данных группы.
// Иначе колонка чата успевала отрисовать один кадр «окна приветствия»
// (GroupInfoPanel с правилами / пустое окно) до того, как эффект авто-выбора
// канала внутри GroupInfoPanel откроет первый текстовый канал.
if (prevLoaded !== data.id) {
  // Дип-линк из уведомления сам откроет нужный канал — не опережаем его.
  const pendingDeepLink = !!deepLinkRef.current?.channel && deepLinkRef.current?.group === data.id;
  // Правила ещё не приняты → показываем гейт правил, канал не открываем.
  // Условие точно совпадает с веткой рендера GroupRulesGate ниже.
  const rulesGated = !!data.rules && !data.rulesAccepted && data.myRole === "MEMBER";
  const firstText = data.channels.find((c) => c.type === "TEXT");
  setSelectedChannel(!pendingDeepLink && !rulesGated && firstText ? firstText.id : null);
}
```

Что здесь важно:

1. **`prevLoaded !== data.id`** вместо `prevLoaded && prevLoaded !== data.id` —
   теперь ветка срабатывает и на **первом** входе в группу (когда `prevLoaded`
   ещё `null`), а не только на переключениях. «Тихие» refresh'и **той же** группы
   (сокеты `profile-updated`/`group-updated`, 30-секундный поллинг панели
   участников) по-прежнему сюда не попадают: у них `prevLoaded === data.id`,
   поэтому открытый канал не трогается.
2. **`rulesGated`** дословно повторяет условие рендера `GroupRulesGate`
   (`data.rules && !data.rulesAccepted && myRole === "MEMBER"`). Если правила ещё
   не приняты — канал не выбираем, и гейт правил честно показывается (его нельзя
   проскочить).
3. **`pendingDeepLink`** защищает переход по уведомлению (`?group=…&channel=…`):
   там нужный канал открывает отдельный эффект по `deepLinkRef`, и мы не
   опережаем его выбором первого попавшегося канала.

> 📖 **Почему `GroupInfoPanel` и его авто-выбор оставлены как есть.** Эффект
> авто-выбора внутри `GroupInfoPanel` продолжает работать «страховкой» для путей,
> где `fetchGroupDetail` не меняет группу: после удаления открытого канала
> (`channel-deleted`, refresh **той же** группы) и сразу после принятия правил
> (`onAccept` вызывает `setGroupDetail` напрямую). В этих случаях `groupDetail` уже
> той же группы, наша ветка не срабатывает, и панель, как и раньше, сама доводит
> пользователя до первого канала. Оба механизма **взаимоисключающи**: при реальном
> переключении `selectedChannel` уже выбран, `GroupInfoPanel` не монтируется и его
> эффект не запускается — двойного выбора нет.

## Verification

**Статические проверки (в песочнице):**

- `eslint src/app/connect/page.tsx` → **0 ошибок.** Единственный warning
  (`react-hooks/exhaustive-deps` на сокет-эффекте) существовал до правки и к ней
  не относится.
- `tsc --noEmit` → **в `connect/page.tsx` ноль ошибок типов.** Остальные 128
  ошибок компилятора — environment-only: в песочнице не скачивается движок Prisma
  (403 Forbidden на `binaries.prisma.sh`), поэтому `prisma generate` не отрабатывает
  и результаты запросов Prisma коллапсируют в `any`/`{}` в `route.ts`/`server.ts`.
  Изменённого файла среди них нет.

> ⚠️ **Что стоит прогнать в полноценной среде** (где доступны движки Prisma и БД):
> `npm run build` (полная сборка Next) и `npm run lint`. Скриншот UI в песочнице
> снять нельзя — приложение не поднимается без БД и движка Prisma.

**Ручное QA — пошагово:**

1. Запустить веб: `npm run dev`, открыть `/connect`, войти.
2. Иметь минимум **две группы** (A и B), в каждой — хотя бы один текстовый канал.
3. Открыть канал в группе A (в Колонке 3 виден чат).
4. Кликнуть по группе B в списке слева.
5. **Ожидаемо:** старый чат плавно гаснет и **сразу** сменяется первым каналом
   группы B. Окно приветствия/инфо-панель группы B мелькать больше **не должно**.
6. Быстро перещёлкать A→B→A→B несколько раз — ни окна приветствия, ни пустого окна
   между чатами быть не должно.
7. **Сценарий «пустого окна»:** взять группу, где правила/описание не заполнены, и
   войти в неё из другой группы — пустое окно мелькать **не должно** (сразу
   открывается первый канал).
8. **Регрессия — гейт правил:** зайти новым участником в группу с правилами,
   которые вы ещё не приняли, — должен показаться `GroupRulesGate` и **остаться**
   (его нельзя проскочить), а не мелькнуть.
9. **Регрессия — панель «Участники»:** открыть панель и подождать >30 сек, находясь
   в канале, — тихое обновление данных группы **не должно** выкидывать вас из
   открытого канала.
10. **Регрессия — дип-линк:** перейти по уведомлению вида `?group=…&channel=…` —
    открывается именно нужный канал, без промежуточного «первого» канала.
11. **Регрессия — удаление канала:** удалить открытый канал — интерфейс должен
    корректно перейти к следующему каналу (или к инфо-панели, если каналов не
    осталось).

## Alternatives

**Альтернатива 1. Убрать авто-выбор из `GroupInfoPanel` и перенести всю логику
приземления в `fetchGroupDetail`.** Сделать `GroupInfoPanel` чисто отображающим.

| Плюсы | Минусы |
|-------|--------|
| Единственный источник правды о «канале приземления» | Меняет поведение путей «удалён канал» и «приняты правила» (там `fetchGroupDetail` не участвует) |
| Меньше «магии» в отображающем компоненте | Пришлось бы дублировать/выносить логику авто-выбора для этих путей — больше кода и риска |

**Альтернатива 2. Гейтить `GroupInfoPanel` через флаг «идёт переключение».**
Не рисовать окно приветствия, пока `groupSwitching === true`.

| Плюсы | Минусы |
|-------|--------|
| Не трогает поток выбора канала | `groupSwitching` — косметический флаг; на первом входе (без него) кадр всё равно мелькнёт |
| Малая правка разметки | Прячет симптом, а не первопричину (поздний выбор канала эффектом) |

Выбранное решение убирает **первопричину** — поздний, послеотрисовочный выбор
канала — и делает это ровно там, где уже решается судьба переключения группы
(`fetchGroupDetail`), не ломая соседние сценарии.

## Quiz

<details>
<summary>1. Почему при старом коде окно приветствия мелькало ровно один кадр?</summary>

**Правильный ответ: Б.**

- **А.** Потому что `GET /api/groups/:id` слишком долгий. — *Неверно: сетевой зазор
  существует всегда, но сам по себе окна не рисует; речь про кадр уже после
  прихода данных.*
- **Б. Потому что выбор канала откладывался на `useEffect` внутри `GroupInfoPanel`,
  который выполняется уже ПОСЛЕ отрисовки окна.** — *Верно: один кадр окна
  успевает показаться до того, как эффект откроет канал.*
- **В.** Потому что `groupSwitching` притемнял колонку. — *Неверно: притемнение —
  косметика, оно не создаёт и не убирает кадр.*
</details>

<details>
<summary>2. Зачем условие сменили с <code>prevLoaded && prevLoaded !== data.id</code> на <code>prevLoaded !== data.id</code>?</summary>

**Правильный ответ: В.**

- **А.** Чтобы срабатывало на тихих refresh'ах той же группы. — *Неверно:
  наоборот, у них `prevLoaded === data.id`, ветка не срабатывает.*
- **Б.** Чтобы убрать лишний рендер. — *Неверно: к числу рендеров это не относится.*
- **В. Чтобы ветка срабатывала и на ПЕРВОМ входе в группу (когда `prevLoaded` ещё
  `null`), и канал приземления выбирался атомарно даже тогда.** — *Верно.*
</details>

<details>
<summary>3. Что произойдёт, если новый участник войдёт в группу с непринятыми правилами?</summary>

**Правильный ответ: А.**

- **А. `rulesGated` истинно → `selectedChannel` остаётся `null` → показывается и
  остаётся `GroupRulesGate`.** — *Верно: условие гейта дословно повторяет ветку
  рендера, канал не открывается, гейт не проскочить.*
- **Б.** Откроется первый текстовый канал, гейт пропустится. — *Неверно: именно от
  этого защищает `rulesGated`.*
- **В.** Мелькнёт пустое окно. — *Неверно: выбор канала теперь атомарен, а гейт
  показывается стабильно.*
</details>

<details>
<summary>4. Почему авто-выбор канала внутри <code>GroupInfoPanel</code> оставили, а не удалили?</summary>

**Правильный ответ: Б.**

- **А.** Из-за обратной совместимости API. — *Неверно: API тут ни при чём.*
- **Б. Он остаётся «страховкой» для путей, где `fetchGroupDetail` не меняет группу:

  напрямую).** — *Верно: в этих случаях наша ветка не срабатывает.*
- **В.** Иначе будет двойной выбор канала. — *Неверно: при реальном переключении
  канал уже выбран, `GroupInfoPanel` не монтируется — конфликта нет.*
</details>

  *Верно: иначе мелькнул бы «не тот» канал.*
