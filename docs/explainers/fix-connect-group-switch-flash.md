# Explainer — Мелькание «пустого окна» при переключении между каналами разных групп

> 🎯 **TL;DR** — При переходе из канала одной группы в канал другой на долю
> секунды мелькало «пустое окно чата» (инфо-панель группы / экран приветствия).
> Причина — выбранный канал сбрасывался в `null` **до** того, как приходили
> данные новой группы, поэтому колонка чата успевала отрисовать промежуточный
> «пустой» экран. Чиним так: канал сбрасывается **атомарно** в момент подмены
> данных группы, одним рендером. Изменён только `apps/web/src/app/connect/page.tsx`.

---

## Background

### Для тех, кто видит проект впервые

**TZ.Connect** — раздел-мессенджер экосистемы TrioZ (аналог Discord/Slack).
Слева направо интерфейс состоит из колонок:

1. **NavRail** — вертикальная панель разделов (Сообщества / Друзья / ЛС).
2. **Колонка 2** — либо список групп («сообществ»), либо список каналов внутри
   выбранной группы (`ChannelSidebar`).
3. **Колонка 3** — область чата (`MessageArea`) выбранного канала. Если канал
   не выбран, здесь показывается «окно» состояния: правила группы
   (`GroupRulesGate`), инфо-панель группы (`GroupInfoPanel`) или приветствие
   (`ConnectWelcome`).

Вся эта раскладка живёт в одном большом клиентском компоненте —
`ConnectPageInner` в `apps/web/src/app/connect/page.tsx`. Ключевые единицы
состояния:

```ts
const [selectedGroup, setSelectedGroup]   = useState<string | null>(null); // id группы
const [groupDetail, setGroupDetail]       = useState<GroupDetail | null>(null); // её данные (каналы, участники…)
const [selectedChannel, setSelectedChannel] = useState<string | null>(null); // id открытого канала
```

> 📖 **Важная деталь потока данных.** `selectedGroup` — это просто **id**.
> Полные данные группы (`groupDetail`) подгружаются **асинхронно** по сети:
> `fetchGroupDetail(groupId)` дергает `GET /api/groups/:id`. То есть между
> «пользователь выбрал группу» и «данные группы применены» всегда есть зазор в
> один-два кадра.

Область чата (Колонка 3) выбирает, что показать, по такому правилу
(упрощённо):

```tsx
{selectedChannel && selectedChannelData
  ? <MessageArea .../>            // есть выбранный канал и его данные найдены
  : selectedGroup && groupDetail
    ? <GroupInfoPanel .../>       // группа открыта, но канал не выбран → «окно» с инфо
    : <ConnectWelcome .../>}      // ничего не выбрано → приветствие
```

где `selectedChannelData = groupDetail?.channels.find(c => c.id === selectedChannel)`.

### Что уже пытались сделать раньше

Проблема «моргания» при переключении групп известна. Коммит `4863b30`
(`FIX-GRPSWITCH`) описал её дословно: **«старые каналы → пустой чат → новые
данные»**. Лечение там было **косметическим** — на время загрузки новой группы
обе колонки притемнялись до `opacity-40`:

```tsx
const [groupSwitching, setGroupSwitching] = useState(false);
// …
<div className={`… transition-opacity duration-200 ${groupSwitching ? "opacity-40 pointer-events-none" : "opacity-100"}`}>
```

> ⚠️ **Ключевой недосмотр.** Притемнение не убирает промежуточный «пустой»
> кадр — оно лишь делает его полупрозрачным. «Окно» по-прежнему **отрисовывается**,
> просто на 40 % яркости. Именно этот дважды-перерисованный экран пользователь и
> воспринимает как «микросекундное появление окна».

## Intuition

Разберём на игрушечном примере. Пользователь смотрит **канал A1** в **группе A**
и кликает **группу B**.

Порядок состояний в старом коде:

| Шаг | `selectedGroup` | `groupDetail` | `selectedChannel` | Что в Колонке 3 |
|-----|-----------------|---------------|-------------------|-----------------|
| 1. клик по B | `B` | `A` (устар.) | `A1` | `MessageArea(A1)` — ещё старый чат |
| 2. **эффект чистит канал** | `B` | `A` (устар.) | **`null`** | **`GroupInfoPanel(A)` ← «пустое окно»!** |
| 3. пришли данные B | `B` | `B` | `null` | `GroupInfoPanel(B)` — финал |

Виновник — **шаг 2**. Старый код сбрасывал `selectedChannel` в `null`
**сразу же**, в эффекте на смену `selectedGroup`, ещё до того как по сети
приедут данные группы B. В этот момент `groupDetail` всё ещё указывает на группу
A, канал уже `null` → срабатывает вторая ветка `? :` и рисуется инфо-панель
старой группы. Это и есть тот самый мелькающий кадр.

Идея фикса: **не трогать канал, пока не приехали новые данные.** Пусть старый чат
спокойно висит (притемнённый), а сброс канала произойдёт **в тот же момент**, что
и подмена `groupDetail`. React группирует (batches) оба `setState` в асинхронном
колбэке в один-единственный рендер, поэтому промежуточному «пустому окну» просто
негде возникнуть:

| Шаг | `selectedGroup` | `groupDetail` | `selectedChannel` | Что в Колонке 3 |
|-----|-----------------|---------------|-------------------|-----------------|
| 1. клик по B | `B` | `A` (устар.) | `A1` | `MessageArea(A1)` притемнён |
| 2. пришли данные B (один рендер) | `B` | `B` | `null` | `GroupInfoPanel(B)` — сразу финал |

Старый чат гаснет и **сразу** сменяется правильным экраном новой группы. Никакого
промежуточного кадра.

> 💡 **Почему это работает — про батчинг.** В React 18+ (проект на Next 16 /
> React 19) обновления состояния внутри `await`-колбэков **автоматически
> объединяются**. `setGroupDetail(B)` и `setSelectedChannel(null)`, вызванные
> подряд после `await res.json()`, дают ровно один перерендер — а не два.

## Code

Изменён единственный файл: `apps/web/src/app/connect/page.tsx`.

### 1. Сброс канала переехал в момент применения данных

Заводим `ref`, который помнит, данные **какой** группы сейчас реально
отрисованы. Когда приходят данные **другой** группы — это и есть настоящее
переключение, и только тогда сбрасываем канал (обычные `refresh`-и той же группы
канал не трогают):

```tsx
// FIX-GRPSWITCH2: какая группа сейчас реально отрисована (её данные применены).
const loadedGroupIdRef = useRef<string | null>(null);

const fetchGroupDetail = useCallback(async (groupId: string) => {
  const res = await fetch(`/api/groups/${groupId}`);
  if (res.ok) {
    const data: GroupDetail = await res.json();
    const prevLoaded = loadedGroupIdRef.current;
    loadedGroupIdRef.current = data.id;
    setGroupDetail(data);
    // Переключились на другую группу: ранее открытый канал ей не принадлежит.
    // Сбрасываем его вместе с применением новых данных (React батчит оба
    // апдейта в один рендер), поэтому «пустой чат» не успевает мелькнуть.
    if (prevLoaded && prevLoaded !== data.id) setSelectedChannel(null);
  }
  setGroupSwitching(false);
}, []);
```

> 📖 **Почему через `ref`, а не через сравнение стейта.** `fetchGroupDetail`
> вызывается не только при переключении, но и на «тихих» обновлениях **той же**
> группы: раз в 30 сек при открытой панели участников, по сокет-событиям
> `group-updated` / `profile-updated`, после восстановления сети. Во всех этих
> случаях `data.id` совпадает с уже загруженной группой, `prevLoaded === data.id`,
> и канал остаётся на месте. Сбрасываем строго при **реальной** смене группы.

### 2. Убрали ранний сброс канала из эффекта

Раньше эффект на смену `selectedGroup` чистил канал немедленно. Теперь — нет:

```tsx
useEffect(() => {
  if (selectedGroup) {
    // FIX-GRPSWITCH2: канал НЕ сбрасываем здесь. Иначе, пока грузятся данные
    // новой группы, колонка чата успевает перерисоваться в «пустой» экран
    // (инфо-панель/приветствие) — то самое мелькающее окно. Сброс канала
    // теперь происходит атомарно в fetchGroupDetail, когда приходят данные
    // уже другой группы: старый чат гаснет и сразу сменяется новым.
    fetchGroupDetail(selectedGroup);
  }
}, [selectedGroup, fetchGroupDetail]);
```

Косметический `groupSwitching` (притемнение на время загрузки) **оставлен** — он
всё так же даёт мягкий фейд, но теперь под ним нет ложного кадра.

**Ручное QA — пошагово:**

1. Запустить веб: `npm run dev`, открыть `/connect`, войти.
2. Иметь минимум **две группы**, в каждой — хотя бы один текстовый канал.
3. Открыть **канал A1** в группе A (в Колонке 3 виден чат).
4. Кликнуть по **группе B** в списке слева.
5. **Ожидаемо:** старый чат плавно гаснет и **сразу** сменяется экраном группы B
   (инфо-панель B либо её первый канал). Инфо-панель/приветствие **группы A**
   мелькать больше **не должны**.
6. Повторить быстрыми кликами A→B→A несколько раз — промежуточного «пустого окна»
   быть не должно.
7. **Регрессия-чек:** открыть панель «Участники» и подождать >30 сек, находясь в
   канале, — тихое обновление данных группы **не должно** выкидывать вас из
   открытого канала (канал сбрасывается только при смене группы, не на refresh).
8. **Deep-link чек:** перейти по уведомлению вида `?group=…&channel=…` — нужный
   канал по-прежнему открывается автоматически.

## Alternatives

**Альтернатива 1. Гейтить fallback по совпадению `groupDetail.id === selectedGroup`.**
Показывать инфо-панель/приветствие только когда данные соответствуют выбранной
группе.

| Плюсы | Минусы |
|-------|--------|
| Не трогает поток сброса канала | Во время загрузки `groupDetail.id !== selectedGroup` → провалится в `ConnectWelcome` = **другое** мелькающее окно |
| Логика «показывай только согласованное» декларативна | Нужно всё равно где-то держать старый канал, иначе колонка пустеет |

**Альтернатива 2. Замораживать снапшот старой колонки на время загрузки.**
Рендерить последний «хороший» экран из отдельного `useRef`, пока грузится новый.

| Плюсы | Минусы |
|-------|--------|
| Идеально гладкий переход без единого лишнего кадра | Заметно больше кода и состояния ради редкого зазора в 1–2 кадра |
| Работает даже при очень медленной сети | Риск показать «замороженный» устаревший экран дольше нужного |

Выбранное решение проще обоих и убирает первопричину (ранний сброс канала), а не
маскирует симптом.

## Quiz

<details>
<summary>1. Почему притемнение до <code>opacity-40</code> (FIX-GRPSWITCH) не убрало мелькание?</summary>

**Правильный ответ: Б.**

- **А.** Потому что `transition-opacity` слишком медленный. — *Неверно: длительность
  тут ни при чём, проблема в самом факте отрисовки лишнего кадра.*
- **Б. Потому что «пустое окно» всё равно отрисовывается — просто на 40 % яркости.**
  — *Верно: opacity меняет прозрачность, но промежуточный `GroupInfoPanel(A)`
  всё равно попадает в кадр.*
- **В.** Потому что `pointer-events-none` блокирует рендер. — *Неверно:
  `pointer-events` влияет только на клики, не на отрисовку.*
</details>

<details>
<summary>2. Что конкретно было первопричиной мелькающего окна?</summary>

**Правильный ответ: В.**

- **А.** Медленный ответ `/api/groups/:id`. — *Неверно: сетевой зазор существует
  всегда, но сам по себе окна не рисует.*
- **Б.** `MessageArea` размонтировался при смене канала. — *Неверно: он
  переиспользуется (нет `key`), это не источник «окна».*
- **В. Ранний `setSelectedChannel(null)` в эффекте — канал обнулялся, пока
  `groupDetail` ещё указывал на старую группу.** — *Верно: канал `null` +
  старый `groupDetail` → рисуется инфо-панель старой группы.*
</details>

<details>
<summary>3. Зачем понадобился <code>loadedGroupIdRef</code>, а не сравнение состояния?</summary>

**Правильный ответ: Б.**

- **А.** Чтобы избежать лишнего перерендера от `useState`. — *Неверно/второстепенно:
  дело не в перерендере ref-а.*
- **Б. Чтобы отличить реальное переключение группы от «тихого» refresh той же
  группы и сбрасывать канал только в первом случае.** — *Верно: на refresh
  `data.id` совпадает с загруженной группой → канал не трогаем.*
- **В.** Потому что `groupDetail` недоступен внутри `useCallback`. — *Неверно:
  доступен, но замыкание было бы устаревшим; суть же в различении switch vs refresh.*
</details>

<details>
<summary>4. Почему <code>setGroupDetail(data)</code> и <code>setSelectedChannel(null)</code> не дают промежуточный кадр?</summary>

**Правильный ответ: А.**

- **А. React 18+/19 автоматически батчит оба `setState` в асинхронном колбэке в
  один рендер.** — *Верно: после `await` обновления объединяются, промежуточного
  состояния нет.*
- **Б.** Потому что они в `useCallback`. — *Неверно: `useCallback` мемоизирует
  функцию, к батчингу отношения не имеет.*
- **В.** Потому что `ref` обновляется синхронно. — *Неверно: обновление ref-а не
  влияет на объединение `setState`.*
</details>

<details>
<summary>5. Какое поведение проверяет регрессия-тест с панелью «Участники» (>30 сек)?</summary>

**Правильный ответ: В.**

- **А.** Что список участников обновляется. — *Не то: это не про мелькание.*
- **Б.** Что сокет переподключается. — *Не то.*
- **В. Что периодический `fetchGroupDetail` той же группы НЕ сбрасывает открытый
  канал.** — *Верно: сброс должен срабатывать только при смене группы, иначе
  refresh каждые 30 сек выкидывал бы пользователя из канала.*
</details>
