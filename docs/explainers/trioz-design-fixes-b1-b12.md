# TrioZ — исправления багов дизайна (B1–B12)

*Explainer к PR с фикс-пакетом заметных (🔴 B1–B6) и средних (🟡 B7–B12) багов
интерфейса. Затронуто 14 файлов, все в `apps/web`. База данных не трогается,
миграции не нужны.*

---

## Background

### Для тех, кто видит проект впервые

TrioZ — это монорепозиторий (`npm workspaces`) из трёх частей:

- **`apps/web`** — приложение на **Next.js 16 / React 18**. Именно здесь живёт весь
  интерфейс, и именно его касается этот PR.
- **`apps/desktop`** — тонкая **Electron**-оболочка, которая загружает тот же
  веб-интерфейс в отдельном окне.
- **`packages/shared`** — общий контракт Socket.IO между вебом и сервером.

Раздел `/connect` — это «Discord-подобная» часть продукта: слева вертикальная
*рельса* (NavRail) с иконками разделов, рядом список каналов, а справа — область
сообщений `MessageArea`. Стилизация построена на **Tailwind CSS** плюс наборе
CSS-переменных в `apps/web/src/app/globals.css` (префикс `--cn-*` для темы
Connect, `--tz-*` для общих величин оболочки).

> [!NOTE]
> **Электрон-оболочка vs. веб.** Один и тот же React-код работает и в браузере,
> и внутри Electron. Чтобы прятать «веб-only» элементы (например, ссылки
> навигации, которых в десктопе быть не должно), в проекте есть анти-flash-скрипт
> в `<head>` (`layout.tsx`), который ещё до первой отрисовки помечает документ
> классом. Раньше это делалось позже, из `useEffect`, — отсюда «вспышка».

### Узкий контекст этого PR

За интерфейсом накопился список из двенадцати дефектов — от лишнего скроллбара
до недоступности меню с клавиатуры. Все они собраны в исходном архиве
`docs/explainers/trioz-design-fixes.zip` (файл `FIXES-README.md`). Этот PR
применяет ровно те правки: никакой новой функциональности, только починка
существующего поведения и наведение порядка в нескольких «магических числах».

## Intuition

Двенадцать багов удобно сгруппировать по сути в четыре идеи.

**1. Одна высота навбара вместо магической `64px`.** Раньше высота навигационной
панели была «зашита» числом `64` в разных местах, а экраны загрузки на `/connect`
использовали `min-h-screen` (= `100vh`). `100vh` не вычитает высоту навбара —
поэтому «экран + навбар» оказывались чуть выше окна, и появлялся вертикальный
скроллбар на пустой странице. Решение: одна переменная `--tz-navbar-h: 64px` и
высота вида `calc(100vh - var(--tz-navbar-h) - …)`.

**2. Не монтировать мобильное и десктопное дерево одновременно.** Вёрстка
`/connect` рендерила и мобильную ветку (`md:hidden`), и десктопную
(`max-md:hidden`) — CSS прятал ненужную, но React монтировал **обе**. Значит
`MessageArea` жил в DOM дважды, открывал два веб-сокета и дублировал запросы.

> [!IMPORTANT]
> Спрятать элемент через CSS (`display:none`) — **не то же самое**, что не
> смонтировать его в React. Скрытый через CSS компонент по-прежнему выполняет
> эффекты, подписки и сетевые запросы. Чтобы убрать двойные сокет-подписки,
> ветку нужно именно *не рендерить*.

Приём — «поднять» медиазапрос в JavaScript:

```tsx
const [isDesktopViewport, setIsDesktopViewport] = useState<boolean | null>(null);
useEffect(() => {
  const mq = window.matchMedia("(min-width: 768px)");
  const update = () => setIsDesktopViewport(mq.matches);
  update();                                   // синхронизируемся при монтировании
  mq.addEventListener("change", update);      // и на каждый ресайз через границу
  return () => mq.removeEventListener("change", update);
}, []);
```

Начальное значение `null` — это «мы ещё не знаем» на первом рендере (важно для
SSR/гидратации): пока `null`, рендерятся **обе** ветки, как раньше, а CSS прячет
лишнюю — верстка не «прыгает» и гидратация не рушится. После первого эффекта
остаётся ровно одна:

| `isDesktopViewport` | мобильная ветка (`!== true`) | десктопная ветка (`!== false`) |
|---|---|---|
| `null` (до эффекта / SSR) | рендерится | рендерится |
| `false` (узкий экран) | рендерится | скрыта |
| `true` (широкий экран) | скрыта | рендерится |

**3. Единая шкала z-index вместо хаоса `9998 / 9999 / 200 / 100`.** Когда всё
подряд объявлено «поверх всего» одинаковым `9999`, порядок наложения перестаёт
что-либо значить, и оверлеи дерутся непредсказуемо. PR вводит осмысленную шкалу и
раскладывает по ней все оверлеи:

```
40 — плавающие элементы страницы     50 — навбар / дропдауны
60 — модалки                          70 — вложенные модалки / оверлеи
80 — полноэкранная демонстрация       85 — мини-профиль
90 — лайтбокс / сплэш                 95 — системные индикаторы
```

Относительный порядок внутри каждой связки сохранён — меняются только абсолютные
числа, поэтому лайтбокс по-прежнему над модалкой, а мини-профиль — над
демонстрацией экрана.

**4. Доступность: клавиатура, фокус и контраст.** Меню пользователя открывалось
только по наведению мыши и «проваливалось» в зазор `mt-1` между кнопкой и
выпадашкой; кнопки управления каналами были видимы только на `hover`; тускло-серый
`--cn-muted` не проходил WCAG AA. Идея правок: заменить `mt-1` на внутренний
`pt-1` (зазор становится частью кликабельной области), открывать меню по
`group-focus-within`, показывать скрытые кнопки на `focus-visible`, дать видимую
рамку фокуса и поднять контраст текста.

## Code

Изменения удобно читать теми же четырьмя группами.

### Группа 1 — высота навбара и лишний скроллбар (B1, B18)

`globals.css` получает переменную и правило резервирования полосы прокрутки:

```css
:root { --tz-navbar-h: 64px; }

@media (min-width: 768px) {
  html { scrollbar-gutter: stable; } /* FIX-B11: контент не сдвигается на 6px */
}
```

`connect/page.tsx` — экраны загрузки и «не авторизован» переходят с `min-h-screen`
на высоту с вычетом навбара (а на мобильных используют `100dvh`):

```tsx
<div className="min-h-[calc(100vh-var(--tz-navbar-h)-var(--tz-desktop-inset-bottom,0px))] max-md:min-h-[100dvh] …">
```

### Группа 2 — единственное дерево на `/connect` (B3)

В `connect/page.tsx` добавлен хук `matchMedia` (см. Intuition), а обе ветки
обёрнуты в условия:

```tsx
{/* Mobile view */}
{isDesktopViewport !== true && ( <div className="md:hidden …"> … </div> )}

{/* Desktop: COL 2 + COL 3 */}
{isDesktopViewport !== false && ( <div className="max-md:hidden …"> … </div> )}
```

### Группа 4 — доступность (B4, B5, B6, B12) и мелочи (B2, B7, B8, B9)

`Navbar.tsx` — меню пользователя чинится структурно: внешний `<div>` становится
позиционером с внутренним отступом `pt-1` (курсор больше не «проваливается»), а
видимая карточка — вложенным `<div>`. Плюс открытие по фокусу:

```tsx
{/* было: mt-1 + один div с фоном; z-50 */}
<div className="absolute right-0 top-full pt-1 w-44 opacity-0 invisible
     group-hover:opacity-100 group-hover:visible
     group-focus-within:opacity-100 group-focus-within:visible
     transition-all duration-150 z-50">
  <div className="bg-white dark:bg-neutral-900 border … rounded-xl shadow-lg overflow-hidden">
    … пункты меню …
  </div>
</div>
```

`layout.tsx` — анти-flash-скрипт помечает Electron-оболочку **до** отрисовки:

```js
if (window.triozDesktop || navigator.userAgent.indexOf('Electron') !== -1)
  d.classList.add('tz-desktop');
```

а `globals.css` мгновенно раскладывает контролы через CSS (без ожидания
`useEffect`):

```css
html.tz-desktop .tz-web-only     { display: none !important; }
html.tz-desktop .tz-navbar-inner { max-width: none; }
html.tz-desktop .tz-navbar-right { margin-left: 0 !important; margin-right: auto; }
```

Соответствующие классы (`tz-web-only`, `tz-navbar-inner`, `tz-navbar-right`)
добавлены в `Navbar.tsx`.

`globals.css` — контраст и фокус:

```css
--cn-muted: #8b93a3;               /* FIX-B5: было #4a5568 (~3.2:1) → ~4.9:1, WCAG AA */

.cn-nav-btn.active::before { left: -12px; } /* FIX-B2: -16px срезался overflow-hidden */

@media (max-width: 767.98px) { … } /* FIX-B7: не пересекается с Tailwind md: (768px) */

.cn-nav-btn:focus-visible,
.cn-channel-btn:focus-visible,
.tz-msg-toolbar button:focus-visible { outline: 2px solid var(--cn-accent); outline-offset: 2px; }
```

`ChannelSidebar.tsx` — скрытые до наведения кнопки (создание/удаление каналов,
mute и т.п.) получают `focus-visible:opacity-100` / `focus-within:opacity-100`,
чтобы быть доступными с клавиатуры.

`MessageArea.tsx` — у скролл-контейнера `p-4` → `px-4 pb-4 pt-5`, чтобы hover-тулбар
первого сообщения (сдвинут на `top: -14px`) не обрезался сверху (B8).

`PanelResizer.tsx` — ресайзер списка каналов переписан с мышиных событий на
**Pointer Events** + `setPointerCapture` (работает на сенсорных экранах и стилусе,
добавлен `touch-action: none`), а жёсткий сброс на `240` заменён новым необязательным
пропом `resetWidth` (по умолчанию `240`), значение которого клампится в `[min, max]`
(B9):

```tsx
export default function PanelResizer({ width, min, max, onChange, resetWidth = 240 }: PanelResizerProps) {
  const onPointerDown = useCallback((e: React.PointerEvent<HTMLDivElement>) => {
    e.preventDefault();
    dragRef.current = { pointerId: e.pointerId, startX: e.clientX, startW: width };
    e.currentTarget.setPointerCapture(e.pointerId);
    …
  }, [width]);
  const onDoubleClick = useCallback(
    () => onChange(Math.min(max, Math.max(min, resetWidth))), [min, max, onChange, resetWidth]);
  …
}
```

> [!NOTE]
> **Обратная совместимость `PanelResizer`.** Проп `resetWidth` необязательный со
> значением по умолчанию `240`, поэтому существующий вызов в `connect/page.tsx`
> продолжает работать без изменений.

## Quiz

<details>
<summary>1. Почему на пустых экранах загрузки <code>/connect</code> появлялся вертикальный скроллбар?</summary>

- **A.** Контента было больше, чем помещается на экран.
- **B.** ✅ Экраны использовали `min-h-screen` (`100vh`), которое не вычитает высоту навбара, поэтому «навбар + экран» оказывались выше окна.
- **C.** Tailwind по умолчанию добавляет вертикальный скролл.
- **D.** Из-за `scrollbar-gutter: stable`.

**Верно B.** `100vh` — это вся высота окна, без учёта навбара; сумма превышала
высоту вьюпорта. Решение — `calc(100vh - var(--tz-navbar-h) - …)`. Ответ D,
наоборот, описывает правку B11, которая *убирает* сдвиг контента, а не создаёт
скролл.
</details>

<details>
<summary>2. Зачем начальное значение <code>isDesktopViewport</code> сделано <code>null</code>, а не <code>false</code>?</summary>

- **A.** Чтобы сэкономить память.
- **B.** `false` вызвал бы ошибку типов.
- **C.** ✅ Чтобы на первом рендере (SSR/гидратация) отрисовались *обе* ветки, как раньше, и разметка сервера совпала с клиентом — гидратация не ломается.
- **D.** `null` отключает медиазапрос.

**Верно C.** Условия `!== true` и `!== false` при `null` оба истинны, поэтому до
первого эффекта рендерятся обе ветки (CSS прячет лишнюю). Если стартовать с
`false`, сервер и клиент могли бы отрисовать разное и вызвать ошибку гидратации.
</details>

<details>
<summary>3. Почему двойное CSS-скрытие ветки (<code>md:hidden</code>) не решало проблему двойных сокет-подписок?</summary>

- **A.** `display:none` тормозит анимации.
- **B.** ✅ Скрытый через CSS React-компонент всё равно смонтирован: он выполняет эффекты, подписки и запросы. `MessageArea` дважды в DOM = два сокета.
- **C.** Tailwind не поддерживает `hidden` на десктопе.
- **D.** Сокеты вообще не зависят от DOM.

**Верно B.** CSS прячет пиксели, но не размонтирует компонент. Чтобы убрать
двойные подписки, ветку нужно именно не рендерить — что и делает условие на
`isDesktopViewport`.
</details>

<details>
<summary>4. Что именно чинит замена <code>mt-1</code> на <code>pt-1</code> в меню пользователя навбара?</summary>

- **A.** Меняет цвет фона меню.
- **B.** ✅ Убирает «мёртвый» зазор между кнопкой и меню: внешний отступ (`mt`) не кликается, а внутренний (`pt`) входит в наведение — курсор больше не «проваливается», и меню не мерцает.
- **C.** Делает меню шире.
- **D.** Отключает анимацию.

**Верно B.** `margin` создаёт визуальный, но не наводимый зазор — при переходе
курсора мышь попадала «между» элементами, `:hover` слетал, меню моргало.
Внутренний `padding` делает промежуток частью области наведения.
</details>

<details>
<summary>5. Ломает ли новый проп <code>resetWidth</code> в <code>PanelResizer</code> существующие вызовы?</summary>

- **A.** Да, теперь его нужно передавать всегда.
- **B.** ✅ Нет: проп необязательный со значением по умолчанию `240`, поэтому текущий вызов работает без изменений; при этом сброс теперь клампится в `[min, max]`.
- **C.** Да, изменилась сигнатура `onChange`.
- **D.** Нет, потому что компонент больше нигде не используется.

**Верно B.** `resetWidth?: number = 240` сохраняет прежнее поведение по
умолчанию. Ответ D неверен — компонент используется в `connect/page.tsx`.
</details>
