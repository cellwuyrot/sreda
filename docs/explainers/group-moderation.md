# Модерация группы: одно правило и то, что из него следует

Точка входа — правый клик по имени или аватару в чате. Состав меню зависит от
того, кто смотрит и на кого.

## Правило

**Действие против другого участника требует строго большего ранга.**

```
OWNER 4  >  ADMIN 3  >  MODERATOR 2  >  MEMBER 1
```

Равные ранги не трогают друг друга, себя не трогает никто, владелец
неприкосновенен и уходит только через передачу владения.

Отдельных запретов вида «модератор не может забанить администратора» в коде
нет и не должно появляться: они следуют из рангов. Модератор не забанит
модератора, потому что 2 не больше 2; администратор забанит модератора, потому
что 3 больше 2. Если однажды понадобится исключение — сначала стоит проверить,
не проще ли поправить ранг.

Живёт правило в `apps/web/src/lib/groupModeration.ts`. Файл намеренно без
единого импорта: только так его берут и серверные маршруты, и клиентские
компоненты. **Своих копий `ROLE_RANK` больше заводить нельзя.** До этого модуля
карта рангов была скопирована в семь файлов, и копии уже разошлись: в
`MessageArea.tsx` в неё добавили ключ `SITE_ADMIN`, который применялся к полю,
никогда такого значения не принимающему, — то есть просто не работал.

## Мини-профиль вместо подписей в ленте

Ник, сайтовая роль и цветные теги убраны из шапки сообщения. В ленте они
повторялись у каждого автора и занимали половину строки, а узнать их всё равно
можно было только вчитавшись. Теперь всё это — мини-профиль по правому клику:
аватар, имя, `@ник`, роль и теги.

**Мини-профиль свой у каждого сообщества.** Роль и теги берутся из членства в
той группе, где открыт чат, поэтому один и тот же человек выглядит в разных
сообществах по-разному — там владелец, здесь участник. Подпись «в этом
сообществе» под значками существует ровно затем, чтобы это не читалось как
глобальный статус.

**Окно одно.** Раньше их было два: карточка `MiniProfile` по наведению на
аватар и меню действий по правому клику — они открывались независимо и налезали
друг на друга. Теперь и наведение, и клик, и правая кнопка открывают одну и ту
же карточку: баннер, аватар, имя, статус «в сети / был(а)», `@ник`, роль, теги
и ниже — действия.

Таймеры показа и скрытия держит `MessageArea`, а не карточка. Закрывать нужно
тогда, когда курсор ушёл И с аватара, И с самой карточки, а знать про оба места
может только общий владелец; карточка лишь сообщает наверх, что курсор вошёл
или вышел. Открытая кликом карточка по уходу курсора не закрывается — её
закрывают щелчком мимо или Escape.

Меню рисуется порталом в `document.body`. Раньше оно жило внутри дерева чата, и
его срезал ближайший предок с ограничением отрисовки: `position: fixed` внутри
такого предка ведёт себя как `absolute`, из-за чего нижние пункты уходили под
край переписки. Высота ограничена высотой экрана, лишнее прокручивается —
раскрытый список причин жалобы длиннее любого разумного окна.

## Кто что видит

| | MEMBER | MODERATOR | ADMIN | OWNER |
|---|---|---|---|---|
| Игнорировать | ✓ | ✓ | ✓ | ✓ |
| Пожаловаться | ✓ | ✓ | ✓ | ✓ |
| Удалить сообщение | — | ✓ | ✓ | ✓ |
| Удалить и ограничить | — | ✓ | ✓ | ✓ |
| Удалить и забанить | — | ✓ | ✓ | ✓ |
| Очистить сообщения | — | ✓ | ✓ | ✓ |
| Таймаут и снятие | — | ✓ | ✓ | ✓ |
| Исключить из группы | — | ✓ | ✓ | ✓ |
| Заблокировать | — | ✓ | ✓ | ✓ |
| Теги | — | — | ✓ | ✓ |
| Роль в группе | — | — | ✓ | ✓ |

Каждая строка читается с поправкой на главное правило: модератор видит эти
пункты только на участнике, администратор — на участнике и модераторе,
владелец — на всех.

Роли выдаются только строго ниже собственной: владелец назначает вплоть до
администратора, администратор — до модератора. `OWNER` не выдаётся никогда,
иначе в группе оказалось бы два владельца.

## Клиент не решает, клиент подсказывает

`allowedActions()` вызывается и в меню, и (через `canActOn`) в маршрутах. Меню
не рисует пункт, который сервер всё равно отклонит, — но разрешение выдаёт
сервер. Раньше это расходилось: модератору показывали «Заблокировать» на
администраторе, и он узнавал о правиле по красной надписи.

## Решения, которые стоит знать

**«Удалить и забанить» уносит одно сообщение, а не всю переписку.** Кнопку
жмут в том числе по одной грубой реплике, и человек не ждёт, что вместе с ней
исчезнут сутки истории. Массовая чистка — отдельный пункт «Очистить
сообщения» с явным выбором окна (10 / 50 сообщений, час, сутки) и отдельным
подтверждением. Необратимое массовое удаление должно требовать отдельного
решения.

**Удаление чужого сообщения пишется в журнал.** Иначе «удалить и забанить»
стало бы способом бесследно подчистить историю. Своё сообщение автор удаляет
молча — это не мера воздействия.

**До этой правки модератор не мог удалить чужое сообщение вообще.** В
`DELETE /api/messages` стояла проверка «автор или `user.role === "ADMIN"`», где
`user.role` — сайтовая роль. Владелец группы не мог удалить сообщение у себя,
а администратор платформы мог удалить любое где угодно. Поэтому пункта не было
и в меню: его нечем было обслужить.

**Новые действия дописаны в тот же журнал.** `logGroupAction` уже вызывался из
банов, киков, смены ролей, тайм-аутов и приглашений; добавились
`message.delete`, `message.purge`, `report.resolve` и `report.dismiss`.
`GroupAuditAction` — закрытый union, поэтому каждое новое действие приходится
объявлять явно: забыть его нельзя, сборка не пропустит.

**Жалоба — вторая и последняя мера обычного участника.** Игнор защищает его
одного и никому ничего не сообщает; жалоба зовёт того, кто может вмешаться.
Без неё «обычный участник может только игнорировать» означало бы, что позвать
на помощь нельзя вообще.

**Жалоба хранит снимок текста.** `GroupReport.excerpt` заполняется в момент
подачи, потому что нарушитель удаляет написанное первым — без снимка модератор
открыл бы пустую карточку. По той же причине `messageId` не имеет внешнего
ключа на `Message`: жалоба должна пережить удаление сообщения, ради которого её
и написали.

**Разбор жалобы не принимает мер.** `PATCH /reports/[reportId]` только закрывает
карточку; бан, тайм-аут и удаление делаются обычными маршрутами. Одна жалоба
может кончиться и баном, и ничем, а очередь должна пустеть в обоих случаях.

**Игнор переехал на сервер.** Раньше список жил в `localStorage` вкладки:
терялся при очистке браузера, не переезжал на другое устройство и не действовал
в десктоп-клиенте. Модель `UserIgnore`, маршрут `/api/ignores`. При первом
заходе старый локальный список переносится наверх и ключ удаляется, чтобы у
тех, кто уже кого-то скрыл, ничего не пропало.

Маршрут игнора не групповой намеренно: игнорируют человека, а не его роль в
конкретном сообществе.

## Что где лежит

| Действие | Маршрут |
|---|---|
| Удалить сообщение | `DELETE /api/messages?messageId=` |
| Очистить сообщения | `POST /api/groups/[id]/moderation/purge` |
| Таймаут и снятие | `POST` / `DELETE /api/groups/[id]/members/[memberId]/timeout` |
| Исключить | `DELETE /api/groups/[id]/members/[memberId]` |
| Роль в группе | `PATCH /api/groups/[id]/members/[memberId]` |
| Забанить и разбанить | `/api/groups/[id]/bans`, `/api/groups/[id]/bans/[banId]` |
| Жалобы | `/api/groups/[id]/reports`, `/api/groups/[id]/reports/[reportId]` |
| Игнор | `/api/ignores` |
| Журнал | `GET /api/groups/[id]/audit` |

Очередь жалоб — «Настройки группы → Жалобы», рядом с «Аудитом». Обе вкладки
видны модератору и выше.
