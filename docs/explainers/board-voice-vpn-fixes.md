# Тулбар сообщения, права в голосовом канале и учёт трафика соединения

Разбор четырёх правок: почему каждая из них была нужна, что именно ломалось и как
это проверить руками. Читать можно с любого раздела — они независимы.

---

## Background

### Для тех, кто в проекте недавно

Раздел `/connect` — это мессенджер **TZ.Connect**: сообщества («группы») с
каналами трёх видов (текстовые, голосовые, холсты), личные переписки и голосовая
связь на WebRTC. Три детали устройства понадобятся ниже.

**Первая: голосовые комнаты живут в памяти сокет-сервера.** Прод запускает не
`next start`, а собственный `apps/web/server.ts` — он держит и Next.js, и
Socket.IO в одном процессе. Состав голосовых комнат лежит в обычном `Map`, а
API-маршруты обращаются к нему через функции, положенные в `globalThis`
(`__forceMuteUser`, `__kickVoiceChannel` и т. п.). Это не изящно, зато честно:
одно состояние, один процесс, никакой синхронизации между репликами.

**Вторая: звания в сообществе — числа.** `lib/groupModeration.ts` задаёт ранги
`MEMBER = 1`, `GUIDE = 1.5`, `MODERATOR = 2`, `ADMIN = 3`, `OWNER = 4`. Любая
мера модерации сводится к сравнению: актор должен быть **строго выше** цели.
Отдельно живут роли в самом проекте (`lib/roles.ts`): `USER`, `CONSULTANT`,
`EDITOR`, `ADMIN` — это администрация сайта, а не сообщества. Путать их нельзя,
и дальше это будет важно.

**Третья: узлы VPN работают «на вытягивание».** Главный сервер не командует
узлом. Узел сам приходит с отчётом на `POST /api/servers/report` и получает в
ответ **полный список своих пиров**, после чего приводит интерфейс WireGuard к
этому списку. Отсюда следствие, на котором держится вся эта часть: **право на
туннель проверяется в момент выдачи списка**, а не только при регистрации ключа.
Кончилась подписка — пир перестаёт попадать в список, и туннель отпадает сам.

> [!NOTE]
> **Пир** — запись «этот публичный ключ WireGuard пускаем в туннель». Приватного
> ключа пользователя на сервере не существует: пара рождается на устройстве, и
> наружу уезжает только публичная половина.

### Узко по делу

Каждый из четырёх багов живёт в своём месте:

| Баг | Где |
|---|---|
| Доска в групповом чате | `MessageArea` → `MessageHoverToolbar` → `BoardPickerModal` → `lib/boardBridge` → `WorkspaceCanvas` |
| Заглушение микрофона | ПКМ-меню в `ChannelSidebar` |
| Перенос между каналами | `useDragUser` + `/api/voice/move-user` |
| Расход и лимит трафика | `lib/connectionUsage` + `/api/servers/report` + `/api/vpn/me` |

## Intuition

### 1. Пикер холстов спрашивал не про то сообщество, а очередь — не про тот холст

У бага две половины, и первую успели закрыть в `main` до этой ветки (PR #135):
окно выбора холста спрашивает у сервера список
`/api/workspace/board-list?groupId=…`, и без `groupId` сервер честно отвечает
«личные холсты — вот, групповых — ноль»:

```
GET /api/workspace/board-list            → { personal: {...}, group: [] }
GET /api/workspace/board-list?groupId=g1 → { personal: {...}, group: [ ... ] }
```

Чат сообщества — единственное место, где групповые холсты вообще имеют смысл, —
собирал контекст без `groupId`. Теперь передаёт, и разделы в окне появились.

Здесь чинится вторая половина, из-за которой выбор в окне всё равно ничего не
решал. Она видна на игрушечном примере. Пусть в сообществе два раздела с
холстами: `canvas-1` («Планы») и `canvas-2` («Черновики»). Человек открыл
«Планы», а из чата отправил сообщение на холст «Черновиков». У элемента очереди
была только область — «групповой», — и его забирал тот холст, который открыт:

```
очередь: [ { scope: "group", boardId: "b7" } ]
открыт «Планы»  → забрал он.   Выбор «Черновиков» пропал молча.
```

Теперь у элемента есть адрес получателя, и чужой элемент **остаётся в очереди**
дожидаться своего холста — терять уже отправленное нельзя:

```
очередь: [ { scope: "group", targetChannelId: "canvas-2", boardId: "b7" } ]
открыт «Планы»      → не его, лежит дальше.
открыты «Черновики» → забрал.
```

### 2. Меню закрывалось от нажатия на собственную кнопку

Меню модерации показывается порталом в `document.body`, а закрывается
слушателем `mousedown` на `window`. Слушатель не смотрел, куда именно нажали:

```
mousedown на «Заглушить микрофон»
  → слушатель на window: setSidebarModMenu(null)
  → React снимает портал
  → mouseup приходит уже в пустоту
  → события click НЕ ВОЗНИКАЕТ ВООБЩЕ → onClick не вызван
```

Событие `click` рождается только если `mousedown` и `mouseup` пришлись на один
и тот же узел. Узла к этому моменту нет — значит, кнопки нет. Внешне это
выглядит как «нажимаю, и ничего»: ни ошибки, ни запроса в сети.

Рядом, в меню громкости голосовой панели, та же логика написана правильно —
там слушатель сначала спрашивает `ref.current.contains(e.target)`. Правка
переносит эту проверку в панель.

### 3. Перетаскивание обрывало себя, а сервер отказывал всем

К моменту этой ветки в `main` уже разрешили тащить участника модератору, который
сам в голосовом канале не сидит (`enabled: !!canManage || !!voiceActions`).
Это было нужное условие, но не достаточное: обе причины ниже оставались.

**Клиент.** Хук `useDragUser` хранил канал под курсором в состоянии React и он
же стоял в зависимостях эффекта, который вешает обработчики указателя:

```
pointerdown       → сеанс открыт
pointermove       → курсор над каналом → setOverChannelId("ch2")
                    → состояние изменилось → эффект перезапускается
                    → его cleanup вызывает reset() → СЕАНС СТЁРТ
pointerup         → сеанса нет, переносить нечего
```

Обрыв случался ровно в тот момент, когда курсор доходил до цели: пока тащишь по
пустому месту — сеанс жив, коснулся канала — умер.

**Сервер.** `/api/voice/move-user` проверял звание так:

```ts
if (!callerMembership || effectiveRank(callerMembership) < 30) → 403
```

Ранги в проекте — `1…4`. `4 < 30` истинно, поэтому «Перенести в канал» получал
`403` и у владельца сообщества. Порог из другой системы счисления — самая
незаметная разновидность ошибки: код читается как осмысленный.

### 4. Соединение: чем «ноль» отличается от «неизвестно»

Учёт трафика устроен так: узел присылает **накопительные** счётчики WireGuard,
главный сервер берёт прирост и складывает его в расход периода.

```
отчёт 1: rx = 1 000        lastRx = 0     → прирост 1 000  расход 1 000
отчёт 2: rx = 1 800        lastRx = 1 000 → прирост   800  расход 1 800
отчёт 3: rx =    50 (!)    lastRx = 1 800 → интерфейс перезапущен: прирост 50
```

Пока отчёты с полем `transfers` не приходят, расход в базе остаётся нулевым — и
клиент показывал «израсходовано 0 ГБ». Это не осторожная оценка, а уверенная
неправда: трафик в это время идёт, просто мимо счёта. Разница между «ноль» и
«неизвестно» здесь принципиальная, поэтому появилась отметка `usageUpdatedAt`,
и клиент теперь говорит «расход с узла ещё не приходил».

Второе. Лимит есть, и он один на обе подписки. Безлимит — это не «дорогая
подписка», а **роль в проекте**: администрации нужно проверять сервис, в том
числе прогоняя через него больше подписочного объёма. Одна функция на весь
проект:

```ts
isUsageUnlimited({ role: "ADMIN" })  // true  — администрация проекта
isUsageUnlimited({ role: "EDITOR" }) // false — редактор ведёт контент, не инфраструктуру
isUsageUnlimited({ role: "USER" })   // false — даже с Premium
```

Роль ровно одна, как и у премиума по роли (`lib/premium`). И речь именно об
администрации **проекта**: владелец или администратор сообщества здесь не
получает ничего — это разные иерархии, и путать их нельзя.

В `main` безлимит для `ADMIN` уже появился, но только в личном окне
(`/api/vpn/me`), где он ни на что, кроме надписи, не влияет: соединение снимает
и скорость режет **отчёт узла**, а он про это исключение не знал. Поэтому
правило переехало в общий модуль и применяется во всех трёх местах.

Третье, самое коварное. Клиент перед подъёмом туннеля ждёт, пока узел узнает о
его ключе, — иначе рукопожатия уходят в пустоту (WireGuard на неизвестный ключ
не отвечает вообще: ни отказа, ни ошибки, просто тишина). Признак «узел узнал»
считался так:

```
lastSeenAt узла  >  updatedAt записи пира
```

И вот что происходило в одном запросе отчёта:

```
T+0 мс   serverNode.update({ lastSeenAt: T })          ← отметка узла
T+8 мс   vpnPeer.update({ rxBytes: … })                ← учёт трафика
         @updatedAt → updatedAt = T+8  >  lastSeenAt = T
```

Проверка отравляла сама себя: после первого учтённого килобайта она не могла
стать истинной **никогда**. Первое включение проходило (пира на интерфейсе ещё
нет — счётчики по нему не приходят), а любое следующее упиралось в «Сервер не
успел принять доступ. Нажмите включение ещё раз через полминуты».

> [!IMPORTANT]
> Отсюда общее правило: `updatedAt` нельзя использовать как признак «пользователь
> что-то изменил», если по той же записи пишет фоновая телеметрия. Нужна
> отдельная отметка того события, которое действительно имеется в виду.

## Code

### Доска: чей холст и какой именно

Источник и получатель разъехались по разным полям. Раньше выбранный canvas-канал
записывался в `channelId` — то есть в поле источника, которое идёт в подпись
карточки, и подпись начинала врать (имя от чата, идентификатор от холста):

```ts
// MessageHoverToolbar.tsx
sendMessageToBoard({
  channelId: boardContext?.channelId,   // откуда сообщение — для подписи
  targetChannelId: sel.channelId,       // куда нести — пусто у личной среды
  boardId: sel.boardId,
  scope: sel.scope,
});
```

Одно правило адресации на очередь целиком — и на разбор накопившегося, и на
живую подписку:

```ts
// lib/boardBridge.ts
export function boardItemMatches(item, scope?, channelId?) {
  if (scope && boardItemScope(item) !== scope) return false;
  if (item.targetChannelId && item.targetChannelId !== channelId) return false;
  return true;
}
```

Элемент без адреса остаётся «для любого холста своей области»: иначе всё, что
люди отправили до этой правки, не забрал бы уже никто.

Холст сообщает, кто он: `<BoardInboxListener scope={remote ? "group" : "personal"}
channelId={remote?.channelId ?? null} />`.

И маршрут списка холстов перестал отвечать посторонним — по ответу видны
названия разделов и досок:

```ts
// api/workspace/board-list/route.ts
const role = await getGroupRole(session.user.id, groupId);
if (role) { /* … собираем холсты сообщества … */ }
```

### Меню модерации: закрываться только по нажатию мимо

```ts
// ChannelSidebar.tsx
const modMenuRef = useRef<HTMLDivElement | null>(null);

const close = (e: MouseEvent) => {
  if (modMenuRef.current?.contains(e.target as Node)) return;
  setSidebarModMenu(null);
};
window.addEventListener('mousedown', close);
```

Одна строка проверки — и все кнопки меню (заглушить микрофон, заглушить
микрофон + наушники, снять заглушение, перенести в канал, выгнать) начинают
работать. Права и доставку событий править не понадобилось: они были целы,
до них просто не доходило дело.

### Перетаскивание: состояние для разметки, реф для обработчиков

```ts
// useDragUser.ts
const overChannelRef = useRef<string | null>(null);   // для обработчиков
const [overChannelId, setOverChannelId] = useState(null); // для подсветки цели

// в pointermove:
overChannelRef.current = found;
setOverChannelId(found);

// в pointerup — реф, а не состояние:
const channelId = overChannelRef.current;

// зависимость на overChannelId убрана: cleanup эффекта больше не рвёт сеанс
}, [enabled, reset]);
```

Подсветка канала-цели по-прежнему идёт от состояния — там оно и нужно.

Порог звания на сервере взят из общей таблицы, как у соседних маршрутов:

```ts
// api/voice/move-user/route.ts
const callerRank = callerMembership ? effectiveRank(callerMembership) : 0;
if (callerRank < ROLE_RANK.GUIDE) return 403;

const targetRank = targetMembership ? effectiveRank(targetMembership) : ROLE_RANK.MEMBER;
if (targetRank >= callerRank) return 403;
```

Событие цели продублировано прямой доставкой через сокет-сервер — тем же
способом, каким это уже сделано для принудительного заглушения:

```ts
// server.ts
(globalThis as Record<string, unknown>).__moveVoiceUser = (targetUserId, channelId, channelName) => {
  for (const sid of Array.from(userSockets.get(targetUserId) ?? [])) {
    io.to(sid).emit("voice:force-join", { channelId, channelName });
  }
};
```

### Соединение: одно правило безлимита, отметка свежести, честная проверка

```ts
// lib/connectionUsage.ts
export function isUsageUnlimited(subject?: { role?: string | null } | null): boolean {
  return isAdminRole(subject?.role);   // только администрация проекта
}

export function usageView(peer, settings, now = new Date(), unlimited = false): UsageView {
  const limitBytes = !unlimited && settings.trafficLimitGb > 0
    ? settings.trafficLimitGb * BYTES_IN_GB
    : 0;
  …
  return { …, unlimited: limitBytes === 0, measuredAt: measuredAt?.toISOString() ?? null };
}
```

Список пиров для узла — единственная точка, через которую доступ существует;
там же и лимит:

```ts
// api/servers/report/route.ts
.filter((peer) => isPeerEntitled(peer.user))
.filter((peer) => !isTrafficBlocked(peer, vpnSettings, new Date(), isUsageUnlimited(peer.user)))
```

Отметка свежести ставится тем же запросом, что и цифры:

```ts
data: expired
  ? { rxBytes: deltaRx, txBytes: deltaTx, lastRx: rawRx, lastTx: rawTx,
      usageResetAt: measuredAt, usageUpdatedAt: measuredAt }
  : { rxBytes: peer.rxBytes + deltaRx, txBytes: peer.txBytes + deltaTx,
      lastRx: rawRx, lastTx: rawTx, usageUpdatedAt: measuredAt }
```

Проверка «узел узнал о ключе» переведена на новое поле:

```ts
// api/vpn/me/route.ts
const peerApplied = !!peer.node.lastSeenAt
  && peer.node.lastSeenAt.getTime() > peer.configAt.getTime();
```

`configAt` меняется ровно там, где меняется конфигурация: при регистрации ключа
(`POST`) и при переезде на другой сервер (`PATCH`). Миграция —
`20260929000000_vpn_usage_freshness`, два `ADD COLUMN IF NOT EXISTS`; у уже
существующих записей `configAt` выравнивается по `createdAt`, потому что их ключ
узлу давно роздан.

Клиент перестал показывать ноль там, где данных нет:

```tsx
{measured ? `· израсходовано ${formatTraffic(usedBytes)}` : "· узел ещё не присылал расход"}
```

Тест на перетаскивание **падает на прежнем коде хука** — то есть проверяет
именно этот баг, а не совпадение:

```
× перетаскивание на другой канал вызывает перенос
× несколько каналов по пути: перенос идёт в тот, где отпустили
```

То же и с рангами: с прежним `< 30` тест «владелец переносит участника» ждёт
`200` и получает `403`.

Инварианты, закреплённые в отчёте узла:

- подписчик за лимитом выпадает из списка пиров (то есть туннель отпадает);
- у администрации проекта той же цифрой лимит не срабатывает;
- при правиле «снизить скорость» подписчик остаётся с потолком, администрация — без;
- отметка свежести учёта ставится вместе с цифрами.

Попутно починен **запуск проекта `jsdom`**: `setupDom.ts` подключал матчеры
входом `@testing-library/jest-dom/vitest`, который делает `import "vitest"` из
корневой `node_modules` — а `vitest` в этой монорепе стоит в `apps/web`. Падал не
отдельный тест, а весь проект целиком, до сбора файлов; в блокировке
зависимостей вдобавок не хватало `@testing-library/dom`. Теперь матчеры
подключаются вручную, и **все** тесты компонентов снова запускаются.

`npm run lint` — чисто. Сборка (`npm run build`) в этой среде не проверялась:
`prisma generate` требует загрузки движков, наружу доступа нет; за сборку
отвечает CI пул-реквеста.

### Как проверить руками

**Доска из группового чата.** Нужен канал-холст в сообществе (лучше два).
1. Наведитесь на сообщение в чате сообщества → значок доски в тулбаре.
2. В окне должны быть разделы: «Личная рабочая среда» и по разделу на каждый
   канал-холст. Раньше был только первый.
3. Выберите холст **второго** канала-холста, откройте первый — карточки там быть
   не должно. Откройте второй — карточка на месте.
4. То же из личной переписки: групповых разделов нет, подсказка объясняет почему.

**Заглушение в голосовом канале.** Нужны два аккаунта: у вас звание выше
(владелец/админ/модератор), у второго — участник.
1. Оба в одном голосовом канале.
2. ПКМ по участнику в боковой панели → меню.
3. «Заглушить микрофон» — у него микрофон гаснет и сам не включается.
4. «Заглушить мик + наушники» — гаснут оба, обратно тоже не включить.
5. «Снять заглушение» — возвращается.
6. Проверьте, что меню по-прежнему закрывается нажатием мимо и по `Esc`.

**Перенос между каналами.**
1. Два голосовых канала, участник в одном из них, вы — там же.
2. Зажмите ЛКМ на участнике и тащите на другой канал: канал-цель подсвечивается
   рамкой, строка участника бледнеет.
3. Отпустите — участник переезжает, у него открывается новый канал.
4. То же из меню: ПКМ → «Перенести в канал» → выбрать канал.
5. Проверьте отказ: попробуйте перенести равного или старшего по званию —
   ничего не происходит, в сети `403`.

**Соединение.** После развёртывания миграции.
1. Обычным аккаунтом с Premium: кнопка TZ → «Трафик». Если учёт с узла не
   приходил, будет написано прямо об этом, а не «израсходовано 0».
2. Прогоните через туннель заметный объём (хватит нескольких сотен мегабайт),
   подождите отчёт узла (пять секунд) и обновите плашку: расход и остаток
   должны сдвинуться. Если надпись «узел ещё не присылал расход» осталась —
   дело в агенте на узле (`apps/vpn`, поле `transfers` в отчёте), а не в сайте.
3. Аккаунтом администрации проекта (`ADMIN`): в плашке «без ограничения», а
   расход всё равно виден. Аккаунт с ролью `EDITOR` должен считаться по общему
   лимиту, как обычный подписчик.
4. Повторное включение: выключите туннель и включите снова, потом ещё раз.
   Прежде второе включение упиралось в «Сервер не успел принять доступ».
5. В `Админ → VPN` сводка «израсходовано» должна совпадать с суммой по людям, а
   администраторы проекта не считаться вышедшими за лимит.

## Alternatives

### Перенос участника: событие цели

| Прямая доставка через сокет-сервер (выбрано) | Только `emitToUser` из маршрута |
|---|---|
| **+** Работает независимо от того, нашёл ли маршрут `io` через `globalThis` | **+** Меньше кода, нет функции в `globalThis` |
| **+** Так же уже сделано у принудительного заглушения — один приём на оба случая | **+** Не нужно помнить про ещё одну «скрытую» точку связи |
| **−** Ещё одна функция в `globalThis` — связь, которую не видно по типам | **−** Молчаливый отказ: перенос «прошёл», а человека не перенесло |

### Признак «узел узнал о ключе»

| Отдельное поле `configAt` (выбрано) | Не двигать `updatedAt` при записи счётчиков |
|---|---|
| **+** Явно называет событие: «конфигурация сменилась» | **+** Без миграции и нового столбца |
| **+** Не зависит от того, кто ещё пишет в запись | **+** Меньше строк |
| **−** Миграция и два места, где поле надо не забыть выставить | **−** Опирается на то, что Prisma уважает явное значение `@updatedAt` — тихая зависимость от версии |
| | **−** Любой следующий фоновой писатель в эту таблицу вернёт баг |

### Адресация очереди холстов

| Адрес канала в элементе (выбрано) | Отдельная очередь на каждый холст |
|---|---|
| **+** Одна очередь, одно правило разбора | **+** Совсем нет «чужих» элементов в очереди |
| **+** Старые элементы без адреса продолжают доставляться | **−** Ключей в `localStorage` столько, сколько холстов; чистить их некому |
| **−** Нужно помнить, что источник и получатель — разные поля | **−** Миграция накопленного между схемами хранения |

## Suggested people to talk to

История этих файлов в `git log` идёт под одним автором (`ANDYCOULBOT`) и
однотипными сообщениями «описание изменений», поэтому по коммитам разделить
зоны ответственности нельзя. Ориентиры такие:

- **Голосовая часть** (`server.ts`, `contexts/VoiceContext.tsx`,
  `api/voice/*`) — самый плотный по состоянию домен: комнаты в памяти процесса,
  WebRTC-сигналинг, принудительные заглушения. Стоит обсудить с тем, кто
  занимался `FIX-FORCELOCK-V2`: там уже была ровно эта проблема — «событие не
  доходит до цели», — и опыт по доставке через `userSockets` пригодится, если
  всплывёт что-то ещё.
- **Соединение (VPN)** — расчёт лимита и отчёт узла завязаны на агент, который
  живёт вне репозитория выкладки (`apps/vpn` ставится на узел руками). Тому, кто
  разворачивал узлы, стоит подтвердить, что на них стоит агент с полем
  `transfers` в отчёте: без этого правка про «расход не приходил» будет
  правильно показывать, что учёта нет.
- **Рабочая среда (холсты)** — `WorkspaceCanvas` большой и с собственным
  хранением состояния; при добавлении новых видов элементов очереди лучше
  сверяться с тем, кто вводил `FIX-BOARDSCOPE`: разделение «личное/групповое»
  придумано именно там, и адрес канала — его прямое продолжение.

- **C.** У пользователя не было прав на групповые холсты.

- **D.** Элемент забирал тот холст, который в этот момент открыт. ✅

- **B.** Не хватало прав, и запрос отвечал 403.

  — Верно. `click` рождается только если `mousedown` и `mouseup` пришлись на один узел.
- **D.** Меню перекрывал другой элемент с большим `z-index`.
