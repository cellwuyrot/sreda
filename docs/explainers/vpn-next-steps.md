## Решения, которые НЕ надо пересматривать без причины

**Приватного ключа пользователя на сервере не существует.** Ни поля в модели,
ни приёма в API — `POST /api/vpn/me` отклоняет запрос, если в теле есть
`privateKey`. Пара создаётся на устройстве владельца, наружу уходит только
публичный ключ. Это осознанный контракт: администратор физически не может выдать
чужой доступ, потому что выдавать нечего.

**Выдача автоматическая, по признаку Premium.** Ручной формы «выдать по логину»
больше нет: она заставляла человека вручную повторять то, что система и так
знает, и привязывала выдачу к рабочему времени администратора. Право проверяет
`hasVpnEntitlement` (`isPremium` либо ADMIN), а пару ключей создаёт сам клиент при
открытии окна VPN. Прямое следствие контракта: профиль показывается **один раз**
и восстановлению не подлежит — только перевыпуск, который отключает прежнее
устройство.

**Свой X25519 в `lib/wgKeys.ts`, а не WebCrypto.** `crypto.subtle` умеет X25519
только с Chromium 133, а десктоп-оболочка собрана на Electron 33 (Chromium 130) —
то есть ровно там, где VPN нужнее всего, WebCrypto бы не сработал. Реализация —
лестница Монтгомери из RFC 7748 на BigInt, сверена контрольными векторами RFC
7748 §6.1 и с X25519 самого Node на случайных ключах. Постоянного времени
выполнения нет намеренно: скаляр рождается из CSPRNG на устройстве владельца и
умножается на фиксированную базовую точку, мерить тут нечего и некому.

**Точка подключения задаётся в панели, а не только на узле.** У WireGuard нет
URL: клиенту нужен `host:port` по UDP. Поле «Адрес» под http(s) для VPN-узла было
бессмысленным — введённый IP молча отбрасывался разбором `cleanUrl`. Теперь у
`ServerNode` есть `endpointHost`, и значение из панели главнее отчёта узла: узел
за NAT своего публичного адреса не знает.

**Связка «на вытягивание», а не «сверху вниз».** Узел сам приходит с отчётом и
получает список пиров и правил SNAT в ответе. Причина не в лени: главный сервер
хранит только хеш токена узла и физически не смог бы предъявить его для
обратного запроса. Побочные выгоды — узел работает за NAT, не требует входящего
порта и сертификата, а состояние сходится само после любого простоя.

**Выключатель сервиса — настоящий.** При `VpnSettings.enabled = false` узлам
уходит **пустой** список пиров, и туннели реально отпадают за минуту. Не
превращать это в косметическое скрытие интерфейса.

**Агент без зависимостей и без сборки.** Обычный `.mjs` на встроенных модулях
Node. Это удерживает правку `package-lock.json` тривиальной (две записи для
workspace) и позволяет поднять узел одной командой `node` на голой машине. Если
захочется добавить зависимость — сначала подумать, стоит ли она усложнения
установки и лок-файла.

## Осталось: генерация ключа в десктоп-клиенте (поднятие туннеля)

Веб-часть закрыта: ключ создаётся в клиенте, профиль выдаётся автоматически.
Осталось то, что браузер сделать не может в принципе — **поднять туннель**.

Что нужно:

1. `apps/desktop/src/main/vpn.ts`:
   - пара X25519 через встроенный `crypto.generateKeyPairSync("x25519")`;
     сырые 32 байта берутся из DER: приватный — хвост `pkcs8`, публичный — хвост
     `spki`, дальше base64;
   - приватная половина шифруется `safeStorage.encryptString` (ключница ОС) и
     ложится в `electron-store`. В открытом виде на диск не писать и в
     интерфейсе не показывать никогда;
   - `enroll()` — `POST /api/vpn/me` с публичным ключом, сессионная cookie
     берётся через `getCookieHeader` из `session.ts`;
   - `status()` — `GET /api/vpn/me` плюс признак «приватный ключ есть локально».
2. IPC: константы в `packages/shared` (там же, где остальные `IPC.*`), обработчики
   в `main/ipc.ts`, проброс в `preload/index.ts` рядом с существующим `api`.
3. Поднятие туннеля — отдельный, самый неприятный кусок: нужен установленный
   WireGuard и повышение прав (`wireguard.exe /installtunnelservice` на Windows,
   `wg-quick up` на Linux/macOS). Конфиг с приватным ключом собирать **в памяти**
   и писать только в защищённый каталог службы; пользователю ключ не показывать.

Три точки связки (`shared` → `ipc` → `preload`) — причина, по которой этот пункт
вынесен отдельно от серверных PR: правки мелкие, но забыть одну из них легко, и
тогда ломается сборка десктопа, которую CI не проверяет.

## Осталось: пункт 3 — автодеплой

**Не включать автодеплой по push, пока голосовое состояние живёт в памяти.**

В `apps/web/server.ts` состояние звонков и демонстраций (`voiceRooms`,
`screenShareState`, карты пиров) хранится в переменных процесса. Любой
`pm2 restart` рвёт активные звонки и показы экрана. Пока деплой ручной, момент
выбирает человек; автодеплой на каждый push начнёт ронять разговоры в случайные
минуты — то есть автоматизация ухудшит продукт.

Порядок:

1. Перенести состояние в Redis (он уже подключён — `src/lib/redis.ts`).
   Это рефакторинг по коду звонков, поэтому **отдельным PR**, где виден только он.
2. Затем workflow: `.github/workflows/deploy.yml`, SSH на главный сервер,
   команда та же, что в README —
   `git fetch && git reset --hard origin/main && npm ci && npm run migrate && npm run build && pm2 restart trioz`.
3. Узлы VPN обновлять **не на каждый релиз**: агент тянет состояние сам, его код
   меняется редко. Шаг обновления узлов вешать на изменения в `apps/vpn/**`.
   Полезно отдавать в ответе на отчёт ожидаемую версию агента и подсвечивать в
   панели «узел на старой версии».

## Масштабирование: что уже есть и что дальше

Сделано в #423: пул внешних адресов на узле (`ServerNode.publicIps`) и
закрепление адреса за пиром (`VpnPeer.exitIp`). Закрепление принципиально —
смена внешнего IP посреди сессии для банков выглядит как смена пользователя.

Что осталось по этой линии:

- **Своя `/24` на узел.** Сейчас подсеть туннеля зашита константой
  `VPN_SUBNET_PREFIX = "10.8.0"` в `src/lib/vpn.ts`, то есть 253 пира на узел, и
  подсети разных узлов совпадают. Пока узлы изолированы, этого достаточно
  (уникальность адреса в базе теперь тоже «в пределах узла» — см. ниже). Для
  маршрутизации между узлами понадобится поле `subnet` на `ServerNode` и выдача
  из пула `10.0.0.0/8`.
- **Выбор региона пользователем.** Распределение уже идёт на наименее
  загруженный узел с учётом вместимости; не хватает только выбора в интерфейсе.
- **Резидентные и мобильные адреса** — это не про наш узел: нужны сторонние
  поставщики, узел становится цепочкой прокси, появляется абонентская плата.
  Коммерческое решение, а не техническое; не начинать без явного запроса.

## Выбор режима маршрутизации — за человеком (01.08.2026)

**Что было.** Маршруты (`AllowedIPs` в профиле) задавались администратором одни на
всех: «весь интернет» либо «только сеть TZ». Человек при включении VPN не выбирал
ничего — доступ выдавался сам при открытии окна, с теми маршрутами, которые кто-то
однажды поставил в панели.

**Почему это неверно.** Это два разных решения, а не настройка сервиса: «сменить
свой внешний адрес» и «дотянуться до сервисов TZ, не заворачивая остальной трафик».
Выбор зависит от человека и даже от дня — за него его принимать нельзя. Заодно
второй вариант в панели был почти бесполезен: он выключал подмену адреса всем сразу.

**Как теперь.** Администратор задаёт **смысл** двух вариантов — какие подсети в
каждый входят (`VpnSettings.allowedIps` и `VpnSettings.serviceAllowedIps`), — а
человек выбирает **вариант** в своём окне VPN. Выбор хранится у пира
(`VpnPeer.routing`: `ALL` | `SERVICES`).

Следствия, которые важно не потерять:

- **Автовыдача убрана.** Раньше доступ выдавался сам при открытии окна; теперь
  сначала виден выбор, потом кнопка «Включить VPN». Иначе выбирать было бы уже
  поздно: профиль выдаётся один раз.
- **Смена режима — это перевыпуск профиля.** `AllowedIPs` живёт в конфиге на
  устройстве, а приватного ключа у нас нет — собрать новый профиль задним числом
  сервер не может даже при желании. Кнопка перевыпуска честно меняет подпись, когда
  выбранный режим отличается от текущего.
- **Режим хранится, а не выводится.** Без записи панель не смогла бы сказать, в
  каком режиме выдан доступ, а перевыпуск «просто потому что потерял файл» молча
  переключал бы человека на другой вид туннеля.
- **Неизвестный режим отклоняется маршрутом** (400), а не толкуется молча: тихо
  выдать «весь трафик» вместо запрошенного «только сервисы TZ» значит отправить
  трафик не туда, куда просили.
- Прежним пирам миграция ставит `ALL` — именно так они и работают. Молча переводить
  кого-то в другой режим нельзя: на устройстве лежит уже выданный профиль.

**Что стоит донастроить на сервере.** По умолчанию «только сервисы TZ» это лишь
подсеть туннеля (`10.8.0.0/24`). Чтобы вариант стал полезным, в панели
(**Сервисы и система → VPN → Какой трафик идёт через VPN**) в это поле дописываются
адреса самого проекта — публичные адреса главного и медиа-серверов.

## Проверка всей цепочки (01.08.2026): что было сломано

Разбор «от разворачивания узла до рабочего туннеля». Живой туннель в среде
разработки не поднять, поэтому цепочка разобрана по коду, спорные места проверены
экспериментом, а пригодное к проверке закрыто тестами (`src/lib/vpn.test.ts`,
`src/app/api/servers/report/route.test.ts`, `apps/vpn/src/rules.test.mjs`).

Пять поломок, все починены:

**1. Закрепление внешних адресов не работало НИ РАЗУ.** Агент вешал ссылку на свою
цепочку в конец `nat/POSTROUTING` (`-A`), а `MASQUERADE` из `wg0.conf` стоит там
раньше и завершает обход таблицы. Проверено счётчиками пакетов в отдельном сетевом
пространстве имён: у `MASQUERADE` 1 пакет, у `TRIOZ_VPN_SNAT` — 0. Теперь ссылка
вставляется первым правилом, а прежние ссылки снимаются — иначе починка не доехала
бы до уже работающих узлов. Порядок закреплён тестом: любая попытка вернуть
`-A POSTROUTING` красит его.

**2. Второй VPN-узел был неработоспособен.** Адрес выдавался из подсети узла
(`allocateAddress` считает занятость по `nodeId`), а уникальность `VpnPeer.address`
в базе была ГЛОБАЛЬНОЙ. Первый же пир на новом узле упирался в чужую запись и
получал отказ вместо доступа. Уникальность стала `@@unique([nodeId, address])` —
это соответствует реальности: `10.8.0.2` на двух узлах суть два разных туннеля.
Заодно снялся потолок «253 пира на всю систему».

**3. Переезд пира на другой узел падал.** При выключенном узле доступ выдаётся
заново, но прежний адрес сохранялся вслепую — в подсети нового узла он мог быть
занят. Теперь адрес сохраняется только при возврате на тот же узел
(`chooseAddress`).

**4. Доступ переживал своё основание.** Право проверялось только в момент выдачи.
Кончилась подписка, сняли премиум руками, забанили человека — пира по-прежнему
присылали узлу, и туннель работал. Проверка переехала туда, где список пиров
уходит на узел (`isPeerEntitled` в `/api/servers/report`): это единственное место,
через которое доступ вообще существует, поэтому любой путь потери права закрывает
туннель за минуту и без задачи по расписанию. Запись пира при этом остаётся —
вернулась подписка, вернулся доступ с тем же адресом.

**5. Правка пула внешних адресов оставляла мёртвые закрепления.** Убранный из
пула адрес оставался за пиром, узел делал SNAT на адрес, которого на машине больше
нет: туннель поднят, рукопожатие идёт, интернета нет. Теперь при смене пула
затронутые пиры получают адреса заново (`rebalanceExitIps`), а уцелевшие
закрепления не трогаются. Побочно решилось и обратное: пул, добавленный позже
пиров, раздаётся тем, у кого адреса не было.

Плюс мелочью: выдача доступа теперь проверяет бан (`checkBan`), а перевыпуск ключа
включает выключенного пира обратно — иначе профиль выдавался бы «в никуда».

## Что проверить нельзя без живого сервера

Честный список — здесь эти вещи не проверялись:

- поднятие интерфейса `wg-quick up wg0`, права, `net.ipv4.ip_forward`;
- фактическое рукопожатие клиента с узлом и прохождение трафика;
- работа обфусцированного форка (`awg`) — набор команд тот же, но бинарник другой;
- поведение при NAT у провайдера узла и MTU.

Первое, что стоит посмотреть на живом узле после обновления агента:
`iptables -t nat -L POSTROUTING -n -v --line-numbers` — `TRIOZ_VPN_SNAT` обязан
быть правилом №1, и его счётчик пакетов обязан расти.

## Известные ограничения, оставленные намеренно

- **Вместимость узла считает и тех, кто потерял право.** `pickVpnNode` смотрит на
  число записей пиров, а не на число выдаваемых узлу. Осознанно: запись держит
  адрес, чтобы вернувшаяся подписка не требовала перевыпуска. При большом числе
  просроченных подписок потолок узла придёт раньше времени — тогда понадобится
  уборка старых записей по возрасту.
- **Туннель по-прежнему поднимает сам человек** штатным клиентом WireGuard: в
  наших приложениях этого нет (см. раздел про десктоп выше). Профиль выдаётся,
  дальше — вручную.
