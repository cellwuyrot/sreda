# Модерация в голосовом канале: заглушение, снятие и перенос

Разбор второй правки по голосовым каналам. Первая (#136) починила то, что не
доходило до сервера; здесь — то, что доходило, но не имело обратного хода.

---

## Background

### Как устроена модерация голоса

Голосовые комнаты в TrioZ живут **в памяти сокет-сервера** (`apps/web/server.ts`):
`Map<channelId, Map<socketId, VoiceUser>>`. Ключ — socketId, то есть запись
участника существует ровно столько, сколько живёт его сокет. Отсюда всё
остальное в этом тексте.

Меры модерации применяются HTTP-маршрутами (`/api/voice/force-mute`,
`force-unmute`, `kick-voice`, `move-user`), а исполняются сокет-сервером:
маршрут проверяет звание по базе, а затем зовёт функцию, положенную в
`globalThis` (`__forceMuteUser` и соседи). Она правит состав комнаты и рассылает
события — цели и всем, кто смотрит на канал.

Звания в сообществе — числа (`lib/groupModeration`): `MEMBER = 1`,
`GUIDE = 1.5`, `MODERATOR = 2`, `ADMIN = 3`, `OWNER = 4`. Мера допустима, если
актор **строго выше** цели. Отдельно есть признак `canManage` — это владелец или
администратор; модератор и проводник в него не входят.

> [!NOTE]
> **Принудительное заглушение** — это не «выключить звук у себя». Микрофон
> глушится у самого человека, и снять это он не может: `toggleMute` отказывает,
> пока стоит замок. Именно поэтому снятие обязано существовать и работать.

### Что уже было починено раньше

В #136: меню модерации в боковой панели закрывалось от собственного `mousedown`
(портал снимался до `mouseup`, и события `click` не возникало вовсе), а
`/api/voice/move-user` сравнивал звание с числом `30` при рангах `1…4` и потому
отвечал `403` всем. Это было необходимо, но недостаточно — и здесь видно, почему.

## Intuition

### 1. Замок помнил клиент, а сервер забывал

Вот вся суть на одной шкале времени:

```
модератор:  force-mute →  сервер: room[socketId].isForceMuted = true
                          цель:   микрофон выключен, свой toggleMute заблокирован

цель:       обрыв связи / переход в другой канал / F5
                          сервер: запись участника УМЕРЛА вместе с сокетом
                          цель:   isForceMuted у провайдера остался = true

цель:       вход обратно
                          сервер: новая запись, БЕЗ пометок
                          панель: показывает человека свободным
                          цель:   микрофон по-прежнему не включается
```

Дальше — ловушка. Модератор видит «незаглушённого» и получает в меню единственный
пункт «Заглушить микрофон»; снимать нечего, потому что для сервера замка нет. А
человек сидит без микрофона и сам его включить не может. Выход был один — уходить
из сообщества, и это ровно то, о чём сообщил пользователь: «заглушить получается,
вернуть обратно — нет».

Лечится это тем, что замок перестаёт быть свойством *сокета* и становится
свойством *пары «канал + человек»*:

```
voiceForceLocks: Map<"channelId:userId", { muted, deafened }>
```

Реестр переживает переподключение, применяется при входе в канал и снимается
только тем, что снимает его по-настоящему — `force-unmute`. Клиент же при выходе
из канала свои пометки **сбрасывает**: помнить замок должен один, и это сервер.

### 2. Меню выбирало не тот пункт

Пункт выбирался по флагу из снимка состава комнаты:

```
заглушён      → показать «Снять заглушение»
не заглушён   → показать «Заглушить микрофон»
```

Логично — и неверно. Снимок приходит событием, а событие может не дойти, прийти
позже или устареть (см. выше). И тогда единственный показанный пункт оказывается
ровно тем, который не нужен. Теперь обе меры на месте всегда, а текущее
состояние — не выбор пункта, а точка рядом с ним.

### 3. «Снять заглушение» снимало половину

Клиент присылал `deafen: <из своего снимка>`, и сервер снимал ровно это. При
устаревшем снимке человек получал обратно микрофон и **оставался без наушников** —
со его стороны это выглядело как поломка связи, а не как чьё-то решение.

Теперь клиент вообще не решает: он просит «снять заглушение с этого человека», а
что именно снять и какое звание для этого нужно, определяет сервер по своему
реестру:

```
замок { muted: true, deafened: true }  → нужен MODERATOR, снимается всё
замок { muted: true, deafened: false } → достаточно GUIDE,  снимается всё
замок неизвестен (сокет-сервер молчит) → нужен MODERATOR
```

Последняя строка — сознательный перекос в сторону запрета: не дать снять — это
неудобство, снять без права — дыра в модерации.

### 4. Власть то была, то её не было

Меню открывалось только в канале, в котором модератор **сидит сам**
(`isActive &&`), а перетаскивать участников из панели с недавних пор было можно и
со стороны. Одна и та же власть в двух местах вела себя по-разному, и объяснить
это человеку нечем.

Вторая половина того же перекоса: перетаскивание включалось признаком
`canManage` — владелец или администратор. Модератор и проводник, которым власть
над голосовыми каналами как раз и выдают, перенести никого не могли.

Теперь обе возможности открываются одним порогом — «проводник и выше», как у
всех прочих мер. Окончательное решение по-прежнему за сервером; интерфейс просто
перестал добавлять к правам свои условия.

### 5. Отказ был неотличим от неработающей кнопки

Каждая кнопка меню делала так:

```js
onClick={async () => { setSidebarModMenu(null); await fetch(...).catch(() => {}); }}
```

Меню закрывалось **до** ответа, а отказ уходил в пустоту: ни «нет прав», ни
«звание не ниже вашего», ни «нет связи». Со стороны это в точности то же, что
мёртвая кнопка, — а лечится совершенно иначе. Теперь меню закрывается на успехе
и остаётся с причиной на отказе.

## Code

### Сервер: реестр замков

```ts
// server.ts
type ForceLock = { muted: boolean; deafened: boolean };
const voiceForceLocks = new Map<string, ForceLock>();     // "channelId:userId"

globalThis.__forceMuteUser = (channelId, targetUserId, deafen) => {
  const previous = readForceLock(channelId, targetUserId);
  /* «мик + наушники» поверх «мика» усиливает замок; обратно — не ослабляет */
  const lock = { muted: true, deafened: previous.deafened || deafen };
  voiceForceLocks.set(forceLockKey(channelId, targetUserId), lock);
  applyLockToRoom(channelId, targetUserId, lock);
  emitToUserSockets(targetUserId, deafen ? "voice:force-deafen" : "voice:force-mute");
  void broadcastVoiceChannelUsers(channelId);
};

globalThis.__forceUnmuteUser = (channelId, targetUserId) => {   // снимает ВСЁ
  voiceForceLocks.delete(forceLockKey(channelId, targetUserId));
  applyLockToRoom(channelId, targetUserId, { muted: false, deafened: false });
  emitToUserSockets(targetUserId, "voice:force-undeafen");
  void broadcastVoiceChannelUsers(channelId);
};

globalThis.__voiceForceLock = (channelId, targetUserId) => readForceLock(channelId, targetUserId);
```

Важная деталь: `__forceMuteUser` больше **не требует**, чтобы человек был в
комнате прямо сейчас. Заглушить можно и того, кто на секунду отвалился, — замок
доедет до него при входе:

```ts
// join-voice
const lock = readForceLock(channelId, authData.userId);
const user: VoiceUser = { …, muted: lock.muted, isForceMuted: lock.muted, isForceDeafened: lock.deafened };
if (lock.muted) socket.emit(lock.deafened ? "voice:force-deafen" : "voice:force-mute", {});
```

Событие уходит и самому вошедшему: его клиент замок при выходе сбросил, и без
напоминания микрофон вернулся бы к нему сам.

### Сервер: снятие решает по своему состоянию

```ts
// api/voice/force-unmute/route.ts
const lock = readLock(channelId, targetUserId);
const minRank = !lock || lock.deafened ? ROLE_RANK.MODERATOR : ROLE_RANK.GUIDE;
if (callerRank < minRank) return 403;
…
emitToUser(targetUserId, "voice:force-undeafen", {});   // снимает и микрофон, и наушники
```

Поле `deafen` в запросе больше не участвует: решение принимает сторона, у которой
есть состояние.

### Клиент: обе меры, один порог, видимый отказ

```tsx
// ChannelSidebar.tsx
const canModerateVoice = rankOf(groupDetail.myRole) >= RANK_GUIDE;   // порог один на меню и перетаскивание

const runModAction = useCallback(async (path, body) => {
  const res = await fetch(path, { method: "POST", … });
  if (res.ok) { setSidebarModMenu(null); return; }          // закрываем на успехе
  setSidebarModMenu(prev => prev ? { ...prev, error: reason } : prev);   // остаёмся с причиной
}, []);
```

Меню больше не спрашивает, сижу ли я в этом канале, и показывает всё сразу:

```tsx
{canForceMute   && <button …>Заглушить микрофон       {muted && <точка/>}</button>}
{canForceDeafen && <button …>Заглушить мик + наушники {deafened && <точка/>}</button>}
{canForceMute   && <button …>Снять заглушение</button>}
```

Пустой набор прав тоже теперь говорит о себе — «Мер модерации к этому участнику у
вас нет» — вместо пустого меню, которое читается как поломка.

### Клиент: замок не живёт дольше сервера

```ts
// VoiceContext.tsx, выход из канала
setIsForceMuted(false);   isForceMutedRef.current = false;
setIsForceDeafened(false); isForceDeafenedRef.current = false;
```

### Голосовая панель: снятие появилось вообще

В `VoiceExpandedPanel` было «Заглушить микрофон» и «Принудительно заглушить», а
обратного пункта не существовало: заглушить можно было оттуда, а вернуть — только
из боковой панели, и то пока её снимок не устарел. Теперь «Снять заглушение»
стоит рядом с наложением, как и в панели.

## Verification

### Тесты

Главный из них — **на настоящем сайдбаре**, а не на его частях: заглушение
складывается из шести звеньев (строка ловит щелчок → панель спрашивает права →
рисует кнопки → щелчок уходит на сервер → сервер рассылает состав → панель
меняет пункты), и ошибка в любом звене выглядит одинаково: «нажимаю — ничего».
Проверять такое по частям бессмысленно — каждая часть по отдельности «работает».

```
src/components/connect/ChannelSidebar.voiceMod.test.tsx   17 тестов
src/app/api/voice/force-unmute/route.test.ts              10 тестов
src/app/api/voice/move-user/route.test.ts                  8 тестов (из #136)
src/components/connect/useDragUser.test.ts                 5 тестов (из #136)
```

Что закреплено:

- «Заглушить микрофон» и «Заглушить мик + наушники» доходят до сервера — и
  проверяется это **полным щелчком** (`mousedown` + `mouseup` + `click`), потому
  что ломалось именно это: обработчик был исправен, а `click` не возникал;
- снятие предлагается **даже когда снимок считает участника незаглушённым** — и
  наоборот;
- снятие уходит без поля `deafen`: решение за сервером;
- меню открывается для канала, в котором меня нет;
- модератор и проводник получают и меню, и перетаскивание; обычный участник — нет;
- отказ сервера виден, меню остаётся открытым;
- права не пришли — меню объясняет, а не исчезает;
- звание для снятия определяется по замку: «мик + наушники» проводнику не снять,
  неизвестное состояние трактуется в сторону запрета.

> [!IMPORTANT]
> В jsdom нет `PointerEvent`: у события от `fireEvent.pointerDown` нет ни
> `pointerType`, ни `button`, и обработчик отсеивает его как чужой. Это
> особенность окружения, а не приложения, поэтому в тесте жест собирается из
> `MouseEvent` с дописанным `pointerType` — так, как его видит браузер. Без этой
> детали тест «проходит» мимо проверяемого кода.

`npm run lint` — чисто. Сборку проверяет CI.

### Ручная проверка

Нужны два аккаунта: у вас звание не ниже проводника, у второго — участник.

**Заглушение и снятие.**
1. Оба в одном голосовом канале. ПКМ по участнику в боковой панели.
2. «Заглушить микрофон» — у него микрофон гаснет и сам не включается. В меню
   рядом с пунктом появляется точка.
3. «Снять заглушение» — микрофон возвращается.
4. «Заглушить мик + наушники» → «Снять заглушение»: должны вернуться **и**
   микрофон, **и** звук. Прежде звук не возвращался.

**Замок переживает переподключение** — это и была ловушка.
1. Заглушите участника.
2. Пусть он перезагрузит страницу или выйдет из канала и зайдёт обратно.
3. Он по-прежнему без микрофона, а в вашей панели рядом с ним точка. Прежде
   панель показывала его свободным, и снять заглушение было нечем.
4. «Снять заглушение» — работает.

**Меры со стороны.**
1. Выйдите из голосового канала, оставив участника в нём.
2. ПКМ по нему в панели: меню открывается, меры работают. Прежде правый щелчок
   не делал ничего.

**Перенос.**
1. Зажмите ЛКМ на участнике и тащите на другой голосовой канал — канал-цель
   подсвечивается, участник переезжает.
2. То же из меню: «Перенести в канал». Этот путь надёжнее, когда нужный канал не
   виден на экране: перетаскивание не прокручивает список.
3. Модератором (не владельцем) — тоже работает. Прежде перетаскивание включалось
   только владельцу и администратору.

**Отказы.**
1. Попробуйте применить меру к равному или старшему по званию: меню остаётся
   открытым и пишет «Звание участника не ниже вашего». Прежде оно просто
   закрывалось.

## Alternatives

### Где хранить замок

| Реестр в памяти сокет-сервера (выбрано) | Поле в базе у GroupMember |
|---|---|
| **+** Рядом с остальным состоянием голоса — оно всё в памяти процесса | **+** Переживает перезапуск сервера |
| **+** Никакой миграции и запроса в базу на каждый вход в канал | **+** Видно в админке, можно посмотреть историю |
| **−** Перезапуск процесса снимает все замки | **−** Запрос к базе в горячем пути `join-voice` |
| **−** Не годится для нескольких процессов — как и сами голосовые комнаты | **−** Замок переживёт даже удаление канала, и чистить его будет некому |

Голосовые комнаты уже живут в памяти одного процесса (см. AGENTS.md), и делать
замок надёжнее самой комнаты бессмысленно: после перезапуска в канале всё равно
никого нет.

### Как показывать пункты меню

| Обе меры всегда (выбрано) | Один пункт по состоянию, но состояние спрашивать у сервера |
|---|---|
| **+** Работает при любом состоянии снимка, в том числе устаревшем | **+** В меню на один пункт меньше |
| **+** Ноль лишних запросов | **+** Пункт всегда «правильный» |
| **−** Модератор видит «заглушить» у уже заглушённого (отмечено точкой) | **−** Ещё один запрос на открытие меню, ещё одна причина увидеть пустое меню |

## Suggested people to talk to

- **Сокет-сервер и голосовые комнаты** (`server.ts`) — самый плотный по
  состоянию участок: комнаты в памяти, grace-окно на обрывы, WebRTC-сигналинг.
  Реестр замков добавлен рядом с ними и живёт по тем же правилам, поэтому стоит
  свериться с тем, кто делал `FIX-GR1`/`FIX-GR2` (тихий реконнект): он лучше
  всех знает, как выглядят обрывы связи в этом коде — а именно они и вскрывали
  ловушку с замком.
- **Панель каналов** (`ChannelSidebar.tsx`, ~1500 строк) — здесь сходятся
  presence, перетаскивание, меры модерации и три режима вёрстки. Тому, кто
  правил `FIX-FORCELOCK-V2` (слияние снимков состава), стоит взглянуть на новый
  порог `canModerateVoice`: прежние условия (`isActive`, `canManage`) появились
  именно там.
- **Права и звания** (`lib/groupModeration.ts`) — модуль с высоким fan-in.
  Порог «проводник и выше» взят оттуда; если решите, что голосовые меры должны
  начинаться с модератора, менять нужно в одном месте, а не в панели.

  — Неверно, и это было прежним поведением: клиент присылал `deafen` из устаревшего снимка.
- **B.** Сервер по своему реестру замков; снимается всё, а звание требуется по силе замка. ✅
  — Верно. Неизвестное состояние трактуется в сторону запрета.
- **C.** Сама цель — событием от своего клиента.
  — Неверно: снять с себя замок цель не может по замыслу.
- **D.** Никто: снятие всегда требует владельца.
  — Неверно: замок только на микрофон снимает и проводник.

- **A.** Так короче.
  — Неверно, наоборот — на несколько строк длиннее.

  — Неверно: касания хук как раз игнорирует, там прокрутка.
