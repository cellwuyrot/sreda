# API, данные и внедрение

## Миграция — обязательна

`20261027000000_personal_chat_parity` добавляет:

- `DirectConversation.user1ReceiptAt`, `user2ReceiptAt`: отдельные опубликованные квитанции. Приватные `user1ReadAt`/`user2ReadAt` не копируются в них.
- `DirectMessage.replyQuote`, `clientMessageId` (nullable, до 80 символов).
- Уникальность `(conversationId, userId, clientMessageId)` и индекс `(conversationId, createdAt, id)`.
- `DirectMessageReaction`, внешние ключи на сообщение/пользователя, уникальность `(messageId, userId, emoji)`.

Данные не удаляются. Проверить миграцию на копии production-БД обязательно: SQL создан и Prisma Client сгенерирован, но реальная PostgreSQL-миграция в этой среде НЕ запускалась. Индексы могут блокировать запись на большой таблице — оценить время и запланировать окно обслуживания.

## Рекомендуемый порядок

1. Сделать и проверить резервную копию PostgreSQL, сохранить текущий код, конфигурацию и загружаемые файлы. Не хранить секреты в архиве релиза.
2. На staging с копией схемы и обезличенными данными: `npm ci` (использовать поддерживаемую проектом версию Node), затем из корня:

```bash
npm run migrate
npm run build
npm run typecheck -w apps/web
npm run lint -w apps/web
npm run test -w apps/web
```

3. Проверить `prisma migrate status` из `apps/web`, реальные запросы к БД и сценарии из VALIDATION.md. Не использовать `prisma migrate reset` и не заменять миграции командой `db push`.
4. Применить миграции в production **до** запуска обновлённого приложения. Для этого использовать текущий штатный процесс проекта и корректный DATABASE_URL; `npm run migrate` применяет все ещё не выполненные миграции репозитория.
5. Пересобрать и перезапустить штатный web/socket-процесс. Сохранить прежнее ограничение одного realtime-процесса из предыдущего ревью. Проверить логи и дымовые сценарии двумя пользователями.

Старые install/build/deploy инструкции сохраняют силу. Архив содержит исходники, не подписанный Electron-инсталлятор, не production `.next` и не зависимости.

## Откат

Предпочтительно вернуть предыдущий код, оставив добавленные nullable-колонки/таблицу: не выполнять разрушительное удаление данных автоматически. До отката проверить совместимость старого Prisma Client. Сохранить новые реакции/квитанции для повторного выпуска. Восстановление БД из backup — только по согласованному плану с учётом новых записей и окна потери данных. Не считать возврат старого кода сохранением новых защит SECURE: прежнее поведение может их не иметь.

## Контракты

- `GET /api/dm/:id?limit=&cursor=` — старая история; `after=` — новые страницы; `around=` — ограниченный контекст цели. Режимы взаимоисключающие, цель проверяется в той же беседе. Ответ включает `messages`, `nextCursor`, `afterCursor`, `firstUnreadId`, `peerReadAt`. Сортировка по времени и ID. Лимит ограничен 100.
- `POST /api/dm/:id` — поддерживает `clientMessageId`, `replyToId`, `replyQuote`. Повтор одного ключа пользователя/беседы возвращает уже сохранённое сообщение без второй записи и повторного уведомления. Ключ должен быть новым для нового логического сообщения. Старые клиенты могут не передавать ключ.
- `PATCH /api/dm/:id` — изменение собственного неудалённого сообщения; для SECURE требуется шифрованный текст. `DELETE` сохраняет существующее мягкое удаление; GET не возвращает тело/вложения/реакции удалённого сообщения.
- `GET /api/dm/:id/search?q=&cursor=` — только участники PERSONAL; q 2–200 символов, постранично 30 результатов. Исключает удалённые/зашифрованные сообщения, проверяет cursor и права. Это case-insensitive contains, не отдельный поисковый движок.
- `POST /api/dm/reactions` — `{ messageId, emoji, active }`; явное состояние вместо toggle. Проверки авторизации, участника, блокировки, типа PERSONAL и удаления; ограничение частоты. Повтор активного/неактивного состояния идемпотентен. Используются события `dm-reaction-added`/`dm-reaction-removed`.
- `GET /api/dm/:id/attachments?cursor=` / `?type=links&cursor=` — страницы по 50 исходных сообщений; `nextCursor`. Клиент фильтрует тип материалов. Для ссылок сервер извлекает HTTP(S) URL из разрешённого текста, но не загружает внешнее превью. SECURE запрещён.
- `POST /api/dm/read` — `{ conversationId, sendReceipt }`: приватный readAt обновляется всегда, опубликованный ReceiptAt и `dm-read` — только если квитанция разрешена. Старые уже опубликованные квитанции не отзываются выключением настройки.
- `POST /api/messages/upload` — нельзя задавать одновременно channelId и conversationId; принадлежность проверяется до обработки, SECURE отклоняется даже с e2eeIv.
- `GET /api/dm/:id/export` — SECURE запрещён; обычный и бизнес-экспорт сохранены.

## Безопасность и незакрытые границы

Защищённый текст отправляется через единый клиентский адаптер без plaintext fallback. Проверка сервером hex-конверта не заменяет криптографическую проверку отправителя. Старые записи, управление/восстановление ключей, метаданные, доставка между устройствами требуют отдельного аудита. Полная защищённая передача файлов отложена, а не имитируется полем e2eeIv. Поиск не проходил нагрузочную проверку на большой БД: для contains на большой истории может потребоваться отдельная стратегия индексации/поиска. Правильность БД-ограничений и конкурентных транзакций нужно подтвердить на PostgreSQL, не только mock-тестами.
