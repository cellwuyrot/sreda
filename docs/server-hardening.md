# Перенос на новый сервер: защита по шагам

Порядок важен: сначала машина закрывается, потом на неё кладётся проект, и только
после этого домен переезжает. Обратный порядок означает, что какое-то время сервис
стоит открытым — и именно это время его находят.

Всё, что нужно заполнить своими значениями, помечено **ЗАПОЛНИТЬ**.

## 0. Развести роли по машинам

| Машина | Что на ней | Открытые порты |
|---|---|---|
| Главная | сайт, БД, Redis | 80, 443 (и SSH) |
| Голос | только TURN | 3478, 5349 + диапазон медиа |
| VPN-узлы | только WireGuard | один UDP-порт |
| Файлы (необязательно) | инсталляторы, APK | 80, 443 |

**Почему TURN обязательно отдельно.** Его адрес приложение отдаёт каждому, кто
заходит в голосовой канал (в ICE-кандидатах). Пока TURN стоит на главной машине,
её адрес знает любой пользователь — и никакой прокси этого не спрячет. На новом
сервере TURN поднимается отдельной машиной, а приложению задаётся `TURN_URL` с её
адресом.

## 1. Закрыть машину

```bash
# ЗАПОЛНИТЬ свой адрес; список прокси — когда он появится (шаг 4)
ADMIN_SSH_CIDR=203.0.113.7/32 ./deploy/firewall.sh app
```

Скрипт откажется работать без `ADMIN_SSH_CIDR` — это защита от самой частой аварии
при настройке экрана: потерять собственный доступ. Роли: `app`, `turn`, `vpn`,
`files`.

Дальше, до всего остального:

* вход по ключу, пароль выключен: `PasswordAuthentication no`, `PermitRootLogin no`;
* обновления безопасности автоматом (`unattended-upgrades` или аналог);
* `fail2ban` из `deploy/fail2ban/` — там же в комментариях, куда положить файлы.

**Проверить со СТОРОННЕЙ машины**, не с сервера:

```bash
nmap -Pn -p 22,80,443,3000,5432,6379,3478,51820 <адрес>
```

Открыты должны быть только порты своей роли. **3000, 5432 и 6379 — закрыты.**
Если открыт 3000 — приложение доступно мимо nginx, со всеми его лимитами.

## 2. Положить проект

```bash
git clone <репозиторий> /var/www/trioz && cd /var/www/trioz
# .env заполняется по отдельному файлу readenv.md (в репозиторий он не кладётся)
npm ci && npm run build
```

Все секреты на новом сервере **создаются заново**. Переносить старые нельзя: часть
из них уже засветилась, и перенос сохранит проблему вместе с проектом.

## 3. Передний край

`nginx.conf` в репозитории уже с пределами частоты, ограничением числа соединений,
таймаутами против медленных запросов и блоком-заглушкой, который обрывает запрос
без нашего домена (`return 444`). Что нужно сделать руками:

1. **Заменить `server_name _`** на свой домен в рабочем блоке. Пока там `_`,
   заглушка бесполезна: рабочий блок принимает любой Host, включая заход по IP.
2. Раскомментировать блок HTTPS и вписать пути к сертификату.
3. Когда появится прокси — заполнить `set_real_ip_from` его диапазонами. Без этого
   все лимиты будут считаться на один адрес прокси, и один шумный посетитель
   упрётся в лимит за всех.

Проверить: `nginx -t`, затем `curl -H 'Host: чужой.домен' http://<адрес>/` — должно
обрываться без ответа.

## 4. Спрятать адрес

1. Поднять прокси/анти-DDoS перед доменом.
2. Заполнить `PROXY_CIDRS` и перезапустить экран:
   ```bash
   ADMIN_SSH_CIDR=203.0.113.7/32 PROXY_CIDRS=173.245.48.0/20,103.21.244.0/22 \
     ./deploy/firewall.sh app
   ```
   Теперь 80/443 принимаются **только от прокси**, прямой заход отбрасывается.
3. **Сменить IP главной машины** после того, как шаги 1–3 готовы. Старый адрес
   остался в архивах DNS: без смены прокси прячет домен, но не сервер.
4. Убедиться, что письма уходят через внешний сервис, а не локальный MTA — иначе
   адрес видно в заголовках `Received:` каждого письма.

## 5. Что остаётся открытым и это нормально

* **Адреса TURN и VPN-узлов** публичны по устройству протоколов. Это не утечка,
  если на этих машинах нет ничего, кроме реле, и экран открывает только их порты.
* **Предпросмотр ссылок** ходит по адресу, который дал человек: его сервер увидит
  адрес нашего. Если это важно — исходящие запросы за предпросмотром выносятся на
  отдельную машину-посредник.

## 6. Порядок действий при атаке

Написать заранее и держать под рукой:

1. Включить у прокси режим повышенной защиты.
2. Посмотреть, что именно льют: `nft list table inet trioz` (счётчики),
   `tail -f /var/log/nginx/access.log`, `fail2ban-client status`.
3. Если льют в обход прокси — значит адрес нашли: закрыть 80/443 на всё, кроме
   `PROXY_CIDRS`, и планировать смену адреса.
4. Если льют на TURN — выключить его: голос отвалится, переписка останется.
5. Если легло — восстановление начинается с базы, а не с сайта. Проверить, что
   резервная копия свежая и лежит **не на этой машине**.

## Что уже сделано в репозитории

* `nginx.conf` — лимиты, таймауты, заголовки, `return 444` на чужой Host;
* `docker-compose.yml` — порт приложения слушает только localhost (БД и Redis
  были закрыты и раньше);
* `deploy/firewall.sh` — экран по ролям с защитой от самозапирания;
* `deploy/fail2ban/` — баны за перебор и поток отказов.

Чего в репозитории нет и быть не должно: значения секретов, адреса машин,
диапазоны прокси. Они живут в `.env` на сервере и в вашем `readenv.md`.
