# Сохранение Next.js static для долгоживущих Electron-страниц

## Что меняется

Production-контейнер перед запуском `server.ts` запускает
`scripts/retain-next-static.mjs`. Скрипт копирует текущий
`apps/web/.next/static` в `/app/next-static/_next/static`, который является
именованным томом `next_static_data`. В образе заранее создаётся этот seed-каталог
и его содержимое принадлежит UID 1001 (`nextjs`); Docker переносит его в пустой
том при первом монтировании. Скрипт:

- не удаляет файлы старых сборок;
- пропускает файл, если SHA-256 совпадает;
- записывает новый файл во временный файл и атомарно публикует его через
  hard-link, поэтому nginx не видит частичную запись;
- не следует по symlink в источнике или хранилище;
- при отличающемся содержимом одного и того же пути оставляет старый файл,
  пишет предупреждение и завершает bootstrap с ошибкой (сервер не стартует
  с неоднозначным набором ассетов).

Nginx монтирует тот же том только для чтения в
`/usr/share/nginx/retained-next-static` и обслуживает `/_next/static/` напрямую.
Если файла в томе нет, именованный location проксирует запрос в текущий app.

Локальные `npm run dev` и обычные команды npm не меняются: bootstrap подключён
только к production `CMD` Dockerfile. Dev-compose не монтирует этот том.

## Первый rollout и bootstrap

Если том пуст, первый старт сохранит только static текущего образа. Уже открытая
страница, созданная **до** первого rollout этой функции, может ссылаться на
старую сборку, которой в новом томе ещё нет. Чтобы не потерять этот ресурс,
сначала скопируйте static из всё ещё запущенного старого контейнера в
`next_static_data`, затем заменяйте app-образ. Например, на хосте (имя тома
уточните через `docker volume ls`):

```sh
mkdir -p /tmp/trioz-next-static-bootstrap
docker cp "$(docker compose ps -q app):/app/apps/web/.next/static/." /tmp/trioz-next-static-bootstrap/
docker run --rm \
  -v trioz_next_static_data:/dst \
  -v /tmp/trioz-next-static-bootstrap:/src:ro \
  alpine sh -c 'mkdir -p /dst/_next/static && cp -a /src/. /dst/_next/static/ && chown -R 1001:1001 /dst'
```

Если старый контейнер уже удалён и его образ недоступен, восстановить эти
файлы этим механизмом нельзя; новые старые build-id появятся только при
последующих запусках, когда они будут источником bootstrap.

При первом включении нужно применить изменения **обоих** сервисов:
`docker compose up -d --no-deps app nginx`. Иначе уже работающий nginx не получит
новое монтирование тома. Перед этим соберите новый app-образ и проверьте production-
конфигурацию nginx. В GitLab-публикацию архива добавлен отдельный шаг обновления nginx.

Дальнейший `docker compose up -d --no-deps app` безопасен для тома. При rollback
существующий `next_static_data` не удаляйте: старые build-id останутся доступны,
а текущий app будет fallback для отсутствующих файлов. Если заранее созданный том
принадлежит root, до старта app установите владельца UID/GID 1001:1001, как в примере
выше: иначе процесс nextjs не сможет добавлять ассеты.

## Nginx и место на диске

При собственной production-конфигурации nginx нужно повторить оба элемента:

1. read-only mount `next_static_data` в контейнер nginx;
2. location `/_next/static/` с `root` на этот mount, `try_files` и fallback
   `proxy_pass` в app. Готовый вариант находится в `nginx.conf` (HTTPS-блок
   содержит отдельную копию location).

Автоматического удаления старых сборок намеренно нет в первой безопасной версии:
том будет расти на размер каждого уникального build-id. Нужны отдельные политика
хранения, проверка активных клиентов/окон и ручная или плановая очистка; не
добавляйте `docker volume prune` в обычный deploy, пока такая политика не
согласована. Пользовательские uploads этот механизм не затрагивает.
