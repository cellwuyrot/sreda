# TrioZ VPN — узел WireGuard

Агент дочернего узла. Ставится на отдельную машину, поднимает WireGuard и
получает список пиров с главного сервера.

## Как это устроено

Модель «на вытягивание». Узел раз в минуту приходит на
`POST /api/servers/report` главного сервера с токеном агента и получает в ответ
**полный список своих пиров**, после чего приводит интерфейс к этому списку:
добавляет новых, снимает лишних. Своего входящего API у узла нет вовсе.

Почему так, а не «главный сервер командует узлом»:

- узел работает за NAT, ему не нужен ни публичный HTTP-порт, ни сертификат;
- не нужна обратная аутентификация — главный сервер хранит только SHA-256
  токена узла и физически не смог бы предъявить его;
- состояние всегда сходится: даже если узел был недоступен сутки, после
  возвращения он приведёт себя к актуальному списку сам.

## Про ключи — коротко и по делу

| Ключ | Где создаётся | Кто его видит |
|---|---|---|
| Приватный ключ **интерфейса узла** | на узле, при первом запуске | только узел (файл с правами `600`) |
| Публичный ключ **интерфейса узла** | производный | сообщается главному серверу, попадает клиентам |
| Приватный ключ **пользователя** | в клиенте, при выдаче доступа | **только владелец** |
| Публичный ключ **пользователя** | производный | главный сервер и узел |

Приватный ключ пользователя не приходит ни на узел, ни на главный сервер —
там нет даже поля, куда его можно было бы записать. Поэтому «выдать чужой
доступ» невозможно технически: выдавать нечего. Один аккаунт — один пир,
повторная регистрация заменяет ключ, и старое устройство теряет связь.

Выдача автоматическая: право на VPN даёт подписка Premium, и при первом открытии
окна VPN клиент сам создаёт пару ключей, отправляет публичную половину и получает
готовый профиль. Администратор в выдаче не участвует и профиля никогда не видит —
из этого же следует, что показать профиль второй раз невозможно, только
перевыпустить.

## Установка

Требуется Linux с `wireguard-tools` и Node 20+.

```bash
apt install -y wireguard-tools
```

### 1. Интерфейс

Агент не создаёт интерфейс — он им управляет. Поднимите `wg0` заранее,
без секции `[Peer]`: пиры добавит агент.

`/etc/wireguard/wg0.conf`:

```ini
[Interface]
Address = 10.8.0.1/24
ListenPort = 51820
PostUp = wg set %i private-key /etc/wireguard/trioz-private.key
# NAT для выхода клиентов в интернет (замените eth0 на свой внешний интерфейс)
PostUp = iptables -t nat -A POSTROUTING -s 10.8.0.0/24 -o eth0 -j MASQUERADE
PostDown = iptables -t nat -D POSTROUTING -s 10.8.0.0/24 -o eth0 -j MASQUERADE
```

Приватный ключ в конфиг **не вписывается**: его создаёт агент при первом
запуске и подставляет строка `PostUp`. Так ключ живёт в одном файле с правами
`600`, а не в конфиге.

Первый запуск: создайте ключ, затем поднимите интерфейс.

```bash
wg genkey > /etc/wireguard/trioz-private.key
chmod 600 /etc/wireguard/trioz-private.key
sysctl -w net.ipv4.ip_forward=1
wg-quick up wg0
systemctl enable wg-quick@wg0
```

### 2. Узел в панели

В админ-панели: **Сервисы и система → Серверы → Добавить узел**, назначение
**VPN**. Скопируйте токен агента — он показывается один раз.

Там же указывается **точка подключения** — IP или домен этой машины, куда
клиенты стучатся по UDP. Порт можно опустить, подставится 51820.

У WireGuard нет URL: в конфиг клиента идёт строка `Endpoint = host:port`, и
никакого http-адреса у VPN-узла не существует — связка работает «на
вытягивание», главный сервер к узлу не обращается вообще. Поэтому для узла с
назначением VPN панель спрашивает именно точку подключения, а не ссылку.

Значение из панели **главнее** переменной `WG_ENDPOINT_HOST` на самом узле: узел
за NAT своего публичного адреса не знает и пишет в отчёт лишь то, что ему
прописали. Отчёт остаётся запасным вариантом, если поле в панели пустое.

### 3. Агент

```bash
TRIOZ_MAIN_URL=https://example.ru \
TRIOZ_AGENT_TOKEN=<токен из панели> \
WG_ENDPOINT_HOST=vpn1.example.ru \
node apps/vpn/src/index.mjs
```

Переменные:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `TRIOZ_MAIN_URL` | — | адрес главного сервера, обязательно |
| `TRIOZ_AGENT_TOKEN` | — | токен из админ-панели, обязательно |
| `WG_ENDPOINT_HOST` | — | запасной вариант точки подключения, если в панели поле пустое |
| `WG_INTERFACE` | `wg0` | имя интерфейса |
| `WG_TOOL` | автоопределение | инструмент управления интерфейсом; задавать только если на узле стоят оба |
| `WG_CONF_PATH` | по имени интерфейса | конфиг интерфейса, откуда читаются дополнительные параметры |
| `WG_PORT` | `51820` | UDP-порт WireGuard |
| `WG_PRIVATE_KEY_PATH` | `/etc/wireguard/trioz-private.key` | файл приватного ключа |
| `TRIOZ_REPORT_INTERVAL_MS` | `60000` | период отчёта |

### 4. systemd

`/etc/systemd/system/trioz-vpn-agent.service`:

```ini
[Unit]
Description=TrioZ VPN agent
After=network-online.target wg-quick@wg0.service
Wants=wg-quick@wg0.service

[Service]
Type=simple
# wg set требует прав на сетевые настройки
User=root
WorkingDirectory=/opt/trioz
Environment=TRIOZ_MAIN_URL=https://example.ru
Environment=TRIOZ_AGENT_TOKEN=...
Environment=WG_ENDPOINT_HOST=vpn1.example.ru
ExecStart=/usr/bin/node /opt/trioz/apps/vpn/src/index.mjs
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

```bash
systemctl enable --now trioz-vpn-agent
journalctl -u trioz-vpn-agent -f
```

## Внешние адреса выхода

Один узел = один публичный IP на всех его пользователей — это главный потолок
масштабирования: отсюда капчи, баны и странная геолокация, а не из-за нехватки
адресов в туннеле.

Заведите у хостера несколько адресов, поднимите их на интерфейсе и укажите в
панели: **Серверы → узел → Внешние адреса**. Главный сервер закрепит за каждым
пиром свой адрес и пришлёт агенту правила SNAT тем же отчётом.

Закрепление адреса за пиром сделано намеренно: смена внешнего IP посреди работы
для банков и длинных сессий выглядит как смена пользователя и приводит к
разлогину.

Агент держит правила в **отдельной цепочке** `TRIOZ_VPN_SNAT`, и ссылка на неё
ставится **первым правилом** `nat/POSTROUTING`. Порядок здесь — не деталь: в
таблице `nat` правила проходятся по очереди, а `MASQUERADE` завершает обход, и
`MASQUERADE` из `wg0.conf` появляется раньше агента. Ссылка «в конец» означала бы,
что закрепление внешних адресов не срабатывает ни разу.

Свою цепочку можно безопасно очищать целиком, не задевая `MASQUERADE` и прочие
правила, прописанные вами руками. Пир без закреплённого адреса проваливается
дальше — к тому же `MASQUERADE`, то есть выходит общим адресом узла.

Проверить — и сами правила, и порядок:

```bash
iptables -t nat -L TRIOZ_VPN_SNAT -n -v
iptables -t nat -L POSTROUTING -n -v --line-numbers   # TRIOZ_VPN_SNAT должен быть №1
```

Счётчик пакетов у цепочки, который стоит на нуле при живых пирах, — верный
признак, что ссылка оказалась ниже `MASQUERADE`. Обновлённый агент переставляет её
сам при первом такте.

Если пул не задан, поведение прежнее — общий `MASQUERADE` из `wg0.conf`.

## Тип подключения узла

Узел может работать в обычном режиме или в устойчивом к блокировкам — это
определяется тем, что установлено на машине, и объявляется в панели: **Серверы →
узел → «Сделать устойчивым»**.

Агент сам находит инструмент управления интерфейсом (`awg`, если он есть, иначе
`wg`) — набор команд у них одинаковый, поэтому вся остальная логика не меняется.
Дополнительные параметры интерфейса он вычитывает из его конфига и присылает
отчётом; главный сервер подставляет их в выдаваемые профили. Вводить их руками
не нужно и негде: единственный источник — сам узел.

Переключатель в панели и отчёт узла независимы намеренно. Обновление на машине
не должно молча менять то, что выдаётся клиентам, поэтому режим включает человек,
а панель показывает, сошлось ли объявленное с реальностью.

## Масштабирование

Узлов может быть сколько угодно: добавляете машину, регистрируете её в панели с
назначением VPN — и новые пиры начнут распределяться на наименее загруженный
узел. Существующие пиры остаются на своих узлах.

## Почему без TypeScript и зависимостей

Это системный агент: он должен подниматься на голой машине одной командой
`node`, без установки пакетов и шага сборки. Каждая зависимость здесь — ещё
один способ уронить прод в неудачный момент. Используются только встроенные
модули Node и `wireguard-tools`.

## Диагностика

```bash
wg show wg0                       # текущие пиры и рукопожатия
journalctl -u trioz-vpn-agent -n 50
```

- `401` в логе — токен отозван или узел выключен в панели. Перевыпустите токен.
- `интерфейс wg0 не найден` — сначала `wg-quick up wg0`.
- пиры не появляются — проверьте, что узел в панели имеет назначение **VPN** и
  показывает статус «на связи».
